**核心结论**：两模型 pass@1 ≈ pass@5 ≈ pass@10（全部 99.1%；精确值 pass@1 = 99.05% = 1149/1160 通过单元、pass@5 = pass@10 = 99.14% = 115/116 任务——第三位小数因 078/051 的失败结构而不同，正文各处 "99.1%" 为两者共同的一位小数舍入）——单采样的 99% 不是运气，失败任务与采样方差无关；10 次采样下**唯一系统性失败任务是 078**（两模型均 0/10）。「LLM 写 Lom 低错误率」的证据链从「四模型单采样」升级为「双模型 × 10 采样 pass@k」，跨模型、跨采样、跨温度、跨时间稳健。

pass@k 为无偏估计（HumanEval / Codex 论文同式：`1 - C(n-c,k)/C(n,k)`，n=采样数 10、c=该任务通过采样数；Fraction 整数精确计算）。

## 失败分析

**078（effects）——两模型 0/10，歧义锚点题的证据链闭环**：

- 要求输出单行 `1700000000 boot`。本轮实测失败形态三种：两行拆分输出（`1700000000\nboot`，经典形态）、丢时间戳（只打 `boot`）、自创格式（`boot @ 1700000000`）。
- 跨证据稳定性：2026-08-03 基线（网页版）挂、2026-08-31 四模型 3 挂 1 过、本轮两模型 10 采样全挂（20/20 失败）。**它测的是模糊需求理解，不是 Lom 语言能力**。保留作锚点题，不改。
- **认知修正（如实记录）**：上轮报告「deepseek-v4-pro + thinking 是首个通过 078 的模型——思考模式能处理这个 prompt 歧义」**不成立**——本轮同模型 temperature=1.0 下 0/10 全挂。上轮的通过是默认温度/采样随机性下的边缘事件，不是 thinking 的稳定能力。差异变量为温度（本轮 1.0 vs 上轮服务商默认）。

**051（match_enum，v4-pro 9/10）与 104（control_flow，glm 9/10）**：temperature=1.0 下的单次采样方差（各 1 次失败），pass@5 已覆盖——正是多采样要区分的「随机错误 vs 系统性错误」。

## 方法论（与基线严格对齐 + 多采样扩展）

- 整分类 prompt 文件作为单条 user 消息（与 2026-08-03 基线及上轮复测完全一致）；每模型 **10 采样 × temperature=1.0**（pass@k 惯例设置，HumanEval 同款；上轮为单采样 × 服务商默认温度）。
- 评分器仍是 `eval/runner/run.ps1 -CandidatesDir`（只比对 stdout + 要求退出码 0），**评分事实源不二设**；passk_summarize 逐采样驱动它构建 116×10 通过矩阵。
- 模型/参数/起止时间/逐分类提取统计记录于各目录 `run_meta.json`；10 采样 × 2 模型 = 20 个分类回复 × 10 = 200 个 raw 文件全部留档可审计；提取 1160/1160 零缺失。
- max_tokens=16384；missing 候选（若有）计为不通过（本轮无此情形）。

### 如实记录的过程偏差

1. **采集过程两次服务端断连崩溃**（glm 74/100 时 RemoteDisconnected、deepseek 80/100 时 IncompleteRead）——原始管线的异常 catch 列表漏掉这两类（非 URLError 子类），已修复（`http.client.HTTPException` + `ConnectionError` 进重试分支）并断点续跑补齐（跳过 74/80 次已有调用，零重复成本）。断点续跑机制即为本轮管线新增能力，两次实战通过。
2. **run_meta 的起止时间是末段进程时段**（断点续跑覆盖语义），完整采集跨两个进程段/约 1.5 小时（deepseek）/约 20 分钟（glm）；每条原始回复的落盘即其生成时刻的留档。
3. **API key 中途失效更换**：上轮 key 在本轮开跑时已全部失效（deepseek `****a34f invalid` / glm 401），用户当日更新后双端点复通。新 glm key 支持 Coding Plan 端点（与上轮 glm-5.3 同路径）。
4. glm-5.3 走 Coding Plan 端点（`api/coding/paas/v4`），deepseek 走标准端点——与上轮各自路径一致。
