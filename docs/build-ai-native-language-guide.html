01

基础知识：开发一门编程语言需要掌握什么

编程语言的开发远比普通项目复杂，但并非高不可攀。核心知识围绕"源代码如何变成可执行程序"这一条流水线展开。

1.1 编译原理：语言开发的根基

开发一门编程语言最核心的知识是编译原理。标准教材是 Aho 等人所著的"龙书"（《Compilers: Principles, Techniques, and Tools》），它系统覆盖了编译的完整流水线[1]：

每个阶段的具体内容：

  • 词法分析（Lexing）：将源代码文本切分为 Token（如关键字、标识符、字面量、运算符）。用正则表达式描述 Token 模式，通过 DFA 实现[1]。
  • 语法分析（Parsing）：从 Token 流构造语法树（AST）。主要方法分自顶向下（递归下降、LL）与自底向上（LR、LALR）[1]。
  • 语义分析：类型检查、作用域解析、变量绑定——确认程序"有意义"。
  • 中间代码生成与优化：将 AST 翻译为中间表示（IR），进行优化（常量折叠、死代码消除等）。
  • 目标代码生成：将 IR 编译为机器码、WebAssembly 或其他目标格式。

1.2 类型系统：语言的灵魂

类型系统决定了语言能捕获哪些错误、AI 能否可靠生成代码。核心概念包括[2][3]：

  • 静态 vs 动态：静态类型在编译时检查（Java、Rust），动态类型在运行时检查（Python、JavaScript）。静态类型能在运行前捕获错误，可视为"有限的程序验证"[2]。
  • 强 vs 弱：强类型严格禁止隐式转换（Rust、Java），弱类型允许（C、JavaScript）。
  • 类型推导（Inference）：编译器自动推导变量类型，无需显式标注。Haskell/OCaml 用 Hindley-Milner 系统做全局推导，Rust/MoonBit 做局部推导[4]。
  • 健全性（Soundness）：若表达式良类型化为 τ，则所有归约要么发散要么归约到 τ 类型的值——类型在归约中被保持[4]。

1.3 运行时系统与内存管理

如果语言需要运行时（而非纯 AOT 编译为裸机码），还需理解[6][7]：

  • 垃圾回收（GC）：标记-清除、复制算法、分代收集。Java 用 G1/Shenandoah，Go 用并发标记-清除[8]。
  • 引用计数（RC）：Swift、MoonBit 采用，编译期插入计数代码，无 GC 暂停[11]。
  • 所有权系统：Rust 独有，编译期静态所有权规则，零运行时开销[31]。
  • 手动管理：C/C++，程序员显式分配/释放，性能极致但风险高。

1.4 标准工具与框架

不必从零手写所有组件，有成熟的工具可供使用：

工具/框架 用途 说明
ANTLR 词法/语法分析器生成 根据 .g4 语法文件自动生成 Lexer 和 Parser，支持多语言目标[12]
flex/bison 经典 Lex/Yacc 基于正则表达式与 LL/LR 文法[1]
Tree-sitter 增量解析库 构建具体语法树，随编辑高效更新，对语法错误稳健，纯 C11 无依赖[13]
LLVM 编译器后端 业界最成熟，提供优化与代码生成，被 Crystal、Zig（早期）等采用[14]
Cranelift 快速代码生成 Bytecode Alliance 出品，编译速度极快，常用于 WASM 运行时[15]
MLIR 多级优化编译框架 Google 推动，Mojo 基于 MLIR 构建[16]
最小知识集

如果要快速起步，最少需要理解：词法分析 + 递归下降解析 + 树遍历解释器。这三者足以在几天内做出一个能跑的语言原型。类型系统、GC、LLVM 后端可以后续逐步加入。

02

AI 辅助开发语言：是否可行

答案是肯定的——已有多个用 AI 构建编程语言的成功案例，但存在明确的能力边界。

2.1 案例：一天内用 Claude 造出语言（FAWK，2025）

开发者 Martin Janiczek 借助 Cursor Agent 驱动 Claude，在一天内构建了 FAWK（函数式 AWK 变体）的解释器。他先让 Claude 生成带示例的 README，再要求完整 Python 实现，同一会话还得到了 C、Haskell、Rust 版本[23]。

开发采用迭代模式：描述特性 → Claude 实现 → 端到端测试验证。难点特性（多维数组、闭包环境等）都正常工作；唯一翻车的是任意精度浮点，改用 mpath 后解决[23]。

坦诚的自述：Janiczek 自承"我对代码零知识……我只通过告诉它实现某个东西并写测试来交互"。代价是拥有一个能跑的解释器，却无法在不先学习代码库的情况下有效修改它[23]。

2.2 案例：16 个 Claude Agent 协作构建 C 编译器（2026）

Anthropic 研究员 Nicholas Carlini 用 16 个 Claude Opus 实例，在共享代码库上并行工作，从零构建一个基于 Rust 的 C 编译器，目标是能编译 Linux 内核。历经约两周、近 2,000 次 Claude Code 会话、约 20,000 美元 API 成本，产出约 10 万行编译器，能在 x86、ARM、RISC-V 上构建 Linux 6.9[24][25]。

重要限定：媒体强调"几乎无人干预"中的"几乎"——Carlini 仍需介入处理一些关键问题；这是探索自主软件开发边界的实验，而非全自动[25][26]。

2.3 AI 的能力边界：能做什么 vs 不能做什么

AI 能胜任 仍需人类主导
解释器/编译器原型快速搭建（数小时到数天） 类型系统设计与健全性证明
多语言实现并生成（Python/C/Rust 同时产出） 语言哲学一致性把控
编写并验证测试套件 性能优化（GC、编译器后端调优）
大规模代码生成（10 万行级） 长期可维护的架构设计
脚手架与样板代码 工具链全局把控与局部化设计
"很多 AI Coding 只提供情绪价值，而我们要重做一门编程语言。"—— 张宏波[30]

2.4 用 AI 开发语言的推荐方式

基于上述案例，如果要直接用 AI 编程工具开发一门新语言，推荐以下方式：

  1. 从解释器开始，不要从编译器开始：树遍历解释器比编译器简单一个数量级，AI 能更可靠地生成。FAWK 就是先做 Python 解释器再迁移到 C/Rust[23]。
  2. 测试驱动开发：先让 AI 写测试用例（包括语法解析、类型检查、运行结果），再让 AI 实现通过测试的代码。这是 FAWK 和 16-agent C 编译器的共同模式[23][24]。
  3. 分模块迭代：不要一次性要求 AI 生成整个语言。先做词法分析器 → 测试通过 → 再做解析器 → 测试通过 → 再做类型检查器，逐步叠加。
  4. 用现有框架降低复杂度：让 AI 使用 ANTLR 或 Tree-sitter 处理词法/语法分析，自己只聚焦语义和语言特性。
  5. 人工审查关键设计决策：类型系统设计、内存管理策略、并发模型——这些需要人类理解其权衡，不能完全交给 AI。
  6. 接受"能用但不可深改"的中间态：如果对编译原理零基础，AI 能给你一个能跑的原型，但你需要花时间学习它生成的代码才能继续迭代[23]。
03

发布与分发：GitHub 与文件格式

编程语言的发布与普通项目有区别，但 GitHub 仍然是标准托管方式。关键在于理解"发布什么"和"文件扩展名怎么处理"。

3.1 新语言可以直接上传 GitHub 吗？

可以，GitHub 是发布新语言源代码的标准方式。几乎所有现代语言都把源代码放在 GitHub。但发布物（编译器/解释器二进制）通常还通过专门网站 + 安装脚本分发[z1]。

语言 GitHub 仓库 独立网站 安装方式
Zig github.com/ziglang/zig ziglang.org 下载压缩包解压即用[z1]
MoonBit github.com/MoonBit moonbitlang.com moon 工具链安装[z4]
Naze github.com/jasonmamy/naze-lang naze-lang.com GitHub 仓库 + 网站[z6]
Zero (Vercel Labs) zerolang.ai curl -fsSL https://zerolang.ai/install.sh | bash[z8]
Dana github.com/aitomatic/dana (AI Alliance) pip install dana + GitHub[z9]
Codong github.com/liupgk/codong (仅 GitHub) GitHub 仓库 + Go 模块[z20]

8 种调研语言全部有 GitHub 仓库，其中 7 种还有独立网站。仅靠 GitHub 仓库分发的极少（如 Codong），但技术上完全可行。

3.2 发布的东西到底是什么？

一个语言发布到 GitHub 时，仓库中通常包含以下产物：

组件 必需性 说明
编译器/解释器源码 必需 核心产物，能编译/运行就行
标准库 必需 至少 IO、字符串、集合操作
README 必需 说明如何编译/安装/运行
示例代码 强烈推荐 HelloWorld + 几个典型用例
预编译二进制 强烈推荐 通过 GitHub Releases 发布多平台二进制
语言规范（SPEC） 推荐 早期可简化，Codong 就有 SPEC 文档[z20]
构建工具/包管理器 后续加入 早期可省略；MoonBit 从一开始内置 moon 是加分项[z5]
VS Code 扩展 后续加入 语法高亮；Zero 发布时就带了[z8]
LSP 服务器 成熟阶段 代码补全、跳转定义等
最小可行发布（MVP）

一个能跑的编译器/解释器 + 标准库 + README + 几个示例——这就是最简形态。Naze 的早期发布就是如此：GitHub 仓库包含编译器、395KB WASM 运行时、157 条语法规则、400+ 测试、109 个示例，明确标注 "research project and work in progress"[z6]。

3.3 文件扩展名：必须创造新的吗？

不是技术上必需的，但强烈建议创建。文件扩展名只是一种约定——编译器/解释器通常不依赖扩展名识别文件（可通过命令行参数或内容嗅探）。但操作系统、IDE、编辑器、GitHub Linguist 都依赖扩展名来关联语言和语法高亮[z12][z13]。

有注册表避免冲突吗？

没有全局性的文件扩展名注册中心。关键发现：

  • VS Code 明确声明不愿充当标准制定机构[z12]
  • GitHub Linguist 维护自己的映射表，冲突时用启发式规则猜测[z13]
  • 微软建议使用长扩展名以避免冲突[z14]

冲突的真实案例

  • .cs：C# 和 Smalltalk 共用[z13]
  • .p：Plasma 语言和 P 语言冲突[z15]
  • .asm：多种汇编语言共用[z12]

实践建议

  • 优先用长扩展名降低冲突概率：如 .moonbit 而非 .mb，.naze 而非 .nz[z14]
  • 查 GitHub Linguist 仓库确认扩展名是否已被占用
  • 提供 TextMate 语法文件（.tmLanguage）实现语法高亮——一份文件覆盖 VS Code、Atom、Sublime Text、GitHub 等众多编辑器，性价比最高[z19]
"The limited length of short extensions make them prone to extension collisions. Using long extensions significantly reduces the chances of a collision."—— 微软官方建议[z14]

3.4 "上传全新文件格式的文件"是怎么回事？

这是对"文件格式"概念的常见误解。源代码文件本质上就是文本文件——.py、.java、.rs 文件的内容都是纯文本（UTF-8 编码），扩展名只是一个约定标记。

因此，"上传全新文件格式的文件"实际上就是：

  1. 在你的新语言中写一些源代码（纯文本）
  2. 保存为 你的扩展名 文件（如 hello.naze）
  3. 像普通文件一样上传到 GitHub

不需要任何特殊的文件格式处理。GitHub 会把它们当作普通文本文件存储。唯一需要做的是向 GitHub Linguist 提交 PR，让你的扩展名被识别为你的语言（这样 GitHub 上会显示正确的语法高亮）[z13]。

04

语言特性分类：完整维度图谱

一门编程语言有多个正交的特性维度，不是简单的"面向对象 vs 过程式"二分法。以下是完整的分类体系。

4.1 类型系统维度

子维度 分类 代表语言 特征
检查时机 静态类型 Java, Rust, Go, MoonBit 编译时检查，运行前捕获错误[2]
动态类型 Python, JavaScript, Ruby 运行时检查，灵活但重构困难
严格程度 强类型 Rust, Java, Python, MoonBit 禁止隐式转换，类型不匹配即报错[11]
弱类型 C, JavaScript 允许隐式转换（如 1 + "1"）
推导方式 全局推导 Haskell, OCaml Hindley-Milner 系统，无需标注[31]
局部推导 Rust, MoonBit, Kotlin 局部变量自动推导，签名需标注[12b]
完全显式 Java, Go（部分） 所有类型必须显式声明

高级类型特性

  • 依赖类型（Dependent Types）：类型可以依赖值，如 Idris、Agda，能在类型层面表达程序性质[31]
  • 线性/仿射类型（Linear/Affine Types）：追踪资源生命周期，确保"用且仅用一次"[31]
  • 精炼类型（Refinement Types）：用逻辑公式约束类型（如 Int where x > 0），SMT 求解器自动验证[31]
  • 渐进类型（Gradual Typing）：TypeScript、Python 类型注解，允许动态与静态混合

4.2 编程范式维度

范式 核心思想 代表语言
命令式（Imperative） 逐步骤指令改变程序状态 C, Go, Rust（部分）
过程式（Procedural） 命令式 + 过程抽象 C, Pascal
面向对象（OOP） 数据和行为封装为对象，继承/多态/封装 Java, C#, Smalltalk
函数式（Functional） 纯函数、不可变性、高阶函数 Haskell, OCaml, F#
逻辑式（Logic） 声明事实和规则，通过推理求解 Prolog, Datalog
声明式（Declarative） 描述"做什么"而非"怎么做" SQL, HTML, Naze[20]

现代语言多为多范式（Multi-paradigm），允许在同一程序中组合不同方法。例如 Rust 同时支持命令式、函数式和部分 OOP 特性。

4.3 其他关键维度速览

维度 选项 代表
内存管理 手动 / GC / 引用计数 / 所有权 C / Java / Swift / Rust[11]
编译模型 AOT 编译 / 解释 / JIT / 混合 C / Python / Java / Dart
并发模型 共享内存线程 / async-await / Actor / CSP / STM / 代数效应 Java / JS / Erlang / Go / Clojure / Koka[31]
求值策略 急切求值 / 惰性求值 OCaml, Python / Haskell[31]
同像性 代码即数据 / 非同像 Lisp / 大多数语言
纯粹性 纯函数式（禁止副作用） / 非纯 Haskell / 大多数语言
效应系统 显式标注副作用类型 / 隐式 Koka, OCaml 5 / 大多数语言[31]
05

设计哲学：保留还是抛弃传统特性

这是最核心的设计问题。答案不是非此即彼——所有主流 AI 原生语言设计者都反对走极端，但各自的选择不同。

5.1 静态类型：AI 原生语言的共识

所有主流 AI 原生语言都选择了静态类型——这不是偶然，而是基于深刻的工程理由：

"动态语言一时爽，重构火葬场……解决这个问题的核心在于代码的可维护性，而这正是需要从编程语言的底层设计上来保证的。"—— 张宏波，MoonBit[10]

Zero 语言同样选择静态类型 + 代数数据类型，且 match 必须穷尽——"Agent 生成的代码必须是穷尽的。一个 Agent 如果生成了不完整的 match，编译器会拒绝它——这比依赖 Agent 的 prompt 工程可靠得多"[15]。

静态类型的三大理由[31]：

  • 可预测性："编译通过即正确"——类型约束在编译期捕捉逻辑错误，编译器反馈可作为外部信号驱动模型自纠正
  • 可组合性：纯函数与不可变性降低 AI 推理隐式全局状态的认知负担
  • 可验证性：类型即规约，依赖类型甚至能实现"生成即验证"

5.2 范式选择：OOP、函数式还是全新范式？

这是最具争议的维度。各语言设计者给出了不同回答：

MoonBit——实用主义中间路线

张宏波并未在 OOP 与函数式之间做非此即彼的选择，而是在 Python/JavaScript（自由）与 Rust/Lean（严格）之间寻找"最佳平衡点"[10]。MoonBit 使用 struct 而非传统 class，支持模式匹配、闭包等函数式特性[11][13b]。

Dana——用 Agent 替代 Class

Dana 最激进的设计是用 agent 替代 class 作为核心抽象[25]：

# 传统方式：静态类
class CustomerAnalyzer:
    def assess_risk(self, customer):
        return static_analysis(customer)

# Dana 方式：自适应 Agent
agent CustomerAnalyzer:
    def assess_risk(self, customer):
        risk_score: float = reason("assess customer risk", context=customer)
        return risk_score

Dana 认为"agent 原生编程模型"优于"带 AI 插件的类"[25]。

Zero——能力制 I/O + 显式错误

Zero 吸收 Rust 的所有权思想但语法更简单，引入"World 能力对象"——程序能做什么完全取决于运行时传了什么进来，没有隐式的全局 stdout[15]。

Naze——纯声明式

Naze 是纯声明式语言，用 column、row、rect 等结构描述 UI，没有传统的 OOP 或过程式概念[20]。

5.3 完全抛弃传统范式是否科学？

结论：不科学，不明智。所有主流 AI 原生语言设计者都反对完全抛弃传统范式。

张宏波明确表示 MoonBit"拒绝在'人类极简'与'机器极致严谨'两端走极端"[8b]。他进一步指出：

"我认为未来是人机协同的模式，而不是单纯给 AI 用的语言……只要人类还需要审查、理解和维护代码，那么语言就必须同时兼顾人类和机器的可读性。"—— 张宏波[10]

行业分析也认为："AI-native 开发通常是叠加在现有语言之上，而非完全取代它们"[32]。

5.4 OOP/过程式的区分对 AI 是否"无意义"？

这个问题没有统一答案，但有关键洞察：

张宏波的核心标准不是范式标签，而是规则复杂度：

"AI 本质还是机器，它更擅长学习简单、清晰的规则，而不是繁琐且充满例外的规则……比如 C++，很多规则都有例外，例外里还套着例外，AI 很难理解这种复杂逻辑。"—— 张宏波[9]

这意味着不是 OOP 或过程式本身的问题，而是规则一致性的问题。一个规则简单统一的 OOP 语言可能比一个规则混乱的函数式语言更适合 AI。

5.5 实际有效的设计策略

实践中真正有效的是"选择性保留 + 选择性创新"的中间路线，而非任何一极：

语言 保留的传统特性 创新的新特性
MoonBit 静态类型、struct、模式匹配 无需 async/await 的并发、局部化设计、let 关键字受限解码[10]
Zero Rust 式代数数据类型、所有权思想 World 能力对象、结构化 JSON 诊断、编译期安全沙箱[15]
Naze 声明式 UI 树（类似 JSX/SwiftUI） 157 条规则分层文法、GBNF 约束解码、Token 复杂度 O(n)[20]
Dana 类 Python 语法、类型标注 agent 替代 class、reason() 调用、POET 自学习[25]

5.6 给新语言设计者的核心建议

  1. 选择静态类型——这是 AI 原生语言的共识，没有例外[10][15][31]。
  2. 规则简单统一比语法简短更重要——"对 AI 来说，简短不是关键，规则简单统一才是"[9]。
  3. 不要完全抛弃任何范式——保留人类可读性，因为人类仍需审查代码[10]。
  4. 副作用必须显式化——Zero 的能力制 I/O、Aria 的代数效应、Argona 的 observe/effect 都体现了这一趋势[15][30][31]。
  5. 编译器作为 AI 的对话伙伴——把编译器设计为能给 AI 提供结构化反馈的系统（MBI 签名、JSON 诊断、类型洞）[10][15]。
  6. 局部化设计——修改一个函数的影响应严格限制在局部，让 AI 处理代码时只需聚焦当前代码块[10]。
  7. 用语法而非 prompt 保证正确性——Zero 的穷尽 match 比 prompt 工程更可靠[15]。
"如果一门语言过于复杂，以至于人类专家都很难一次性写对，那么 AI 大概率也无法稳定地生成正确的代码。"—— 张宏波[10]
