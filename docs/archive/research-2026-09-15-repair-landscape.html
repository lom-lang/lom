修复基建全景：传统工具链与 APR 学术线（第 3 轮调研·单主题轮）

轮次：第 3 轮（单主题）——源于用户对 positioning.html"只此一家"宣称的质疑（第 2 轮暴露判定边界问题，本轮补齐坐标系）
日期：2026-09-15
方式：文档级调研（不安装）——rustc/rustfix/cargo fix 官方文档、TypeScript code fixes 机制文档、APR 学术 survey 一手核对；R43 纪律执行
产出用途：为 positioning.html 的差异化宣称提供"整个修复生态坐标系"内的事实地基（当前仅在新兴 agent-native 语言两家中对比）

0. 结论摘要

  1. 用户质疑被证实，且比边界声明承认的更重：Rust 生态早在 cargo fix 时代（2018 前后）就具备结构化建议（span + suggested_replacement）+ 置信度分级（applicability 四级）+ 迭代自动应用到不动点（compile→fix→recompile 循环）——与 Lom 的 lom-fix/v1 + 置信度三级 + --apply 迭代收敛机制同构。Lom 在"机制层"没有原创性。
  2. Lom 真正的差异收窄为四点（相对传统基建）：①定位中心性——修复闭环是 Lom 的语言存在理由（repair-native）而非工具链附属；②修复语料回归网（fix_corpus 8 对作为 CI 常驻资产）；③高温 LLM 实测口径（修复类任务在 temperature=1.0 下 20/20）；④公开 schema 契约（lom-diag/v1 + lom-fix/v1 是语言规格的一部分，为 agent 消费而设计）。机制相同，产品形态与证据纪律不同。
  3. 学术谱系的关键分型（本报告的分析框架）：修复分两支——生成型修复（APR 学术线：从失败测试反推补丁，GenProg→学习型 AlphaRepair/CURE→LLM 型"ChatGPT 修 162/337 bugs 每 bug $0.42"，Defects4J 基准）与建议型修复（编译器诊断前向给出修复动作：rustfix/Lom/TS code fixes）。Lom 属后者，但 LLM-based APR 的兴起是 repair-native 定位的学术平行证据：世界在向"修复效率"投入，主流走"更强的补丁生成器"路线，Lom 走"为修复设计的语言与协议"路线——两条线互补且未被 APR survey 收录任何"语言级"工作（survey 分类的输入端只有代码/测试/缺陷报告）。
  4. positioning 的最终口径建议：从"修复执行自动化只此一家（新兴赛道内）"再收窄为——"把 rustfix 级别的修复基建做成语言的中心定位与公开契约，并配上修复语料回归网与高温 LLM 实测——这个组合在工程与学术两个谱系中均未见先例（截至本报告检索）"。

1. 工程谱系：传统自动修复基建

1.1 Rust：rustc → rustfix → cargo fix（机制最完整的前辈）

  • 结构化建议：rustc 诊断的 JSON 输出携带 suggestion 子诊断——span（文件/行列）+ suggested_replacement（替换文本）+ suggestion_applicability 四级：MachineApplicable（"definitely what the user intended... should be automatically applied"）/ MaybeIncorrect / HasPlaceholders / Unspecified（[rustc book · JSON 输出](https://doc.rust-lang.org/rustc/json.html)、[rustc-dev-guide](https://rustc-dev-guide.rust-lang.org/diagnostics.html)）。
  • 应用层：rustfix 是低层库——"you pass it the JSON output from rustc, and you can then use it to apply suggestions to in-memory strings"（[rustfix 文档](https://doc.rust-lang.org/beta/nightly-rustc/rustfix/index.html)）。
  • 编排层与迭代：cargo fix 以 --error-format=json 跑 rustc → rustfix 应用 MachineApplicable 建议 → 重编译 → 循环到不动点；cargo fix --clippy 应用 Clippy 机器建议、--edition 做 edition 迁移（[Cargo book](https://rustwiki.org/en/cargo/commands/cargo-fix.html)、[RFC 3085](https://rust-lang.github.io/rfcs/3085-edition-2021.html)）。
  • 生态消费：rust-analyzer / bacon / Emacs 插件直接消费 suggested_replacement+span 构造 quick-fix。

1.2 TypeScript：code fixes + fix-all + ts-fix

  • 语言服务在 src/services/codefixes/ 注册 provider（provideCodeFixes 返回带 fixName 的 CodeFixAction）；fix-all 机制：code fix 携带 fixId，编辑器调 getCombinedCodeFix 一次算出全文件同款问题（设计提案 [#14549](https://github.com/Microsoft/TypeScript/issues/14549)）；微软官方另有 ts-fix CLI 批量应用（[microsoft/ts-fix](https://github.com/microsoft/ts-fix)）。
  • ESLint --fix（fixer 返回文本替换）与 C# Roslyn analyzers + IDE code fixes 为同类机制，不赘。

2. 学术谱系：APR（自动程序修复）

  • 领域形态：APR 从失败测试/缺陷报告出发自动生成修复补丁，评测依赖缺陷基准（Defects4J 等）。三代演进：搜索/约束型（GenProg 传统）→ 学习型（AlphaRepair：cloze 式 token 级修复，[ICSE 2023](https://abhikrc.com/pdf/ICSE23.pdf)；CURE：预训练模型）→ LLM 型（"Fixing 162 out of 337 Bugs for $0.42 Each using ChatGPT"，[ISSTA 2024](https://lingming.cs.illinois.edu/publications/issta2024.pdf)；LLM-based APR 已在基准上超越传统方法——[arXiv survey 2025](https://arxiv.org/html/2506.23749v1)、[ACM CSUR 2024 learning-based survey](https://dl.acm.org/doi/10.1145/3631974)）。
  • 与本报告主题的分型（本报告提出，供讨论）：生成型（APR：测试失败 → 反推候选补丁 → 测试验证，产物是"猜测的修复"）vs 建议型（rustfix/Lom/TS：编译器诊断 → 前向的结构化修复动作，产物是"编译器已知答案的建议"，如拼写/未导入/迁移）。前者解决"没人知道怎么修"，后者解决"知道怎么修但每次手写"。
  • 关键观察：LLM-based APR survey 的分类学（输入=代码/测试/缺陷报告）中没有"语言级/工具契约级"工作——即"为修复而设计的语言"在学术谱系中同样缺位（截至本报告检索的 survey 覆盖面）。

4. 对 positioning 的影响（供下次更新）

  • 现有 §4 判定边界声明方向正确但需再进一步：不只是"概念非首发"，而是机制三件套（建议结构/置信度/迭代应用）在 Rust 生态已完整存在多年——Lom 的宣称应落在"组合的产物形态"上：中心定位 + schema 契约 + 修复语料回归 + 高温实测，四个维度同时成立的组合未见先例（截至检索）。
  • APR 学术线为 repair-native 提供平行论据（修复是真实且被大量投入的问题域）而非竞品（不同修复类型）；对外叙事可引"生成型 vs 建议型"分型说明 Lom 与 LLM-APR 的互补关系（Lom 的诊断码把"建议型修复"的确定性发挥到极致，为"生成型"兜住高频低难错误）。

5. 方法与局限

  • 文档级调研；rustc/TS 机制来自官方文档与设计提案（一手），APR 来自 survey 与代表论文（一手）；未实测 cargo fix/ts-fix 的当前行为（机制文档足够本报告目的）。
  • "未见先例（组合四维度）"仍是检索范围内的判定：未穷尽 scalafix/SonarLint/IntelliJ 意图动作等长尾（机制同类，按 §1.2 同类推断）；APR survey 覆盖面以两份 survey 的分类学为据。
