§0 结论摘要（先读）

  1. 发现社区目录站 agentlanguages.dev：35 家"为 AI agent 写代码而设计"的语言， 分三营（Syntactic 表征派 / Verification 验证派 / Orchestration 编排派），目录最后更新 2026-06-14。赛道规模远超第 1 轮估计（当时深读 2 家、广搜零散）。 目录提供 llms.txt / llms-full.txt 机器可读版，本身就是"为 agent 设计"的。Lom 不在 目录中。
  2. 三营分类学对 Lom 定位是净增益：三营的共同底色是"防错"（token 层防歧义 / 编译期防语义错 / 流程层防 agent 失控）；Lom 的 repair-native 是"治错"——接受错误 必然发生，让修复循环（诊断→建议→应用→回归）成为语言的存在理由。在 35 家的 描述层面，没有一家以修复闭环为核心卖点，但存在部分元素：Codong （"structured JSON errors with fix/retry fields"，69★）与 X07（"quickfixes the toolchain applies deterministically"，8★）。机制层无原创的结论（第 3 轮）再次被 强化；"四维组合未见先例"在目录描述层面仍然成立，但样本基数应如实写为 "35 家目录 + 2 家深读"。
  3. Zero CLI 补深（第 2 轮未尽项）：修复是 CLI 一级命令（zero fix --plan --json = typed repair plan）；check --json 诊断含 repair metadata 字段；LSP quick-fix 已落到五个具体诊断码（TAR002/TYP009/ ERR002/ERR003/PUB001）；另有 zero skills（skill 文档与编译器版本捆绑， agent 可加载）与 zero tokens（token 计数意识）。Zero 在"计划层"的完整度 比第 2 轮认知更进一步，但仍未见修复语料回归网与置信度分级（文档层面）。
  4. 行动启示（记录，非裁决）：① Lom 符合目录收录标准（"bar is intent"）， 提交收录属于对外发布动作——冻结裁决下不做，挂账解冻后；② positioning 一页纸的 判定边界节已按本轮样本面同步（35 家目录 + Codong/X07 部分元素如实列出）； ③ Mog 的"spec 3200 tokens"口径与 Zero 的 skills 捆绑，对 Lom 的 SPEC_FOR_AI 尺寸意识是同源参照（记录，不动语言面）。

§1 agentlanguages.dev：赛道目录站（本轮最大发现）

来源：https://agentlanguages.dev/（本轮 fetch 全文）。定位原文：社区维护的 "programming languages designed for AI agents to write"目录。关键事实：

  • 规模与时点：35 家语言，目录页标注 last updated 2026-06-14（星数同为该日 刷新时点）——即本轮拿到的是约三个月前的快照，检索时点 2026-09-16。
  • 三营分类（目录自己的分类学，比我们的"三范式"更成体系）：
    • Syntactic（表征派）：问题出在 token 层歧义——X07（JSON AST 替代文本）、 NERD（英文关键词替代运算符）、Magpie（SSA 表面语法）、Mog（spec 3200 tokens）、 Codong、Tacit 等；
    • Verification（验证派）：目录导语原文 "The model doesn't need to be right. It needs to be checkable."——Vera、MoonBit、NanoLang（193 条 Coq 定理、零公理）、Aver（Lean4/Dafny 风格）、Vow（ESBMC 模型检查）、Intent、 Prove（反向：明确禁 AI 训练）；
    • Orchestration（编排派）：导语原文 "It isn't a language problem. It's an agent-coordination problem."——Boruna、Fabro（1.2k+★，工作流 harness）、Pel（CMU）、Quasar（Penn）、Marsha（2023-07，最早的"LLM 即编译器" 实验之一，466★）。
  • 收录标准（原文大意）："The bar is intent"——收录显式为 AI/agent 写作而 设计的语言；不收"运行时调用 LLM"的语言；"唯一创新是'works with Copilot'的不算"。 Lom 完全符合收录标准（repair-native 是显式设计意图）。
  • 机器可读：提供 /llms.txt 与 /llms-full.txt，另有 markdown 伴随版——目录本身也在为 agent 消费而设计。
  • 编辑方式：社区编辑、GitHub 仓库公开接受提交。下轮复核： 目录维护者与 Vera 作者的关系（本轮上下文压缩后未能从原文直接再核验，不作为事实引用）。

§2 三营分类学与 Lom 的位置：防错三营，治错第四维

目录三营的共同底色是防错：表征派防 token 歧义、验证派防语义错误、编排派防 agent 流程失控——全部押注"让错误不发生"。Lom 押的是另一面：错误必然发生，让修复便宜 （诊断→结构化建议→迭代应用→修复语料回归）。这个"治错"维度在 35 家的描述层面没有 对应条目。

但必须如实记录部分元素（描述层面，未读源码）：

  • Codong：错误 JSON 带 fix/retry 字段——"建议型修复"的字段级实现；
  • X07：quickfix 由工具链确定性应用——Lom "迭代应用到不动点"的最小形态；
  • Zero：typed repair plans + repair metadata + LSP quick-fix 五码（§4）——计划层 完整度最高的同行。

结论（承接第 3 轮口径并扩样本）：Lom 的机制层无原创（rustc/cargo fix 早已有之， 目录里 Codong/X07 又添两个小型例证）；差异化仍在四维组合——修复闭环作为语言存在 理由 + schema 作为语言契约 + fix_corpus 修复语料回归网 + 高温 LLM 实测口径——该组合在 35 家目录描述层面仍未见完整对应。样本边界从"2 家深读"扩到"35 家目录 + 2 家深读 + Zero CLI 一手补深"。

§3 广域样本归位：BirdDisk 与 AINL（本轮早期一手 fetch）

  • BirdDisk（github.com/Jawbreaker1/bird_disk_code，3★/78 commits， 个人 POC）：不在目录中，但其设计支柱与 Lom 高度重合——结构化 JSON 诊断 + fix-its、三后端（VM/WASM/native）差分测试作默认测试、require-tests 门禁、 确定性输出格式化，并有"LLM 全程生成 Yahtzee"自证实验。定性：独立收敛到同款支柱的 小样本，反证该设计方向的自然性；工程量与证据链与 Lom 不可比。
  • AINL（whitepaper 一手）：graph-first 工作流编排编译系统（"Canonical IR = nodes/edges; everything else is serialization"）。相邻赛道（编排营外围），非直接 竞品；但其 bounded repair loops + 结构化诊断（lineno/span/kind/suggested fixes）与 Lom 修复理念同款，属编排营向修复理念的渗透信号。
  • 观点领袖信号（WebSearch 线索，未深读下轮可选）： Armin Ronacher "A Language For Agents"博文（2026-02）；"use boring languages with LLMs"反方讨论并存——赛道热度的两面。

§4 Zero CLI 补深（第 2 轮未尽项，本轮一手原文）

来源：https://zerolang.ai/cli（本轮 fetch）。第 2 轮已确认 fix --plan 计划层同构；本轮增量细节：

  • 修复是一级命令：zero fix --plan --json <input>——"Ask for a typed repair plan"。修复与 check/fmt/test 平级，不是附属模式。
  • 诊断 JSON 含修复元数据：zero check --json 的诊断字段包括 code、 span、expected/actual 细节、help、repair metadata、targetReadiness。
  • LSP quick-fix 已落到具体诊断码：文档 LSP smoke 节展示 quick-fix code actions surfaced from zero fix，覆盖 TAR002 / TYP009 / ERR002 / ERR003 / PUB001 五码——即"编辑器内一键应用修复"在 Zero 已是文档化承诺。
  • zero skills：与编译器版本捆绑的 skill 文档，agent 按工作流加载 ——与 Lom 的 SPEC_FOR_AI 思路同源，但 Zero 做到"版本化捆绑 + CLI 分发"。
  • zero tokens：token 计数意识进入 CLI（与 Mog 的 3200-token spec 口径同源）。
  • xfail 机制：测试框架支持 expected failures 标注——工程口径与 Lom 差分纪律 相邻（Lom 用 §11f 已知分歧白名单 + 探针守护，方向不同）。

对比结论：Zero 在计划层（typed repair plan、repair metadata、LSP quick-fix）完整度 高于此前认知；文档层面仍未见 Lom 的三件东西——修复执行闭环（迭代应用到不动点的 默认工作流）、fix_corpus 修复语料回归网（历史修复案例作为回归资产）、置信度 分级。第 2 轮"Zero 计划层同构、Lom 独有执行层与语料层"的结论维持，且论据更实。
