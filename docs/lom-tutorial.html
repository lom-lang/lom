第一部分:先建立心智模型

1.1 这个项目在做什么

解释器(Interpreter):一个"读程序并直接执行它"的程序。你用 Python 写代码时,运行它的 python.exe 就是解释器。本项目就是 Lom 语言的解释器,只不过它是用 Rust 写的。
宿主语言:用来"实现"另一门语言的语言。这里 Lom 是被实现的语言,Rust 是宿主语言——就像 CPython 用 C 实现 Python 一样。

一句话:用 Rust 手写了一个新编程语言 Lom 的解释器和配套工具链。你写的 .lom 文件,由这个 Rust 程序读进来、理解、执行。

你是 AI 专业的,我用你熟悉的类比:

编译原理概念AI 领域的类比
源代码一段待理解的文本
Lexer(词法分析)Tokenizer:把字符流切成 token
Parser(语法分析)把 token 序列解析成结构化的树(类似 constituency parsing)
AST(抽象语法树)句子的语法树,是后续一切处理的中间表示(IR)
Interpreter(解释器)直接在树上"执行语义"
Typechecker执行前的静态校验,类似约束检查
token(词法单元):源代码被切碎后的最小有意义单位。比如 let x = 3 会切成 4 个 token:关键字 let、标识符 x、运算符 =、整数字面量 3。注意:这和 LLM 的 token 不是一个东西,只是都叫这个名字——LLM token 是子词片段,编译器 token 是带语法类别的符号。
AST(Abstract Syntax Tree,抽象语法树):把线性文本变成树形结构。表达式 1 + 2 * 3 变成树之后,* 是 + 的子节点,运算优先级就"长"在树的形状里了。后续所有模块(执行、类型检查、修复)都操作这棵树,不再碰原始文本。

关键区别:编译器 vs 解释器。 编译器(如 C/Rust)把源码翻译成机器码再运行;解释器直接读源码执行。Lom 两者都有:主路径是树遍历解释器(tree-walking interpreter)——不生成字节码、没有虚拟机,拿到 AST 后直接递归遍历这棵树、边遍历边算结果;Phase 7 又加了一条WASM 编译后端(lom build --target wasm),把同一棵 AST 翻译成 WebAssembly 二进制,交给 node 跑——同一个程序、两种载体、输出逐字一致(CI 强制比对)。

字节码 / 虚拟机(VM):更高级解释器(如 Java、Python)会先把源码翻译成一种"中间指令集"(字节码),再由一个模拟 CPU 的程序(虚拟机)执行这些指令,比直接遍历语法树快。Lom 的 WASM 后端走的是类似思想:编译成字节码(WASM 指令),由现成的虚拟机(node/V8)执行。

为什么先是树遍历? 三个原因:

  1. 项目目标不是性能,是验证"AI 原生语言设计"这个 thesis——树遍历解释器是实现一门语言最快的方式;
  2. 语言特性还在快速迭代(一个月加了 match、闭包、效应系统、Map……(2026-08-02 立项)),解释器改起来成本最低;
  3. 零依赖手写(Cargo.toml 里 [dependencies] 是空的,CI 有专门 gate 强制),不引入 logos/crates,保持整个项目可控、可读、可被 AI 维护。

那 WASM 后端算不算"又要性能了"? 是,但目标变了:Phase 7 的动机是①把递归深度天花板从解释器的 ~10⁴ 层解放到宿主栈可调(V8 --stack-size 下 10⁵ 层实测通过);②性能对照实测——解释器循环被编译掉后,自举式 O(n²) 负载纯计算提速约 49 倍(7.10);③为"可移植的参考实现"铺路(RFC-0003 全量自举的载体)。差异化押注没变——lom fix 修复闭环仍是项目身份,JIT/MLIR/AOT 原生机器码依然不做。

thesis:英文"论题/主张"。这里指项目想证明的核心命题——"一门专门为 LLM 编码习惯设计的语言,能让 LLM 写代码的错误率更低、修复更快"。整个项目就是在做实验验证这个主张。
零依赖(zero-dependency):Rust 项目通常在 Cargo.toml 里声明第三方库(叫 crate),编译时自动下载。这个项目一个都没声明,lexer/parser/JSON 解析/WASM 二进制编码全部手写——好处是供应链攻击面为零(SECURITY.md 有正式承诺,CI 用 awk 扫 Cargo.toml 强制执行)、构建可复现,代价是一切都得自己造。

面试被问"性能怎么办",分两层答:短期靠 WASM 后端(编译掉解释器开销);长期明确不做 JIT/MLIR/张量——差异化在 lom fix 工具链,不在执行速度。

通俗解读

把整个项目想象成"你发明了一门新的外语,然后雇了一个翻译官"。.lom 文件是用这门外语写的信,那个 Rust 程序(约 23,700 行)就是翻译官——他拿起信,逐句读懂,然后照信里的指示办事(打印东西、算数、读写文件)。

这位翻译官有两种工作模式:口译(树遍历解释器)——拿到信当场一边读一边做,信改了他随时重读;后来他又学了笔译出版(WASM 后端)——把整封信正式翻译装订成一本"机器能直接照着执行的小册子"(WASM 二进制),以后办同样的事不用再读原信,快得多。两种模式翻译出的结果逐字一致(这是 CI 每天三平台强检的)。这个项目想验证的始终是"这门外语本身设计得好不好"——所以先造口译官(迭代快),等语言稳定了再补笔译官(性能+可移植)。

JIT(Just-In-Time 编译):程序运行过程中把热点代码动态编译成机器码提速的技术,Java/V8 都靠它。MLIR:LLVM 生态的多层中间表示框架,做编译器后端的基础设施。这两个都是"高性能语言"的标配,Lom 明确说不做。

第二部分:逐模块拆解

2.1 Lexer:手写分词器(src/lexer.rs,695 行)

游标(cursor):一个记录"现在读到哪了"的位置指针。Lexer 就是一个游标在源码字符数组上从左往右爬,边爬边切 token。

核心机制:一个游标在字节数组上移动,三个原子操作:peek()(看一眼不消费)、advance()(消费一个字符并维护行/列计数,遇 \n 就 line+1)、next_token() 按首字符分派(数字→扫数字、"→扫字符串、字母→扫标识符/关键字)。

通俗解读

Lexer 的工作像极了你读一句英文时的下意识动作:眼睛从左往右扫,看到字母就拼单词,看到数字就拼数,看到空格就断开。peek 就是"瞟一眼下一个字符再决定":看到 1 时是整数,但瞟到后面跟着 . 和更多数字,就知道该拼成小数 3.14 而不是两个独立的数。

比如源码 let x = 42 经过 lexer 出来就是:[关键字 let][名字 x][等号 =][整数 42],每个后面都标注着行列号,像快递单上的地址,后面哪一步报错都能指回源码的准确位置。

两个面试细节:

最长匹配(maximal munch):词法分析的经典规则——能合成更长的 token 就优先合成。看到 - 时不能急着定性,要先看下一个字符:是 > 就合并成箭头 ->,否则才算减号。
  • 多字符运算符用"最长匹配":看到 - 先消费,再 peek 下一个,如果是 > 就合成 Arrow(->),否则是 Minus(lexer.rs:291 附近)。|> 和 |、=> 和 == 同理。
  • 每个 token 携带 (line, col)(SpannedToken,lexer.rs:84)。这看似不起眼,却是后面两个重要特性的数据基础:换行敏感语法 + 所有诊断定位。

容错机制(重点):lexer 有两个入口。严格版 tokenize() 遇到错误直接放弃;容错版 tokenize_recover()(lexer.rs:147)出错后回退到保存点、强制前进一个字节、丢弃坏字符、继续扫描,返回 (tokens, errors)——错误和正常 token 一起出来。这就是"AI 原生"的第一层:LLM 一次拿到全部错误,而不是修一个错再跑一次。

通俗解读

对比两种批改作业的老师:严格版老师看到第一个错别字就把卷子一扔,"改完再来";容错版老师把整份卷子读完,用红笔圈出所有错别字一起还给你。哪个对 AI 友好显而易见——AI 改一遍的成本不低,当然希望一次拿到所有问题。

"强制前进一个字节"是容错版不卡死的秘诀:遇到实在看不懂的字符,把它扔掉,脚往前挪一步,继续读后面的。这样无论代码多烂,lexer 保证能走到文件结尾,只是手里多了一张"错误清单"。

一个容易答错的点:很多人会以为"换行敏感"意味着 lexer 会产出 Newline token。Lom 不是——换行符被当空白直接跳过(lexer.rs 的 skip_whitespace_and_comments,205 行——next_token 根本不见空白),换行信息只存在于每个 token 的行号里,由 parser 比较相邻 token 行号来判断。面试官如果深挖这里,答错就露馅。

2.2 AST:中间表示(src/ast.rs,352 行)

三层结构:Program { items: Vec<Item> } → Item 是函数/枚举/导入三种 → 函数体是 Block { stmts: Vec<Stmt>, tail: Option<Expr> }。

Vec<T> / Option<T>:Rust 的标准类型。Vec<T> 是动态数组(一堆 T);Option<T> 表示"可能有也可能没有"(Some(值) 或 None)——Lom 语言里的 Option 设计就是从 Rust 借来的。
尾表达式(tail expression):代码块最后一行如果是个"表达式"而不是"语句",它的值就自动成为整个块的值。所以 Lom 函数最后一行写 x + y 就是返回值,不用写 return。这个设计借自 Rust/Ruby。

面试要点:

  • 尾表达式设计:Block 最后一个表达式就是块的值(和 Rust 一样),return 只用于提前退出。这是为 LLM 减错的设计——"忘了写 return"这个错误类型被从语言里消除了(DESIGN_RATIONALE.md §9)。
  • Stmt::Hole(空洞):parser 解析失败的地方插入一个占位节点,AST 结构保持完整(ast.rs:181)。作用有三:收集全部错误、下游工具(lom info/fix)还能消费部分正确的 AST、执行到洞才报错(坏代码被天然隔离)。
  • Span(位置信息)只挂在声明级:FnDecl/EnumDecl 记录了完整起止位置(Phase 3.2 加的),表达式节点还没有。这是务实的渐进策略——先让诊断能指到"哪个函数",表达式级定位留给将来的 LSP。
  • MatchExpr.end_line 单独记录 match 的 end 关键字行号——为了后面自动修复能在 end 前精准插入缺失分支。记住这个字段,它串起了 typechecker 和 fix 两个模块。
通俗解读

用一个迷你程序感受这三层结构。下面这段 Lom 代码:

fn double(x: Int) -> Int
    x * 2
end

变成 AST 就是:Program(整个文件)里装着 1 个 Item(类型是"函数");函数里装着 1 个 Block(函数体);Block 里没有普通语句,只有一个尾表达式 x * 2——它同时也是函数的返回值,所以不需要写 return。树的最小叶子是 x 和 2,它们的父节点是 * 运算。

而 Stmt::Hole(空洞)就像拼图缺了一块时先放个灰色占位块:画面(树)还是完整的,你知道哪里缺了,其他部分照常能看、能分析。这对 AI 至关重要——LLM 写错了第 50 行,前 49 行的分析结果仍然可用。

LSP(Language Server Protocol):编辑器(VS Code 等)和语言工具之间的标准协议,提供悬停提示、跳转定义、自动补全。Phase 4.3 已用声明级 Span 实现了基础 LSP(lom lsp):悬停显示函数/枚举签名、补全候选、诊断推送。表达式级精确定位留待后续阶段。

2.3 Parser:递归下降 + 三个特色机制(src/parser.rs,1820 行)

递归下降(Recursive Descent):最直观的语法分析写法——语法里每种结构对应一个函数,函数之间互相调用(像顺着语法规则往下"下降"),遇到嵌套就递归。比如"解析表达式"的函数会调用"解析加法",后者又调用"解析乘法"……全是手写函数,不用任何解析器生成工具。

机制一:优先级链

表达式解析不用任何表驱动,就是一串函数互相调用,每个优先级一个函数,低优先级的调用高优先级的:

parse_or → parse_and → parse_comparison(== < >) → parse_pipeline(|>)
  → parse_addition(+ -) → parse_multiplication(* / %) → parse_unary(- !)
  → parse_question(后缀 ?) → parse_postfix(调用/索引/字段) → parse_primary(字面量/括号/闭包/if/match)
优先级链怎么体现优先级? 以 1 + 2 * 3 为例:parse_addition 先调用 parse_multiplication 拿"左操作数",而后者会贪婪地把 2 * 3 整个吃掉再返回——于是乘法子树天然长在加法下面,优先级就通过"谁调用谁"编码进了函数调用关系里。
左结合(left-associative):a - b - c 算 (a - b) - c 还是 a - (b - c)?前者叫左结合(数学运算符几乎都是)。用"while 循环不停把新节点包在旧节点外面"就天然实现左结合。

每个函数的模式都一样:先调下一级拿左操作数,然后 while 循环"如果当前 token 是我这级的运算符就吃掉、再调下一级拿右操作数、组装节点"——这天然实现了左结合。

面试可能问"1 + 2 |> f 怎么解析":因为 |> 在链上低于 +,所以是 (1+2) |> f。有测试钉死这个行为(parser.rs 的 pipeline 优先级测试组)。

通俗解读

"每个优先级一个函数、低优先级调用高优先级"听着抽象,其实就是小学数学"先乘除后加减"的代码版。看 1 + 2 * 3 怎么被解析:

① 入口 parse_addition(管加减)上来先说"我不急着看 +,先让管乘除的把左边算出来"→ 调用 parse_multiplication;
② parse_multiplication 也不急,先让 parse_primary 拿一个数 → 拿到 1。它看看下一个 token 是 +,不是 * 或 /,就把 1 原样交回去;
③ parse_addition 看到 +,吃掉,再叫 parse_multiplication 去算右边 → 这次右边是 2 * 3,parse_multiplication 会把 2、*、3 全吃掉,组装成乘法小树交回来;
④ 最终拼成 1 + (2*3)——乘法树被压在了加法下面。

规律:越是"先算"的运算符,它的函数在链条越深处(越后被调用),吃 token 越贪婪,在树里位置越低。优先级不是靠查表,是靠"谁调用谁"这条链天然形成的。

(诚实提示:文件头注释自称"Pratt 解析",实际是固定优先级链,不是真正的 Pratt 算法。面试时按链式结构讲,别背注释。)
Pratt 解析(Pratt parsing):另一种表达式解析算法,用一张"结合力(binding power)数值表"驱动单个循环处理所有运算符,代码更短但更抽象。Lom 的头注释说有,实际没用——这是文档与代码不一致的一个例子。

机制二:换行敏感怎么实现

is_newline_before()(parser.rs:172):比较当前 token 和前一个 token 的行号,不同就是"跨行了"。它在五处改变解析行为,最经典的两个:

  • 0\n-1 是两条语句(0 和 -1),不是 0 - 1——因为 - 前换行了,不当二元减法;
  • 0\n(-1) 不是函数调用 0(-1)——跨行的 ( 不接在前面表达式后面。

为什么要这个设计?SPEC_FOR_AI §1.9 说了:换行当语句分隔符(像 Go),但缩进不敏感(不像 Python)。因为 LLM 经常缩进错误,缩进敏感会让"缩进错一格"静默改变语义——这是对 LLM 最不友好的特性,所以 Lom 用 end 关键字闭块、缩进纯装饰。

通俗解读

Python 里缩进就是语法:if 下面缩进的行属于 if,少缩进一格代码含义就变了——而且程序不报错,只是悄悄做错事。LLM 生成几十行代码时缩进错误很常见,于是 bug 神不知鬼不觉地混进去。

Lom 的选择是"明码标价":块从哪开始、到哪结束,全都用 end 这个单词写出来,缩进只是给人看的排版。就像写文章,Python 派靠"段落空两格"暗示结构,Lom 派直接写"第一节……第一节完"。对容易手滑的作者(LLM)来说,显式的 end 容错得多。

机制三:容错解析 + 同步点恢复(这个项目的招牌之一)

同步点(synchronization point):容错解析的"安全锚点"——解析出错后,解析器扔掉若干 token,跳到一个"几乎肯定能重新开始"的关键字处继续。就像你在嘈杂录音里听丢了半句话,等下一个句子的开头再接上。

parse_recover()(parser.rs:83)的三级恢复:

  1. 顶层:某个 fn/enum 解析失败 → 跳到下一个 fn/enum/from 关键字再续(这些叫同步点);
  2. 语句级:某条语句失败 → 插入 Stmt::Hole → 跳到块结束符(end/elif/else)或"下一行开头的语句起始 token";
  3. match 级:某条分支失败 → 保守策略,直接跳到本 match 的 end(因为分支里的块也有 end,跨分支恢复容易误吞)。

还有一个防死循环保险:ensure_progress——每次恢复至少前进一个 token。

这套机制存在的理由就是 AI 原生:LLM 生成 200 行代码有 3 个错,传统编译器报第 1 个就退出,LLM 要迭代 3 轮;Lom 一次报 3 个错 + 附带可用的部分 AST,1 轮修完。eval 里 error_repair 15/15 就是在验证这个。

通俗解读

三级恢复可以想象成"听一段有噪音的录音做听写":

① 顶层恢复 = 某一段完全听不清?跳过,等听到下一个"第 N 章"(fn/enum 这类大标题)再接着记;
② 语句级恢复 = 某一句话听不清?在稿纸上留个"□"(就是 Stmt::Hole),等听到换行后的下一句开头继续;
③ match 级恢复 = 听不清的地方正好在一处带很多"小结尾"的段落里?那就保守一点,整段跳到"大结尾"(本 match 的 end)再说——因为乱猜可能把大结尾也吞掉,损失更大。

"防死循环保险"则是铁律:每次跳过至少往前挪一个词。不然听写卡在一个地方永远原地踏步,程序就死机了。

run(program)          注册所有顶层函数/枚举 → 找到 main → 执行(552 行)
 → exec_block         逐条执行语句,最后算尾表达式(685 行)
  → exec_stmt         let/if/while/for/return/match(707 行)

必懂概念一:Value 枚举

枚举(enum)类型:Rust 的核心类型,表示"一个值是这几种形态之一"。Value 枚举的意思是:Lom 运行时的任何一个值,必然是 Int / Float / Bool / Str / Unit / 闭包 / 枚举值 / 记录 / 元组 / 列表 / 字典 之一——用大 match 分情况处理。Lom 语言自己的 enum 语法也是向 Rust 学的。

运行时一切值都是 Value:Int/Float/Bool/Str/Unit + Closure(闭包)+ Enum(Ok/Err/用户变体)+ Record(结构记录)+ Tuple + List + Map(Phase 5.20 加的字典)。注意 Result/Option 不是特殊类型,就是内置枚举 Ok/Err/Some/None。

List 和 Map 的内部表示是 Phase 5.19/5.20 两场"换心手术"的结果,面试值得讲:

  • List = 不可变链表:ListVal 是 Nil | Cons(Rc<ConsNode>)(interpreter.rs:58)。头插/取头/取尾 O(1),永不整表复制——代价是随机访问 list_get 从 O(1) 退化为 O(n) 走查(遍历式代码无感)。换之前,"取尾"每次 elems[1..].to_vec() 整表复制,自举式环境查找是近立方复杂度(n=800 要 87 秒),换后同基准 1.9 秒(46 倍,Phase 5.19 实测);
  • Map = 共享可变的字典:Value::Map(Rc<RefCell<HashMap>>)。查 2000 条 × 2000 次从 18.1 秒变 55 毫秒(330 倍,其中 ~48ms 是进程启动,纯计算约 2500 倍,Phase 5.20 实测)。刻意与 List 相反的语义:map_set 就地改、两个名字共享同一份——因为实践中字典就是"共享记事本";想要不可变的结构化数据应该用 Record。写代码时别指望"旧 Map 还在",要快照就用 map_keys 重建。map_keys/map_values/json_stringify 的输出按键排序(确定性)。
通俗解读

解释器在运行时手里只把玩一种东西:Value。可以把它想成"万能收纳盒",盒子上贴着类型标签。整数 42 装进去,贴"Int";字符串 "hello" 装进去,贴"Str";一个函数打包装进去,贴"Closure"。

这样做的好处是:解释器每一步只需要问一句"你这盒子上贴的是什么标签?"——加法时发现两边贴的是 Int 就相加,发现一个 Int 一个 Str 就报"类型不匹配"。这就是"动态类型"的含义:类型信息贴在值上,运行时才检查,而不是写在变量上提前检查。

最后一句值得品味:Ok/Err 并没有什么魔法,它们只是两个预置的标签名。Lom 的错误处理不是语言引擎里的特殊机制,就是普通数据——这正是"错误即值"设计在实现层的体现。

必懂概念二:作用域链与闭包(面试最高频)

Rc<RefCell<T>>:Rust 的两个智能指针组合。Rc = 引用计数共享所有权(多个持有者,计数归零才释放内存);RefCell = 内部可变性(允许在运行时可变修改,绕过 Rust 编译期的借用检查)。组合起来就是"多方共享 + 大家都能改"——闭包捕获环境的标准实现,也是 GC 语言的廉价替身。

作用域是 Rc<RefCell<Scope>> 组成的父指针链表:

struct Scope {
    vars: HashMap<String, Value>,
    parent: Option<ScopeRef>,   // 查不到就往父层查
}
作用域(scope):变量"可见"的范围。函数体、if 块各自开一层新作用域;内层查不到的变量沿 parent 链去外层查——这套链表结构就是"词法作用域"的运行时骨架。
遮蔽(shadowing):内层作用域定义了和外层同名的变量,内层"遮住"外层。因为查询从当前层开始,先命中内层,自然实现遮蔽。
  • let 只写当前层(所以内层同名变量自然遮蔽外层,shadowing);
  • 赋值沿链向上找已存在的变量改掉;
  • 闭包捕获:闭包创建时把当前作用域的 Rc 直接存进闭包里(interpreter.rs:864/986 两处闭包构造)——不做自由变量分析,整个环境按引用共享,O(1);
  • 闭包调用时以"定义处环境"为父创建新作用域(interpreter.rs:1130-1144 的 eval_call 分支),而普通函数以 globals 为父。
闭包(closure):"函数 + 它出生时能看到的变量环境"打包在一起的值。比如 let add = fn(x) x + base end 里的 base 不是参数,是从定义处环境"捕获"来的——这就是闭包和普通函数的区别。
自由变量分析:严格的编译器实现会静态分析闭包"到底用到了哪些外部变量",只捕获那几个。Lom 不做分析、整个环境 Rc 一锅端——实现简单,代价是内存持有范围变大。

这就是词法作用域(静态作用域):闭包看到的是"它出生的地方"的变量,不是"它被调用的地方"。这是几乎所有语言面试的必考题,你能用 Rc 引用计数共享环境讲清楚实现,就超过了 90% 的候选人。

通俗解读

作用域链可以想象成"一串用门连起来的房间":每个函数体、每个 if 块都是一间房,房里有自己的抽屉(变量表),墙上有一扇门通向外面那间房(parent)。找变量的规则:先翻自己房间的抽屉,没有就推门去外间找,再没有就继续往外,直到最外面的大厅(globals),还找不到就报"未定义"。

闭包是怎么回事?一个经典例子:

fn make_counter() -> Fn
    let mut count = 0
    fn step() -> Int
        count = count + 1
        count
    end
    step        # 把内层函数 step 当返回值交出去
end

make_counter 执行完,按理说它的"房间"该拆了,count 也该消失。但 step 被交出去时,偷偷带走了那把通向自己出生房间的钥匙(房间 Rc 的引用计数 +1)——只要 step 还活着,那间房就拆不掉。之后每次调用 step(),它都能回到出生房间改 count。这就是"闭包捕获环境":函数值带走了它的出生环境,这就是计数器能一直累加的原因。

词法作用域 vs 动态作用域:词法作用域看代码写在哪(定义处),动态作用域看函数从哪被调用(调用处)。现代语言几乎全是词法作用域。记住对比,面试官可能追问。

追问"Rc<RefCell> 有没有问题":有——闭包如果存回自己捕获的作用域,会形成 Rc 循环引用,引用计数永不为零 → 内存泄漏。标准解法是 Weak 弱引用。本项目没做,因为:作用域 parent 链本身是树(外层不指内层),实际很难成环;且解释器进程跑完就退,泄漏由 OS 回收。这是"正确性换简单"的有意取舍——能主动说出这个 trade-off 是加分项,别说成"没有问题"。

Weak 弱引用:Rc 的配套指针,不算入引用计数。环中把其中一条边换成 Weak,环就有了"弱点",计数可以归零。标准库的解法,代价是使用时要多一步"检查目标是否还活着"。

必懂概念三:控制流信号

return 和 ? 都不是普通求值,怎么从深层递归里"跳出来"?

  • return 把值包成 ControlFlow::Return(v),一路向上冒泡到函数边界(exec_block/exec_stmt 的多个分支,interpreter.rs:684-698 一带集中处理);
  • ? 遇到 Err(e)/None 时抛一个特殊的 RuntimeError::EarlyReturn(...)(定义在 interpreter.rs:352),传播到函数边界转成提前返回(interpreter.rs:1019 的 ? 求值分支)——复用错误通道实现控制流,是树遍历解释器的经典手法。
通俗解读

为什么 return 需要特殊机制?因为解释器执行你的代码时,自己也在层层套娃:执行 main → 执行函数 f → 执行 if 块 → 计算表达式 → 计算子表达式……可能套了十几层。这时 Lom 代码里一句 return 42,意思是"整个 f 到此为止,答案是 42"——十几层套娃得一起收工。

做法像接力赛:return 把 42 装进一个贴着"紧急撤离"标签的信封,每层套娃收到信封都不拆,原样往上传;传到 f 的边界,才拆开把 42 作为 f 的结果。? 更省事:它直接把错误塞进 Rust 自己的"报错通道"(Err)往上飞,同样到函数边界被接住。两种手法殊途同归——用一个特殊标记穿透任意多层递归。

为什么需要"信号"? 解释器是层层递归的函数调用(eval_expr 套 eval_expr 套 exec_block……)。Lom 代码里的一个 return 可能要穿透十几层 Rust 递归——普通返回值做不到,只能用特殊标记一路往上抛,函数边界处接住它。

其他速记

  • |> 在哪层实现:parser 原样存 Expr::Pipe 节点,求值时去糖——x |> f(y) 把 x 插到参数列表最前面变成普通调用 f(x, y)(interpreter.rs:1044);
  • 效应(! [IO])运行时零作用:纯静态注解,解释器根本不读这个字段(ast.rs:81 注释明说),检查全在 typechecker;
  • stdlib 是硬编码的:模块表(8 个模块:io/string/math/list/json/map/file/env,interpreter.rs:412-469)+ import 白名单 + call_builtin 里一个巨型 match 分发到 Rust 原生实现;只有 println/print 是 prelude,其他必须显式 from string import {len}——这是防 LLM 幻觉的设计:没 import 就报"符号未导入,需 from X import {...}",错误信息本身就是修复指令(interpreter.rs:1447)。
通俗解读

"stdlib 硬编码"的意思是:所谓 Lom 标准库,并不是用 Lom 写的一堆 .lom 文件,而是解释器这个 Rust 程序内部写好的一张"功能菜单"。Lom 代码调 len("abc") 时,解释器收到请求,在菜单里查到 len,转身调用 Rust 自己的字符串长度函数,把结果包回 Value 盒子里递回去。Lom 程序从头到尾不知道背后干活的是 Rust。

"效应运行时零作用"也很好懂:! [IO] 注解就像餐厅员工胸前的工牌,写着"我有权进后厨"。检查工牌的是门口的质检员(typechecker);真正炒菜的厨师(interpreter)根本不看工牌——到他那儿时菜照炒。所以效应系统不影响程序跑起来的行为,只影响"检查时报不报警告"。

去糖(desugar)/ 语法糖:语言为了好写提供的便利写法叫"糖";解释器/编译器内部把它翻译成更基础的形态叫"去糖"。x |> f(y) 是糖,f(x, y) 是糖化开之后的样子。
prelude(预导入集):不用 import 就能直接用的那一小撮内置符号。Lom 只放了 println 和 print 两个,其余全要显式导入——故意克制,防幻觉。

2.5 Typechecker:渐进式类型检查(src/typechecker.rs,2472 行)

类型检查(type checking):在运行之前静态地核对"类型对不对"——比如字符串不能和整数相加、函数调用参数个数要对。静态语言(C/Rust)强制全查,动态语言(Python)全不查,Lom 站在中间,所以叫"渐进式"。

"渐进式(gradual)"在这个项目里是四个具体行为,面试要逐条说(注意第 1 条在 2026-08-22 评审整改后变了,老版本的教程/资料还写着"默认不检查"):

  1. 默认运行路径也检查——lom file.lom 直接跑时照常执行类型检查,诊断输出走 stderr、永不拦截执行(main.rs:374-381,注释原文"类型检查可见化")。此前的行为是运行完全跳过检查,被外部评审指出"'渐进式类型'名不副实"后整改;--check/--json 则是只检查不执行;
  2. 类型错误是 Warning 不是 Error——退出码仍为 0,程序照跑;只有名称解析错误(未定义变量、重复定义)才是 Error 会阻止运行。逻辑:名称错了 = 程序员笔误,必须拦;类型不匹配 = 可能是检查器推断能力不够,只提醒;
  3. 推断不出就放行——内部用 TypeOrUnknown::{Known, Unknown},Unknown 一律跳过不报错(typechecker.rs:94);
  4. 通配类型 _Any——stdlib 函数签名用 _Any 兼容一切,避免误报。

对齐运行时语义的三处修正(第三轮评审整改,2026-08-22,各有回归测试锁定)——不知道这三条容易答出"检查器比解释器严"的旧印象,恰好是反的:

  • Int/Float 混合算术记 Float 不报 TYPE001(解释器早就提升,检查器此前没跟上);
  • 管道 arity 假阳性修复:x |> add(1) 的 TYPE003 现在把管道左值计入(此前误报"期望 2 得 1");
  • 包符号感知:新增 check_program_with_externals(main.rs:338 调用),从 lom.toml 依赖图收集包的公开符号传入,包函数不再喷 NAM003 假 error(根因:解释器 load_packages 注册包符号,检查器此前不知情)。
通俗解读

"渐进式"用老师改卷来对比就明白了:

· Java/C 是严厉老师:类型有一个错,整份卷子零分,不许运行;
· Python 是放养老师:根本不批改,错不错跑起来才知道;
· Lom 是佛系老师:每次交卷都顺手用铅笔标注(warning,走 stderr 打个招呼),但从不因批注扣分——卷子照跑、分数照给;只有"写了不存在的名字"这种明显笔误才用红笔拦下(error)。看不懂的地方(Unknown),他诚实地说"我判断不了,先放过",而不是硬猜一个然后误伤。

为什么对 AI 要佛系?因为 AI 的迭代模式是"快速生成 → 跑 → 看反馈"。如果类型检查动辄拦路,AI 大量时间耗在伺候检查器上;宽松一点,程序先跑起来,诊断信息照样给 AI 看,让 AI 自己决定改不改——这正是"工具服务 AI,而不是审问 AI"的设计立场。2026-08-22 的整改只是把"铅笔标注"从"只有点名才看"改成"每次都给"——批改更勤了,但"永不拦路"的承诺一字未动。

退出码(exit code):程序结束时返回给操作系统的整数,0 = 成功,非 0 = 失败。CI 脚本、AI agent 都靠它判断"这次跑没跑成"——所以"warning 退出码仍是 0"意味着类型错误不挡路,这是渐进式的关键机制。

两遍分析:第一遍只收集所有函数签名和枚举定义进表,第二遍才检查函数体。为什么两遍?让前向引用和互递归可检查——检查 f 时 g 的签名已经在表里了。

前向引用 / 互递归:前向引用 = 代码里先用了后面才定义的函数;互递归 = f 调 g、g 又调 f。如果一遍从头扫到尾,扫到 f 时还不认识 g。先收集全部签名再查函数体,就解决了。

三个特色检查:

  • 结构等价:记录类型按字段名递归比较,顺序不敏感——{x: Int, y: Int} 和 {y: Int, x: Int} 是同一类型(typechecker.rs 的结构等价比较函数)。这是 TypeScript 式结构类型,LLM 不用记类型名,只记"形状";注意 7.7 修过一个坑:WASM 后端的 Record 比较曾只比较字段名不比内容,已修成逐字段内容比较,双后端一致;
  • match 穷尽性(MAT001):收集已覆盖的变体名,没 _ 通配就对照枚举全表,缺谁报谁;诊断行号填 match 的 end 行——给自动修复留的钩子;
  • 效应检查(EFF001):规则一句话——调用方的效应声明必须是被调方的超集。纯函数(无 ! [...])调了 println(声明了 [IO])就报警告。两条豁免:main 隐式拥有全部效应(强制 main 写注解是"给 LLM 增加无意义负担",typechecker.rs:43 注释);闭包继承外层函数的效应集。

2026-08-31 新增第四个检查:不可变重赋值(MUT001,v0.20.0)——此前 let x = 3; x = 4 静默通过(spec 说"应被拒绝",实现零校验,第四轮评审自查抓出,用户裁决按 warning 级落地)。现在 TypeEnv 多了一张与 vars 平行的 mutables 表,define 时显式记录可变性:let 不带 mut、函数参数、for 循环变量、match 绑定、元组解构绑定全部不可变,对它们重赋值(含 += 去糖后的形式)报 MUT001 warning。仍是佛系老师:只批注、不拦路,解释器零改动。有一个文案细节值得记住:诊断消息不能写死"let 声明未带 mut"——参数也会命中,而 Lom 没有 mut 参数,hint 若诱导 LLM 写 fn f(mut x) 就是诊断在误导它唯一的读者。AI 原生语言的诊断文案是给 LLM 看的,准确性要求和编译器正确性同级。

通俗解读

把效应想成"门禁权限"。每个函数签名上的 ! [IO, Clock] 就是它的门禁卡清单:IO = 能碰外部世界(打印、读写文件),Clock = 能读时钟。规则是:你调用的函数拥有的每张卡,你自己也得有。一个"纯函数"(没有卡)调了带 IO 卡的 println,就像没卡的人想蹭别人的卡进后厨——检查器报警:"你想用 IO,先在自己签名上声明"。

两条豁免也合情理:main 是老板,天然有所有卡(总不能要求入口函数连打印都要写申请);闭包是员工的"随身工具",跟主人用同一套卡。

这套系统对 AI 的价值:LLM 写代码时很容易"随手 println 调试",效应声明让这些副作用在签名层面显形;而且 EFF001 警告附带的修复方案是机械唯一的(在签名加 ! [IO]),所以能被 lom fix 自动修——这是 2.6 闭环故事里的主角。

结构类型 vs 名义类型:判断两个类型"是否相同"的两种哲学。名义类型(nominal,如 Java 的 class)看名字——都叫 Point 才相等;结构类型(structural,如 TypeScript)看形状——字段一样就相等。对 LLM 来说记形状比记类名+继承体系容易,所以 Lom 选结构类型。
match 穷尽性(exhaustiveness):match 必须覆盖枚举的所有变体,漏一个就报警。这逼着 LLM 处理 Err 分支,而不是假装错误不存在——"错误必须被面对"是 Lom 错误处理哲学的核心。
效应系统(effect system):让函数在签名里声明自己会产生的副作用(读写文件、打印、读时钟……),如 ! [IO, Clock]。学术上源自 Koka 等研究型语言。作用:纯函数和副作用函数边界清晰,工具链(和人/AI)一眼看出"这段代码会不会碰外部世界"。

2.6 AI 工具链:这个项目的差异化核心

这是面试最该重点讲的部分,因为它是项目存在的理由。四个阶段串成管道:

① lom-diag/v1:结构化诊断(diagnostics.rs)

每条诊断是一个 JSON 对象:severity / stage / code / message / line / col / source_line / is_hole / hint。

为什么这么设计(对应 LLM 的 function calling/structured output 思维):

  • code 稳定错误码:NAM003 永远=未定义变量。LLM 可以按码学修复模式,不依赖措辞多变的英文散文——和你让模型输出 JSON 而不是自然语言是同一个道理;
  • source_line + hint 自包含:每条诊断自带出错行源码和修复建议,LLM 不用回读文件就能修;
  • 错误码分段:LEX(词法)/PARSE(语法)/TYPE(类型)/MAT(match)/NAM(名称)/EFF(效应)/RUNTIME。
通俗解读

传统编译器的报错是写给人看的散文:"Type mismatch: expected Int, found Float near line 42"。人看得懂,但 AI 要从这段话里抠出"哪个阶段、什么错、在哪行、怎么修",全靠理解自然语言——模型的注意力被浪费在解析报错文本上。

Lom 的做法是把报错变成"标准工单":字段固定的 JSON。这和你调用 LLM API 时要求它"只输出 JSON、不要寒暄"是同一个思想,只是方向反过来——这里是工具对 AI 说话。稳定错误码 NAM003 相当于工单编号:AI 见过几次就知道 003 类工单的标准处理流程,不用再理解千变万化的英文措辞。

source_line(出错行原文)和 hint(修复建议)塞进同一张工单,意味着 AI 不用再掉头去读源文件——省一轮交互,省一份上下文。这对按 token 计费、上下文有限的 LLM 都是实打实的节约。

function calling / structured output:让 LLM 按预定 JSON 格式输出、供程序消费的技术。Lom 的诊断设计就是这个思想的镜像:不是 LLM 输出 JSON 给人,而是工具输出 JSON 给 LLM——格式稳定、字段自包含,模型才好处理。

② lom-fix/v1:修复计划(fix.rs,1749 行——M1/M3 + 3.2b span 接线后从约 900 行长到这么大)

输入诊断,输出"修复计划":每条诊断挂若干 FixAction,action 有 insert/delete/replace/hint 四种。replace 曾经是"定义了但没人生成"的空架子,2026-08-25 修复引擎深化 M1 落地了它:NAM003/NAM004 拼写建议现在会产出真正的 Replace 动作(两条规则 fix.rs:553-649)。定位方式在 2026-08-31(Phase 3.2b)升过级:此前 typechecker 诊断没有表达式级位置(line/col=0),只能靠 find_token_occurrences(fix.rs:866) 整词扫描源码(跳过字符串里的转义引号、遇 # 跳过行注释、记录字段场景要求名字前是 .);现在表达式节点全带 span,诊断自带精确位置,precise_occurrence(fix.rs:830) 直接产出单点 Replace——但留了两道防呆:字节列→字符列换算(lexer 按字节记列,含中文的行会分叉),以及"诊断位置的字节内容必须真的是那个名字"的校验,不符才回退扫描。

关键是置信度分级:

级别含义例子
High修复唯一无歧义,可自动执行行末补 "、EFF001 补效应注解、MAT001 补内置变体分支(Ok(_) 模式已知)、M3 的行末/文末补 )
Medium方向明确但需确认用户枚举补分支(参数未知——安全边界)、M1 的拼写替换(猜"你想写的名字",猜错改错)、M3 的 match 缺 end(插入位置可能歧义)
Low只有建议"期望 X 得到 Y"有多种修法

retry 字段:有具体可粘贴文本 → true(值得重试);纯文字建议 → false。

③ lom-apply/v1:写回源文件(apply.rs,723 行)

两道安全闸:只有 High 且非 Hint 的修复才会被应用;再验坐标合法性。

偏移漂移(offset drift):所有修复坐标都是按"原始文件"算出来的。如果先应用了第 2 行的插入(文件变长了),原本第 5 行的修复位置就错位了。经典解法:从后往前改。

经典算法题:逆序应用。 所有修复坐标基于原始源码,如果先改前面的(第 2 行插入字符),后面的坐标就漂移了。解法:按行号降序、同行按列号降序排序,从文件末尾往前改,互不影响(apply.rs:169-176)。

M2(2026-08-25)把单趟应用升级成迭代闭环(main.rs:892 的 apply_iterative):应用一轮 → 重新诊断 → 再修,直到"无高置信度可应用项"或"源码不再变化"为止,上限 5 轮防震荡。修复历史每轮各写一条 entry(带 round 字段;读旧格式无 round 的按 1 处理)。为什么需要迭代?因为第一轮修复可能暴露(或引入)新的可修错误——修好缺的 ) 之后,才看得见下一行的类型错误。这正是"LLM 反复跑修复"的机器版,只是 LLM 完全不用在场。

还有一个 Unicode 细节:诊断坐标是字符列,写文件要字节偏移,中文环境下必须换算("你好\nworld" 中 (1,2) = 字节 3,因为"你"占 3 字节,apply.rs:285 的 line_col_to_offset)。

通俗解读

"逆序应用"用一个生活场景就懂了:你拿红笔改论文,批注上写着"第 2 段末尾加一句"、"第 5 段开头删两字"。如果你先改第 2 段——加了一句,原文变长了——那"第 5 段开头"现在还是原来那个位置吗?不是了,所有后续批注的位置都作废了。

聪明做法:从最后一处批注改起。先改第 5 段,再改第 2 段——后面怎么动都不影响前面的位置。代码里就是把所有修复按"行号从大到小"排序再逐个执行,一行排序代码解决一整类 bug。

字符/字节问题类似:人按"第几个字"数,磁盘按"第几个字节"存。英文时代一个样,中文时代"你"一个顶三个字节,不换算的话,写入位置可能切在汉字正中间,文件直接变乱码。

字符 vs 字节:UTF-8 编码下,一个英文字母占 1 字节,一个汉字占 3 字节。人说的"第 2 列"是字符序号,文件写入要的是字节位置——混用会切在汉字中间导致乱码。所有处理文本的工具都会踩这个坑。

④ fix-history.jsonl:NDJSON 历史(fix_history.rs)

NDJSON(Newline-Delimited JSON):每行一个独立 JSON 对象的文本格式,也叫 JSON Lines。对比"一个大 JSON 数组":追加新记录时数组格式要读出整个文件、解析、加一项、重写;NDJSON 直接在文件末尾加一行,O(1)。日志类数据的标准选择。

为什么 NDJSON(每行一个 JSON)而不是 JSON 数组?追加是 O(1)——打开文件加一行就行;数组格式每次都要读-解析-重写整个文件。且单行损坏不影响其他行。

一个闭环故事(面试可以直接讲)

LLM 写了个纯函数里调 println → typechecker 报 EFF001(warning,带函数签名行号)→ lom fix 生成 High 置信度 insert 计划("在签名行末插入 ! [IO]")→ --apply 逆序写回 → M2 迭代:重新诊断,看还有没有可修的,最多 5 轮 → 每轮历史追加一行带 round 的 NDJSON → LLM 重跑通过。诊断→计划→执行→再诊断→追溯全自动,LLM 只需要读 JSON。 这就是 "LLM-repair-native" 的完整含义——也是本项目与 MoonBit("让 LLM 一次写对")差异化的核心("写错后高效修复",不重生成)。
通俗解读

这个闭环最值得记住的一点:整个修复过程没有让 LLM 参与"猜"。传统方式是 AI 写错 → 人/AI 读报错 → 重新生成整段代码(可能引入新错);Lom 的方式是工具链自己把"哪行哪列插入什么字符"算好,AI 只需要点点头(或者连点头都不用,--apply 直接改)。

置信度分级则是给"自动化"上的一道保险:修复方案唯一确定(High)才自动动手;拿不准(Medium/Low)就只给建议。这和自动驾驶的分级很像——路况简单就自动开,路况复杂就交还方向盘。盲目自动修改源码比不修改更危险,这条边界是这个工具链工程成熟度的体现。

2.7 REPL(Phase 4.2,已完成)

REPL(Read-Eval-Print Loop):交互式解释器——你敲一行,它立刻执行并打印结果,像 Python 的 >>> 提示符。读入(Read)→ 求值(Eval)→ 打印(Print)→ 循环(Loop)。对人和 AI 都是"低成本试错"的环境。
  • 输入完整性判定 is_input_complete:逐字符扫描,跟踪括号深度、字符串状态、块关键字(fn/if/while/for/match 需配对 end,只在行首识别,enum 单行不需要 end);全部归零才算"输入完了,可以执行";
  • 会话保持:一个长寿命 Interpreter 实例贯穿会话;fn 定义注册进函数表,let 绑定直接写进 globals 作用域(exec_repl_block,interpreter.rs:619),所以下一条输入能看到上一条的变量;
  • 错误不退出会话——对 LLM 试错友好。
通俗解读

REPL 和普通运行的区别,就是"微信聊天"和"写信"的区别。普通运行:你把整个 .lom 文件(信)交给解释器,它一口气执行完,结束;REPL:你一句它一句,语境一直在——你上句说"令 x 等于 5",下句问"x 是多少",它记得。

"会话保持"的实现因此特别直白:整个聊天期间,解释器这个对象一直活着不销毁,你定义过的函数存在它的函数表里,let 的变量存在它的全局作用域里。所谓"记住上下文",其实就是"不关机"。

为什么这个项目在乎 REPL?因为 LLM 调试代码的天然节奏就是"试一句 → 看结果 → 再试"。REPL 把每次试错的成本降到一行代码,而不是改文件、保存、重新跑整个程序。

为什么 REPL 需要"完整性判定"? 用户敲 fn add(x: Int) 回车,函数还没写完——REPL 不能急着执行,得等他继续输入直到 end 出现。判断"这段输入是否构成完整单元"就是括号配对 + 块关键字配对的计数问题。

2.8 LSP:让编辑器懂 Lom(Phase 4.3,已完成)

JSON-RPC 2.0:基于 JSON 的远程过程调用协议——客户端(编辑器)发一个 {"method": "textDocument/hover", "params": {...}} 请求,服务端(Lom)回一个 {"result": {...}} 响应。LSP 规定了一批方法名(hover/completion/didOpen 等)和参数格式。
  • 传输层:stdio 上的 JSON-RPC 2.0——每条消息前加 Content-Length: N 头,编辑器和 Lom 通过标准输入输出通信,不需要开端口;
  • 悬停(handle_hover):鼠标停在函数名/枚举名上,返回它的签名(fn add(x: Int, y: Int) -> Int)。靠声明级 Span 定位——Phase 3.2 给 FnDecl/EnumDecl 加的 span 字段这里派上用场;
  • 补全(handle_completion):输入时弹出候选——当前文件的所有函数、枚举及变体、import 的符号、内置变体(Ok/Err/Some/None)、关键字;
  • 诊断推送(compute_diagnostics):文件一打开/一改动,重新跑解析+类型检查,把诊断转成 LSP 格式(行号转 0-based)推给编辑器,编辑器画红波浪线。
通俗解读

LSP 是让"编辑器变聪明"的通用协议。没有 LSP,你写 .lom 文件就像在记事本里写——没有提示、没有报错、没有跳转。有了 LSP,VS Code(或任何支持 LSP 的编辑器)启动 lom lsp 当后台服务,你在编辑器里看到的红色波浪线、悬停提示、自动补全,全是这个后台服务算出来推给编辑器的。

有趣的是,LSP 复用的全是前面造好的轮子:诊断推送就是 Diagnostics::from_parse_result + typechecker::check_program,悬停就是读 FnDecl.span 定位再格式化签名。LSP 本身不引入新的语言分析能力,只做"协议翻译"——把 Lom 内部的诊断/签名翻译成编辑器能听懂的 JSON-RPC。

2.9 包管理:让 Lom 长出项目骨架(Phase 4.4,已完成)

清单文件(manifest):描述一个项目的元数据文件——项目叫什么、什么版本、依赖哪些其他包。Rust 用 Cargo.toml,Node 用 package.json,Lom 用 lom.toml。它放在项目根目录,是整个项目的"身份证"。

前面的章节讲的都是"单文件 Lom 程序"——一个 .lom 文件里写完所有函数。但真实项目会拆成多个文件、多个包,这时候就需要包管理:声明依赖、解析依赖、让 from mathlib import { square } 能找到 mathlib 包里的 square 函数。

lom.toml 清单格式

Lom 的清单文件用手写 TOML 解析器读(零依赖,不引入 toml crate),格式极简:

# 项目根目录的 lom.toml
name = "app"
version = "0.1.0"

[dependencies]
mathlib = { path = "mathlib" }

三个字段:name/version 是项目身份;[dependencies] 表里每行是一个依赖,键名是包名(必须和依赖包 lom.toml 里的 name 一致),值目前只支持 { path = "相对路径" }(本地路径依赖,不联网拉包)。

依赖解析:DFS + 循环检测

resolve_dependencies() 用深度优先搜索(DFS)递归遍历依赖树:读根项目的 lom.toml → 对每个依赖,跳进它的目录读它的 lom.toml → 再递归它的依赖……直到所有依赖都加载完。

循环依赖(A 依赖 B,B 依赖 A)会让 DFS 无限递归,所以要用 visiting 集合记录"当前递归链上正在访问的包"——如果再次遇到,说明出现环,立即报 CircularDep 错误并给出环路径。

符号收集:顶层自动公开

Lom 的包管理做了一个简化决策:顶层 fn 和 enum 自动公开,不需要 pub 关键字。collect_public_symbols() 扫描包里所有 .lom 文件,把顶层 FnDecl 的函数名和顶层 EnumDecl 的枚举名收进 public_symbols 列表。

这和 Rust 的 pub fn 显式公开不同——Rust 追求精确控制可见性,Lom 追求"零负担复用"。对 LLM 来说,少一个 pub 关键字就少一个遗忘点(LLM 写 Rust 常忘 pub 导致符号不可见)。

导入解析:process_import 的三级查找

当你写 from mathlib import { square },解释器的 process_import() 按顺序查三个地方:

  1. 标准库模块(io/string/math/list/json/file)——内置,无需声明依赖
  2. 外部包——查 self.packages 里有没有这个包,有则校验 square 在它的 public_symbols 里(不在则 PKG006 "符号未导出")
  3. 都没有 → PKG005 "未知模块/包",错误信息列出所有标准库名提醒你

lom build 子命令

lom build 不编译(树遍历解释器没有编译步骤),它做的是"依赖体检":读 lom.toml → 解析依赖图 → 对每个包的源码跑解析+类型检查,报告哪个文件通过、哪个文件有诊断。这是 CI 友好的:依赖坏了能立刻发现,不用等运行时才报错。

通俗解读

包管理就是给 Lom 长出"项目骨架"。之前你只能写单文件程序,现在可以拆成多个包、多个文件,像 Rust 的 cargo workspace 一样组织代码。lom build 相当于 cargo check——不跑代码,只检查依赖和类型对不对。

设计上做了两个简化:① 只支持本地路径依赖(path = "mathlib"),不联网拉包(避免引入注册表/网络/版本锁的复杂度,留待将来);② 顶层符号自动公开(无 pub 关键字,降低 LLM 遗忘负担)。这两个简化让包管理在 16 个单测内完整跑通,零新依赖。

2.10 自举与新语法缺口(Phase 5,已闭环)

自举(self-hosting / bootstrapping):语言的"成年礼"——用 Lom 语言本身写出 Lom 的解释器/编译器,并且它能正确处理 Lom 代码。鸡生蛋、蛋生鸡:第一版解释器用 Rust 写(种子),之后语言就可以"养活自己"。

Phase 5 的目标是自举:证明 Lom 强大到能写出自己的解释器。2026-08-19 收尾评估:阶段目标"语言能养活自己"达成——最终形态 stmt_interp.lom(1450 行 Lom)具备完整编译器流水线(词法→语法→静态检查→求值),14 个测试程序 39 条输出与 golden 文件逐字一致(CI 强制比对)。但要诚实:这个迷你语言只是完整 Lom 约 20% 的子集(无 Float/Record/Map/闭包/管道/?/效应/模块),全量自举(Lom 写的完整 Lom 解释器)是独立 phase 级工作量,已作为 RFC-0003(Phase 8 候选)正式立项调研。全里程碑列表(examples/bootstrap/):

  • 5.0 可行性验证:用 Lom 写了一个迷你解释器(mini_interp.lom)——逐字符扫描切 token、递归下降解析、求值,正确处理运算符优先级。结论:递归 enum + match + 字符串逐字符扫描,足够表达编译器核心三阶段;
  • 5.1 元组解构:自举时发现的"头号缺口"——LLM 自然写 let (a, b) = ... 但语言拒绝,于是补上了(AST/parser/解释器/类型检查全链路);
  • 5.2 语句层自举:stmt_interp.lom 在表达式之上加了 let/if/块,环境用函数式链表管理;
  • 5.3 for 遍历 List(v0.4.1):for x in xs 支持列表——此前只能遍历 String(逐字符)和 Int(0..n),遍历 List 会报 RUNTIME000。解释器加了 Value::List 分支,类型检查器同步推导元素类型(List<Int> 的元素就是 Int)。
  • 5.4 字符串拼接提升(v0.4.1):"n = " + 42 合法了——+ 的任一侧是字符串时,另一侧自动转成显示文本再拼接(此前必须手动 int_to_string,LLM 几乎必踩)。
  • 5.5 复合赋值(v0.4.1):n += 1 这种写法合法了(+= -= *= /=)。实现上用了一个偷懒但正确的技巧:去糖——parser 把 n += 1 直接翻译成 n = n + 1 的语法树,后面的解释器和类型检查器一行都不用改,所有现有检查(变量是否存在、类型对不对)自动生效。
  • 5.6 range 表达式(v0.4.2):for i in 1..10 合法了。设计很省:1..10 不求值为新类型,而是直接变成整数列表 [1,2,...,9](左闭右开)——于是 5.3 刚做好的 for-in-List 和整个 list 模块自动全部适用,一行新的运行时机制都不用写。
  • 5.7 match guard(v0.4.2):match 分支可以带条件了——m if m > 0 => ...,模式先匹配、条件再过滤,条件不成立就继续试下一分支。一个细节:带条件的分支不算"必然覆盖",类型检查器仍会要求你写 _ 兜底(和 Rust 一样)。
  • 5.8 具名函数作为值(v0.4.2):let f = double 合法了——具名函数和闭包字面量地位平等,可以直接传给高阶函数。实现只有几行:把函数的参数表和函数体连同全局环境打包成一个闭包值,之后走现成的闭包调用路径。这为将来的 list_map/list_filter 铺平了路。
  • 5.9 高阶 list 标准库(v0.4.3):函数式三件套 list_map/list_filter/list_fold 到位。从 5.3 到 5.9 像搭积木:for 能遍历列表(5.3)→ 字符串随便拼(5.4)→ 1..6 就是列表(5.6)→ 函数能当值传(5.8)→ 于是 list_map(double, 1..6) 这种教科书写法自然成立。每个特性单独看都很小,组合起来语言就"像样"了。
  • 5.10 自举深化:用 Lom 写的迷你解释器又长本事了——源语言支持 while 循环了。更有意思的是它的执行器核心被换成了 list_fold:5.9 刚给语言加的高阶函数,转头就被用在了自举代码里。这就是狗食法的正循环——语言每强一点,自举代码就简洁一点,而写自举代码时发现的不便,又是下一个语言特性的需求来源。
  • 5.11 自举函数:迷你解释器支持 fn 定义和调用函数了,而且是词法作用域(函数看不到调用者的局部变量)——是的,就是 2.4 节讲的那个词法作用域,现在轮到我们在 Lom 里为它实现一遍。开发中踩了一个很有教育意义的坑:迷你语言没有 == 运算符,lexer 把 = 静默丢掉,导致 n == 1 变成两个无关表达式,程序无限递归把栈撑爆——"输入被静默吞掉"永远是调试噩梦,这也是为什么 Lom 主语言选择显式报错。
  • 5.12 自举值系统:迷你语言里的"值"从只有整数,升级为整数/字符串/布尔三件套——这下 "hello, " + name、3 > 2 打印 true 都能跑了。最好的一步棋是顺手把上一节的坑填了:= 和 == 从"静默丢弃"变成了正经 token——犯错不可怕,可怕的是犯过的错没有变成结构性的修复。
  • 5.13 自举诊断层:迷你解释器从"出错装没事(静默返回 0)"升级到"明确告诉你错哪了"(未定义变量、参数个数不对、类型错误、除以零)。实现上就是把 Lom 自己的招牌设计——Result + ? 错误传播——在 Lom 里用了一遍:每个求值函数不再直接返回答案,而是返回"要么答案要么错误信息",? 负责一路把错误传出去。写自己的语言实现自己语言的核心特性,这种感觉就叫自举的浪漫。
  • 5.14 递归值类型:值里可以套值了——[[1, 2], [3]] 这样的嵌套列表能创建、能打印、能比较、能按 xs[0][1] 取值。实现上靠的是递归枚举:Val 的定义里引用 Val 自己。至此这个迷你语言有了像样的数据基础,离"能写正经程序"又近一步。
  • 5.15 容错解析:迷你语言也学会了主语言的看家本领——代码写错了不崩溃,把错误变成一个特殊的 AST 节点,等执行到那里再正经报错。于是 @ 这种乱码字符、写了一半的 1 +、甚至空文件,都能得到一句人话诊断而不是程序崩溃。顺带记录一个编写过程中的真实事故:补 end 的时候把不需要 end 的分支也补了——犯错→定位→理解规则差异→修复,这个过程本身就是最好的学习。
  • 5.16 内建函数:迷你语言有了不用定义就能用的工具箱——split 拆字符串、contains 查包含、trim 去空白、push 往列表尾加元素。机制上是一张"内建名单":调用先查名单,不在才去用户定义的函数里找。和主语言的 stdlib 白名单是同一个思路,只是规模迷你。
  • 5.17 诊断带行号:错误消息从"出错了"升级到"第 4 行出错了"。做法和主语言一模一样:lexer 切 token 时把行号烙上去(包成一条小记录),parser 出错时读出来写进消息。到这一步,迷你语言的报错和主语言的报错已经长得差不多了——阶段、消息、位置三要素齐全。
  • 5.18 性能摸底:给语言做了一次体检,用真实数据说话。两个发现:① 列表的"取尾部"操作每次都整表复制,导致自举式的环境查找慢得离谱(n=800 要 87 秒)——所以下一步该修的是列表的内部表示,而不是别的;② 递归到 10 万层会把 256MB 的大栈都撑爆——树遍历解释器的天花板就在这。体检的意义:不靠猜,靠数据决定下一步修什么。
  • 5.19 列表换心手术(v0.5.0):把列表的内部表示从"数组"换成"链条"(cons 单元)——取头、取尾、头插都变成 O(1),不再整表复制。效果:刚才要 87 秒的基准现在 1.9 秒(快 46 倍)。这是数据驱动决策的完整闭环:5.18 测量定位瓶颈 → 5.19 换表示 → 同基准复测验证。列表从此成为真正可用的函数式数据结构。
  • 5.20 map 模块(v0.5.1):语言有了"字典"——按名字存东西、按名字秒查,不用像列表那样从头翻到尾。同样是查 2000 条数据查 2000 次,列表要 18 秒,字典只要 55 毫秒(快 330 倍),而且数据量翻倍时间几乎不涨。设计上有个讲究:列表是"不可变"的(改一下就产生一份新列表,旧的还在),字典是"可共享修改"的(两个名字指向同一个字典,一处改处处见)——因为字典在实践里就是当"共享的记事本"用的,想要不可变的结构化数据应该用记录(record)。
  • 5.21 自举换字典(v0.5.1):新工具立刻自己先用上——自举解释器的"变量环境"(记录每个变量当前值的本子)从列表换成字典。原来解释器每读一个变量都要把本子从头翻到尾,现在直接按名翻到那一页。效果立竿见影:压测程序跑 400 轮,旧版 2.4 秒、新版 0.29 秒(快 8.3 倍);而且旧版规模翻倍时间要乘 2.9(越涨越快),新版只乘 1.3(基本平)。代码还变简单了:原来每执行一条语句都要"返回一个新本子",现在改同一本就行,签名里的环境往返全部删掉。
  • 5.22 自举长出"编译期检查":迷你语言的流水线从"解析 → 执行"两段变成"解析 → 检查 → 执行"三段,和主语言架构对齐。检查阶段在运行前就把"变量没定义""函数参数个数不对"这类错误揪出来(打上 check error: 前缀),检查不过关就不执行。这就像交卷前先把"姓名写没写"查一遍,而不是等阅卷老师发现。至此,迷你语言已经有了真编译器的完整骨架:词法 → 语法 → 检查 → 求值,四段齐全。
  • 5.23 自举收尾:函数表也从列表换成字典——查函数和查变量一样秒查,自举解释器里所有"按名字找东西"的操作全部 O(1)。迷你语言还补齐了 < <= >= != 四个比较符,写起程序来更像一门真语言了。
  • 5.24 一个"不做"的决定:语言规范里一直挂着个悬案——要不要单独的"字符"类型?结论:不做,一个字符的字符串就是字符(和 Python 一样)。理由很务实:LLM 最熟的 Python 就没有;Rust 里 'a' 和 "a" 的区别恰恰是让 AI 频繁写错的地方;而且实测证明性能瓶颈从来不在字符上。有时候最好的设计决策就是想清楚之后决定不做。
通俗解读

Phase 5 的玩法像"让刚学会做饭的人给自己做一顿饭"——不是为了吃饱,是为了证明厨艺真的学会了。用 Lom 写 Lom 解释器的过程中,每发现一个"写不了"的地方,就是语言的一个真实缺口;补掉它(5.1 元组解构、5.3 for 遍历 List 都是这样来的),语言就长大一点。

这叫狗食法(dogfooding):自己用自己的产品,需求全来自真实踩坑,而不是坐在屋里想。5.3 的修法本身很简单——for 循环原来只认两种可迭代的东西(字符串、整数),现在多认一种(列表),像检票口原来只认身份证和护照,现在加认学生证。

2.11 工程化:版本、CI、治理(Phase 6,已闭环)

Phase 6 之后语言本身不再长新特性,长的是"让项目能被长期维护"的机制——从玩具到工程的分水岭。六个里程碑:

  • 6.1 语义版本:Cargo.toml 成为版本单一事实源,lom --version 从 CARGO_PKG_VERSION 宏读取;语言/工具链变更升 minor、修复升 patch;首个 tag v0.5.1;
  • 6.2 治理三件套:CONTRIBUTING / CODE_OF_CONDUCT / RFC 流程——RFC 模板里有"LLM 影响分析"必填节(连治理文档都为 AI 协作设计);RFC 编号从 0001 起,0000 是模板;

通俗解读

Phase 6 像小店办营业执照:菜品(语言)没变,但有了发票(语义版本)、卫生公示(CI)、员工手册(治理文档)。CI 的意义是"每道菜出锅前过同一套检查",而且是三个后厨(Linux/macOS/Windows)各过一遍——历史上 Windows 的换行符(CRLF)真把"逐字比对"坑过,跨平台门禁不是仪式。

"golden 逐字比对"值得单独说:早期防线只查"输出行数对不对"——39 行变 39 行但内容错乱,行数检查毫无感觉。升级成逐字 diff 后,错一个字符都过不了 CI。门禁的强度必须对齐它声称防御的风险,这是 CI 设计最容易被糊弄的一环。

2.12 WASM 后端(Phase 7,已闭环,v0.15.0)

WASM(WebAssembly):一种可移植的字节码格式——把程序编译成 WASM 二进制后,任何带 WASM 虚拟机的环境(浏览器、node)都能执行。它像"通用机器码":一次编译,处处运行,且执行速度接近原生。

Phase 7 把"同一棵 AST、两种载体"变成现实:lom build <file> --target wasm 输出真正的 WASM 二进制,由 node 执行。两个文件分工:

  • wasm.rs(574 行,二进制 emitter):LEB128 变长编码、section 拼装、模块/导入/导出/数据段的容器层——按 WebAssembly 二进制格式规范逐字节手写,零依赖(wabt/walrus/binaryen 全拒);
  • wasm_codegen.rs(4859 行,AST→WASM 编译器):全项目最大文件。编译的是动态语义(与树遍历解释器逐字对齐),不是静态类型特化——因为 Lom 是渐进式类型,类型信息不可靠,tag 分派必须在运行时做。

核心机制一:tagged i64 值表示

所有 Lom 值编译成一个 i64,低 4 位是 tag:0=Int、1=Bool、2=Unit、3=F64 盒(堆指针)、4=Str、5=Closure、6=Enum、7=Tuple、8=Record、9=List(cons)、10=Map。Int 是 v<<4;堆对象(Float/Str/Record……)走 bump allocator(arena 不释放——目标负载是短生命周期 CLI,见 RFC-0002 的取舍记录)。

两个深坑,都有方法论价值:① tag 掩码耗尽(7.6)——7.2 设计的是低 3 位 tag(掩码 7),7.6 加 tag 8/9 后 8 & 7 == 0,Record 被当成 Int,值表示全局迁 4 位。教训:tag 空间要预留扩展位,掩码值必须单一事实源。② opcode 表连串看错(7.4)——i32.and/or 因漏排 div/rem 整体错位,症状极具迷惑性:trim/upper 静默变成恒等函数——字节全对、验证全过、结果全错,靠"抠 helper 字节离线单测"才定位。教训:查表要看块的成对排列,调试要构造最小隔离。

核心机制二:helper 运行时

60+ 个手写 WASM helper 函数(7.2 交付 19 个,7.4-7.6 随 stdlib/复合值持续扩充;如 rt_add / rt_eq / rt_print / rt_map_probe……)承担全部运行时 tag 分派,codegen 只做"结构翻译 + call helper"——每个二元运算不内联展开一坨分派逻辑,编译器输出可读、可调试。闭包走 call_indirect(funcref 表);Map 是手写开放寻址哈希表(FNV-1a 哈希、线性探测、墓碑删除、负载 0.5 翻倍 rehash)——零依赖到连哈希表都自己写。

与解释器的 4 处已知语义差异(如实记录在 wasm_codegen.rs 文件头与 SPEC_FOR_AI §11f;被问"双后端完全一致吗"照此答):

  1. 除零/取模零:WASM 是 trap(harness 退出码 1),消息文本与解释器不同;
  2. trim:WASM 侧只去 ASCII 空白,解释器是 Unicode 空白;
  3. JSON 数字:经宿主中介后 Int/Float 由 JS 值决定,解释器按源语法判定;
  4. 闭包捕获:WASM 是创建时值拷贝,解释器是 Rc 共享作用域——创建后修改被捕获变量,两后端行为不同(该模式实践中罕见,如需共享语义提 issue)。
通俗解读

tagged i64 是"一物两用"的快递单号:一个 64 位数字,前 60 位装货,后 4 位是货物类型贴纸。收到 17 这个数,看贴纸(低 4 位=1)知道它是"真"这个布尔值,不是整数 17。所有运算前先撕贴纸看类型——这就是"动态语义"的运行时代价,也是 49 倍提速的来源之一:撕贴纸是几条机器指令,而解释器做同样的事要走一整层 Rust 的 match 分发和递归调用。

对 4 处差异的正确心态:工程上没有"逐字一致"的免费午餐,诚实记录差异 + CI 强制 108 任务逐字一致,比嘴上说"完全一样"可信得多。闭包那条最有画面感:解释器闭包拿着出生房间的钥匙(Rc 共享),WASM 闭包只带走了出生时房间里的东西清单副本(值拷贝)——房间后来换了家具,前者看得见,后者不知道。

第三部分:为什么这样设计(论证线)

如果面试官问"这个项目和随便一个玩具解释器有什么区别",你要能打出 DESIGN_RATIONALE.md 这套牌:每个语法决策都在回答"这能不能降低 LLM 的错误率或帮助恢复"。

决策拒绝的方案LLM 视角的理由
end 关键字闭块{}、缩进LLM 数不对 };缩进错一格静默改语义;end 是单词,生成更可靠
类型后置 + 推断优先C 式前置强制注解let x: Int = 3 符合 LLM 叙述顺序;局部变量免注解减负担
Result + match + ?try/catch最重要的决策:异常是隐性控制流,LLM 常忘 catch;Result 是数据,match 穷尽性强制处理错误分支;类型错误还能指导修复
管道 |>嵌套调用 g(f(x))LLM 从左到右生成,g(f(x)) 逼着它先写外层——逆生成顺序
显式导入无通配符import *通配符让 LLM 没有可用符号清单 → 编造符号(幻觉);显式导入缺失时错误信息直接是修复指令
结构类型类/名义类型LLM 只记形状 {x: Int, y: Int},不用追踪类名和继承体系
默认不可变全部可变LLM 追踪长函数里的状态变化很吃力,let mut 是显式信号
JSON 结构化诊断纯文本报错项目身份特性:稳定错误码可学习、retry 指导迭代、容错解析支持部分反馈
Result / Option:来自 Rust 的错误处理方案。函数可能失败时,不抛异常,而是返回 Result<成功值, 错误值>(Ok 或 Err);可能没值时返回 Option(Some 或 None)。错误变成了"数据",必须显式处理。? 运算符是"是 Ok 就解包继续,是 Err 就直接从我的函数返回"的简写。
try/catch 异常:Java/Python 的错误机制——出错时"抛出"一个异常,沿调用栈飞上去,被某层 catch 接住。问题:飞去哪一层不可见(non-local),LLM 经常忘记写 catch,错误就被静默吞掉了。

还有一组"不做"同样能讲:不做缩进敏感、不做异常、不做通配导入、不做宏/元编程(生成的代码不可见,LLM 没法验证)、Phase 0-3 不做 tensor/GPU(不跟 Mojo 硬碰)。

通俗解读

把整张决策表往回收一句话:每个决策都在消除一类"LLM 常犯的具体错误"。LLM 数不对括号 → 用 end;LLM 缩进手滑 → 缩进不算语法;LLM 忘写 return → 尾表达式;LLM 忘 catch → 没有异常可忘;LLM 编造不存在的函数 → 必须显式列清单;LLM 嵌套顺序写反 → 管道顺着生成顺序写。

所以"AI 原生"在这门语言里不是宣传词,而是一张"错误清单 → 设计对策"的对照表。面试时如果被质疑"不就是 Rust 语法改改吗",这张对照表就是最硬的回应:改的每一处都对应 LLM 的一种实测失败模式,而不是为了不同而不同。

Q:解释一下整个项目的架构?

画 1.2 那张管道图:lexer→parser→AST,然后三个消费者(解释器/类型检查器/AI 工具链)。强调"一份 AST 多消费者"和"每个 JSON schema 带版本号"。

Q:闭包怎么实现的?

Rc<RefCell> 作用域链 + 创建时存定义处环境的 Rc + 调用时以捕获环境为父。追问泄漏:Rc 环 + Weak 解法 + 本项目取舍(见 2.4)。

Q:容错解析怎么做的?

lexer 层回退丢字节 + parser 三级同步点恢复 + Stmt::Hole + 全量错误收集 + ensure_progress 防死循环。动机:LLM 一轮修全部错。

Q:|> 管道是语法糖吗?

准确说法:parser 保留 Pipe 节点,求值时去糖为普通调用,把左值插到参数列表最前。

Q:类型系统是静态还是动态的?

渐进式:默认运行路径也检查(诊断走 stderr、永不拦截执行,2026-08-22 整改后如此,别再答"默认不查");--check/--json 只检查不执行;类型错误只警告,名称错误才是 Error;推断不出放行。为什么:检查器能力有限,报 Error 会误伤;且类型错误的受众是 AI 修复工具,不是编译闸门。

Q:效应系统是什么?

函数签名声明副作用(! [IO, Clock]),调用方效应集必须是被调方超集,违例报警告;main 豁免;闭包继承;纯静态零运行时开销。类比:给函数标注"我会碰 IO",让工具链能追踪副作用边界。

Q:凭什么说 99% 通过率证明 AI 原生?

这题要答得有分寸:100 题评测集(10 类),error_repair 15/15、0 语法错误、0 导入缺失——证明语法设计不踩 LLM 常见坑。但要主动承认局限:单一模型单次采样、评测集自建无基线对照(Python/Rust 同题对比还没做)。DESIGN_RATIONALE §12 自己就写了"只有对照实验才能坐实 AI-native 主张"——你能主动说出这个局限,比背 99% 数字更加分。

Q:为什么做 WASM 后端?不是说性能不是目标吗?
