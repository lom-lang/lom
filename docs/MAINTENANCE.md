## §1 角色与铁律

### 1.1 三角色

- **用户**：唯一方向与裁决者——批次方向、复审发起、批次内裁决点、规则变更
  （§6 清单）、对外发布逐项批准。规划者只呈菜单与建议。
- **规划者（主会话）**：读档与关键决策消化、批次设计与裁决点、自包含任务书
  拆解与派发、验收（含亲自复跑）、git 提交/推送/tag 独占、CI/tag 门禁、
  交接五件套刷新、治理动作（审查报告落盘、规则更新）亲自执行。
- **执行者（子智能体）**：读码供料、实施代码与用例、跑单项验证、探针复现、
  基线全量回归执行。并行同时不超过 2 个（规划者控制节奏）。

### 1.2 铁律（十条，规范源在此；HANDOFF_PROMPT 代码块为携带式镜像）

1. **中文与并行纪律**：全程中文交流与注释；执行者并行 ≤2（**体系内独立
   审查的审查者编成除外**——§4.5，2026-10-19 用户裁决）；git 写操作
   （add/commit/push/tag/stash/checkout 等）只由规划者执行。
2. **彻底优先于效率**：改码前先读码（读码供料可派执行者，关键路径规划者
   仍须亲自理解）；计算结果必须真实可复现，推测明确标"主观推测"；
   参考数据用官方/权威源，"校准"一词只用于基于真实数据的场合。
3. **里程碑即提交推送**：提交前跑 HANDOVER §2.2 全量回归（单项可派执行者，
   规划者汇总并**亲自复核 verify_selfcomp 与 doc_audit 两项**）；推送后必看
   CI 首跑；tag 只在 CI 全绿后切；**行为改动与文档成对交付**。
4. **落盘纪律**：任何含反斜杠转义的内容一律用 Write/Edit/apply_patch 落盘，
   禁用 heredoc/printf 直写——执行者同样遵守，任务书中明示。
5. **语言面 v1.0 冻结**（SPEC §14）：语法、20 关键字、诊断码、43 内建的
   变化必须新 RFC；warning 级新检查虽是安全区，也必须用户裁决。
6. **发布线已解冻但解冻≠免呈报**（2026-10-04 用户裁决）：每个对外动作
   （README 门面、Release、宣传帖、外部目录提交、对外发声）先呈方案获
   用户批准再执行。
7. **调研纪律**：不安装竞品（文档级深读）；关键数字必须打开原始来源核对，
   不转述搜索摘要。
8. **数字落盘门禁**：新文档含数字落盘前先跑 `python tools/doc_audit.py`；
   改既有登记措辞前先查 tools/doc_audit.py 与 tools/claims.json 锚点
   （锚句式是措辞级契约——#235 CI 红事故教训）。
9. **方向裁决只由用户做出**：下一批次、复审发起、任何裁决点——规划者呈
   菜单与建议，不越权动工。
10. **诚实与可检索**：失败如实报告（命令+输出+退出码），不以"应该可以"
    收尾；写"将在 X 实现"的句子必须带可检索标记（R15 教训）；宣称
    "全数抓出"前先全仓 grep 全部出现面（R31/R43/R48 教训——gate 覆盖面
    ≠ 全部出现面）；评审/执行者结论逐条复核后再采信。

### 1.3 协作偏好（原 HANDOVER §0 收编，违者引发用户不满）

顺序工作不堆并行；代码逐行检查后提交、文档逐节核对；每个里程碑完成即
提交并推送（"先推送再继续"）；回复跟随用户语言。

### 1.4 裁决分级表（2026-10-22 用户批准，头脑风暴 F2 入册——给呈批装减压阀）

分级只分层"哪些动作需要**事前呈批**"，不让渡方向权与终裁权（§1.1 不动）；
判据 = 批的可机械判断属性（触不触对外面/src//语言面/宣称面），不用
"小事/大事"模糊语。**执行中发现超出预授权面 = 立即停止转 L0 呈批**；
本表自身的任何修改 = L0（改减压阀须阀主同意）。

**L0 · 永远人工（不可预授权）**：对外面全体（铁律 6）；语言面/冻结面
（SPEC §14）与新 RFC 发起；**触 src/ 的任何改动**（含纯注释——R135 先例）；
语义选边与行为修复方案；评测集/任务集扩容（宣称面变化）；新批次方向与
新方向裁决；独立审查发起；外部观察/头脑风暴启动（触发 = 用户指令）；
规则变更（§6 清单全体）；升版批与 tag 切换；费用、账号/身份/凭据、
对外承诺。

**L1 · 预授权-报备型**（规划者自主执行 + 报备痕迹 + 用户可否决；否决 =
指示规划者回滚或修正）。每笔 L1 批义务：commit message 首行带 `[F2-L1]`
标记并引用条款号；TODO 状态块落一行报备记录；门禁照常（doc_audit/
link_check/CI 首跑）；超范围即停转 L0：

1. **tag/CI 门禁回填批**——已推送提交的 run 号、tag sha 回填既有登记位
   （git log 与 Actions API 实查为准，零新增宣称）。
2. **doc_audit FAIL 指引的机械锚同步**——已知新值刷现值（数字来源 =
   已裁决交付批），不含锚句式重构与新增宣称（§2.3 SOP 第 3 步的自然
   执行）。
3. **观察项现值刷新**——外部观察/定期实查后的登记值更新，随在途批顺带
   或独立小批。
4. **纯指针化替换**——R159/R160 先例的复写数字改指针引 HANDOVER §2.2
   单一源（doc_audit 全过 + 零新增宣称）。
5. **镜像中途同步**——§5.4"里程碑批收官即同步"的非交接批时点独立小批
   （主写位内容以既有裁决为源）。

**L1 归类与补登细则（R199/R200，三十八审整改批 2 成文，用户裁决"按建议
执行"）**：① **报备行可后补但必须补齐**——缺位一经发现（含审查开账），
随下一批补回溯报备行并标注补登时点；不得以 commit message 段落替代 TODO
状态块报备（报备位置不可偷换——f43ed83/f734303/692c28d 三笔缺位实录，
2026-10-27 补登）。② **实施批验收环节产生的宣称数字修正归实施批收尾
面**——属该实施批用户裁决授权范围，不构成 L1 批的超范围（f43ed83 的
A/B 终判措辞修正按此定性：内容有 designs/0026 验收环节授权源；其"L1 批
中未停批"的程序偏差如实登记，以本成文根治——不得把"如实披露"当作免停
依据，披露义务与停止义务是两条）；L1 批中发现**与该批无关**的宣称修正
仍须立即停止转 L0 呈批。

**L2 · 免报备（仅一处）**：target/probes/（gitignored）内部整理（探针、
报告、INDEX、decisions 档）——不触仓库跟踪面，无授权需求，列此完备。

与既有规则关系：铁律 3（里程碑即提交推送）/铁律 6/铁律 9 与 §3.2 验收
细则对 L1 批完全适用不变；R172 同包收口留痕由报备行满足。

## §2 工作项循环

### 2.1 步骤（每个语义改动按序执行）

1. **改前读码**；疑似 bug 先写探针复现（能复现才叫 bug，复现形态记入
   TODO 证据区）。
2. **批次动工前置**：涉值表示扩展、发射层结构变化、宿主工具面或语义选边
   的批次，必须先产出设计方案（docs/designs/NNNN）并呈裁决点，用户裁决后
   动工（0001 起惯例，此处成文）。纯文档批与已裁路线的后续小批可免。
3. **实施**：规划者拆自包含任务书（§3.1）派执行者；规划者中途抽查关键结论。
4. **验收**：按 §3.2 细则 + HANDOVER §2.2 全量回归；实施类加存量 hex 对比
   与 fmt gate。
5. **文档成对**：按牵动面同步 SPEC_FOR_AI / LANGUAGE_SPEC（§13 changelog）/
   SECURITY / README / positioning / RFC 修订记录 / designs 状态行 / TODO
   交付段——改了"宣称"就改文档，改不了宣称就改回实现。
6. **数字锚同步**：按 §2.3 SOP。
7. **升版与门禁**：按 §2.2 决策表升版（Cargo.toml/lock 同步）→ 提交推送 →
   看 CI 首跑（含 doc gates job）→ 绿后切 tag，tag 信息与 SPEC §13 对齐。
8. **三实现一致律**：宿主 parser/诊断/内建行为改动 → 默认怀疑 WASM 与
   自举（self_interp.lom）同款偏差，两侧同步修并各有测试；selfhost 六模式
   逐个全跑（--wasm 慢也要跑——R57 三连红教训）。

### 2.2 升版决策表

| 改动性质 | 处置 |
|---|---|
| 语言面变化（语法/20 关键字/诊断码/43 内建） | 新 RFC + minor |
| 用户可见新功能（CLI 子命令/工具/评测面扩容） | minor |
| 用户可见支持状态/宣称面翻转（experimental→supported 等） | minor（v1.8.0 L2 转正先例，R161 回写） |
| 行为修复、诊断文案修正 | patch |
| 触 src/ 任何改动（含纯注释） | 按行为修复升 patch（R135 先例：v1.9.3/v1.10.1，R161 回写） |
| 纯文档批、治理批 | 不升版 |
| 纯新增独立工具（不触 src/、不改任何既有命令行为） | 可登记"纯工具批"不升版（l2fix 先例；一旦触 src/ 或行为变化即按上表升） |

### 2.3 数字锚同步 SOP（根治多写位漂移——R93/R98/R103/R106/R111/R113 六笔同族）

1. 数字变化的源头是交付批（测试数/行数/版本/quine 字节/任务数等）。
2. **唯一主写位 = TODO 顶部状态块**——先改它。
3. 跑 `python tools/doc_audit.py`，按逐项 FAIL 报告修正其余文档位——
   **工具即清单**，禁止凭记忆找位补改。
4. 大段重写任何治理文档后，提交前必跑 doc_audit 终检（锚句式是措辞级
   契约，CI #235 红事故实录）。
4b. **升版批必含 J 锚现值**（R123，二十九审）：README Current release
    段升版时必含 quine 现值（`quine **N**`）——否则 J 锚模式挂回上一版
    Previous 段（三版同值时绿灯巧合，quine 变化即楔死）。doc_audit 若
    PASS 而锚位在 Previous 段 = 漏检面，升版验收时人工核一眼锚在
    Current 段。
5. 新增合计类宣称 → tools/claims.json 登记（分项附证据指针，合计由回加
   得出，不手写——R22 教训）。
6. **写位准入（R164 成文，2026-10-19 用户裁决）**：新增长期文档复写基线
   数字（版本号 / 测试计数 / quine 字节等高 churn 值）须呈批，默认指针化
   ——数字一律引 [HANDOVER §2.2](HANDOVER.md) 单一源；doc_audit 锚扩张
   仅留给高 churn 数字位（指针化先例：AGENTS.md R160 / README.zh-CN
   R159——只刷现值已被证撑不过两个版本周期）。

## §3 执行者派发与验收

### 3.1 任务书规范

任务书 = **执行者先读 [docs/EXECUTOR_TEMPLATE.md](EXECUTOR_TEMPLATE.md)
全部**（通用铁律摘要、输出格式硬性规范、冻结面、按触发面的坑索引——模板
在仓库内，自包含由此成立且零重复手写）+ **批次段**（背景与目标、仓库相关
文件、验收标准含期望值、边界与禁止事项、产出物形态＝改动文件清单 + 验证
输出原文）。任务书内仍需明示铁律 1/4 两条（git 禁令与落盘纪律）。

### 3.2 验收细则（规划者侧）

- 执行者回报必须满足模板输出格式（逐项"命令/关键输出/退出码"）。
- **计数与配对类数据逐项行式复核**：执行者输出 `名称 = 值` 行式数据；
  target×计数等**配对数据必须逐项单独执行获得**（例：逐个 `--test` 跑），
  禁止从合并输出推断配对——2026-10-06 基线回报曾把同一组数字错误配对到
  target 名（总数对、配对全错），规划者逐项复跑方纠。
- **规划者必亲自重跑**：verify_selfcomp 与 doc_audit 两项（铁律 3）；
  实施类任务加存量 hex 对比与 fmt gate；计数类结论抽查 ≥2 项复跑。
- **"看起来对"禁例**：转述计数不复核、散文式"全部通过"无逐项输出、
  失败项缺失——一律视为未完成，退回重报。

### 3.3 执行者偏差史（防复发登记）

| 偏差 | 时点 | 根治位 |
|---|---|---|
| git stash 擅用（核 fmt 预存性时） | v1.6.1 批 | 任务书明示 git 全禁（模板冻结面） |
| clippy --all-targets 存量 lint 误判为"9 错"（CI 口径实为零输出） | v1.3.2 批 | 模板坑索引"改宿主 Rust"条目 |
| 计数配对转述错乱（总数对、名字-数字全错） | 2026-10-06 基线回归 | §3.2 配对数据逐项单独执行 |
| 执行者使用限额中断 | json 批 | 规划者盘点遗留亲自兜底（修订 22 先例） |

## §4 审查与常设机制（2026-10-21 起：审查 + 外部观察 + 头脑风暴三常设机制并列）

### 4.1 发起与性质

时机：每个大包/维护周期收官后，**用户裁决发起**。性质：体系内 agent 分工
的独立敌手审查，**不是外部同行审计**——报告必须如实标注该边界。审查阶段
不改产品源码；git 严格只读；cargo 串行；探针只落 target/probes/（gitignored）；
只开账不修码。

### 4.2 报告框架（八节，reviews/review-<date>[-N].html 自包含 HTML）

① 报告头（基线 HEAD、增量提交清单、审查执行者）② 审查边界声明 ③ verdict
评级框 + 一行式总评 ④ 审查方法 ⑤ 基线矩阵（全部亲手跑，含 CI GitHub API
实查、tag 指向实核、逐 target 计数）⑥ 增量批次核心宣称逐批复核（敌手化）
⑦ 敌手探针表（编号/方向/实测/结论 + 击穿判定）⑧ 文档对账数字链 + 开账 +
评级依据（+ 附录探针目录）。审查任务书 = EXECUTOR_TEMPLATE + 本节框架 +
覆盖范围与上轮整改验收探针复跑要求。

**档案落位（R170/R171/R173 成文，2026-10-19）**：① 审查任务书随审落
`target/probes/<review-N>/task.md`（gitignored，本地可审计），报告附录
登记其路径；② 重大裁决（§6 类与方向裁决）的呈报菜单原文落
`target/probes/decisions/<date>-<topic>.md`（gitignored），TODO 裁决段
注路径——呈报充分性自此可事后审计；**呈批档随附"裁决侧摘录"节**（R215，
三十八审成文：用户回复原话或可获得的最近似原话 + 日期 + 采集方式标注；
存量不追溯——登记位互证不构成"逐字忠实"的证明，档案义务在规划者侧）；③ 报告头增**执行者耗时行**（取自
subagent usage 数据）——审查工时自此有台账。

### 4.3 开账纪律

新发现从 **TODO 顶部状态块登记的顺延号**起（本文件不写时点编号）；每账
必带可复现形态（探针/命令）与候选处置；整改项必须配"应修"+"绝不能这样修"
负向测试锁定；开账后整改顺序由用户裁决；审查报告原文一经落盘不回写（事后
勘误以追加框登记，历史评级不重评）。**开账同批收口（随批整改）须在 TODO
记一句用户裁决痕迹**（原话或"随 X 批裁决"）——同包收口不得无裁决记载
（R172，2026-10-19 成文）。

### 4.4 评级规则

每轮独立评级，历史评级不得外推；整改后状态只能由下一轮复审重估。P1/P2
在场不入 A 档（十四审惯例）；P3 文档精度不挡 A-（R102/R111/R113 先例）。
**档位速判（R174 成文，2026-10-19——与 37 轮轨迹核验一致）**：B = P1
在场；B+ = P2 在场且无 P1；A 系 = P1/P2 零在场（P3 密度与机制性再分
A-/A）。

### 4.5 审查执行模式（2026-10-19 用户裁决："以后的独立审查也遵循这个模式"——三十七审模式标准化）

- **双层覆盖**：产品面（增量宣称敌手复核 + 基线矩阵 + 敌手探针）必审；
  元层面（维护进程 / 文档规则体系 / 规划者-执行者模式 / 审查体系自身 /
  规划者呈报质量 / 对外面）按事件性质选维度——编成与维度划分随审查
  任务书呈用户裁定。
- **多执行者并行**：审查者编成豁免铁律 1 的 ≤2 限制（按规模 3-5 个并行；
  cargo 独占分配给产品面执行者，元面执行者用 python 纯工具与只读 lom.exe）。
- **两级红线**（任务书置顶 + 执行者开工前复述义务）：一级（绝对）零对外
  交互——任何 push、任何写语义网络请求、任何外部平台动作；联网仅限
  只读 GET。二级——本地 git 严格只读、仓库既有文件零修改、探针与章节
  片段只落 target/probes/<review-N>/、构造性验证限"未跟踪临时文件→验证
  →即删→终态 git status 干净披露"形态。
- **自指缓解**：元面问题清单由执行者自主拟定（规划者不提供，避免被审
  方引导）；报告章节机械拼接（规划者零内容编辑权，仅写报告头/边界声明/
  附录）；报告头必含自指披露段（审查者由被审规划者派出，独立性以此为
  上限）。**元面维度段限"维度名 + 一句边界"**（R214，三十八审成文）——
  检索线索（提交号/路径/预期值/裁决原话例句）不得写入任务书正文，可另附
  "事实索引附录"供执行者取用：预期值前置会使执行者拟题空间被预先收敛
  （三十七审任务书极简括注 vs 三十八审子检项化对照实录）；不得反向要求
  规划者预审执行者拟题清单（自指缓解倒退为前置审批）。
- **产出形态**：双 verdict 分列（产品面 + 元面各自评级，不混评）；开账
  号段预分配（空号如实登记）；审查任务书 / 菜单原文 / 执行者耗时行按
  §4.2 档案落位段执行。
- 首例：三十七审（review-2026-10-19.html，2026-10-19）。

### 4.6 外部观察（常设机制；2026-10-21 用户批准，与独立审查并列）

- **触发**：唯一触发 = 用户指令（"启动外部观察"，可带当次重点变体）；规划者不主动发起、不设日程。用户可附带当次特殊要求（新增观察对象、特定问题、深度要求）。
- **编成**：单执行者（观察执行者）；任务书 = 本协议通用模板 + 当次特殊性，每次随报告同目录存档（task.md + report.md——对齐 §4.2 档案落位制度）。
- **红线**：与 §4.5 审查同款两级——一级（绝对）零对外交互，联网仅限只读 GET，严禁任何账号语义动作；二级本地 git 严格只读、仓库既有文件零修改、产出只落 target/probes/observations/。
- **默认观察对象集**（当次可增删；基线登记位 = TODO 顶部状态块观察项段，现值不写本文件——**各对象的开闭与收口状态同样以 TODO 观察项段为准，本列表是协议语义的默认集、不是登记位**，R203）：MoonBit release 线 / 目录仓动态（原"目录 PR #68"，已合并收口——后续动态随观察项段）/ Zero（vercel-labs/zerolang）/ Vera（aallan/vera）/ 本仓 CI 最新 run / 当次指定项。
- **产出与回传分级**：观察报告（各对象：实查值 vs 基线登记值、变化标注、来源 URL 与访问时间）落 `target/probes/observations/<日期>/report.md`；INDEX.md 滚动记录（日期/触发原话/摘要/是否触发呈报）。回传两档——纯动向（无事件）：摘要汇报，登记值过期随下个批次顺带刷新（不单独动仓库）；事件（竞品 1.0 正式发布 / PR #68 被处理 / 重大生态变化）：当日呈报 + 建议对应动作，**动作本身仍逐项呈批**。连续观察的基线滚动：每次报告成为下次对照的基线。
- **边界**：观察发现若牵动仓库（登记值批量过期、触发 delta 复核）走正常批次流程，不在观察内修仓库；调研纪律（铁律 7：关键数字开原始来源）全程适用。与独立审查同构不同物：审查 = 对仓库的敌手复核，观察 = 对外部的只读监测——红线、任务书落档、报告存档制度共用。

### 4.7 头脑风暴（常设机制；2026-10-21 用户批准，与独立审查、外部观察并列）

- **触发**：唯一触发 = 用户指令（"头脑风暴"，或带焦点变体"就 X 头脑风暴"）；规划者不主动发起、不设日程。用户可附带当次特殊要求（焦点域、深度、禁区）。
- **编成**：单执行者（头脑风暴执行者）；任务书 = 本协议通用模板 + 当次焦点——**无焦点不开工**（发散产出无对账形态，焦点约束是质量闸）；按规模需并行时呈请用户豁免（铁律 1）。
- **红线**：与 §4.5/§4.6 同款两级——一级（绝对）零对外交互，联网仅限只读 GET；二级本地 git 严格只读、仓库既有文件零修改、产出只落 `target/probes/brainstorm/<日期>/`。
- **结构与质量约束**：分桶组织（桶语义沿用首例：A 等待期配套 / B 评测证据 / C ACRI 生态 / D 语言工具面 / E 对外影响力 / F 维护者治理 / G moonshot——当次可增改并在报告头声明，新主题桶字母从 H 扩展）；每点子必带一句话价值 + 成本量级 + 主要风险；moonshot 单列并附不现实理由（防点子污染）；涉竞品/生态的点子须先只读核对现状（前置事实表，防基于过时事实发散）。
- **梳理环节（2026-10-22 用户裁决设立——"头脑风暴后要梳理；怎么梳理、规则、文档维护方式完全由规划者独立决定"；规划者设计定稿：**收敛漏斗**形态）**：头脑风暴执行者在产出点子后**接着做梳理**（同一任务内不另派）——**初稿全集不是交付形态**。梳理 = 执行者自筛出两层：**提案层**（值得进待裁菜单的点子，软上限 12——一屏可读的量级，超出须有强同族理由）与**沉档层**（其余全部——不删除，留档可追溯，用户将来提起可捞回，编号按维护条款不回收）。**报告必须含全集去向对照表**：初稿每个点子一行（去向 = 提案/沉档 + 一句理由）——这是"梳理确实发生"的唯一可审计形态；去向分类由执行者自主决定（合并同族/压缩标注/直接沉档均可），不设刚性枚举。梳理结果经规划者复核后**呈用户裁决入池**（提案层内容属方向性判断，不预授权）。
- **产出与消化闭环**：报告（report.md）+ 当次任务书（task.md）同目录存档；报告固定结构：§1 焦点与前置事实表 → §2 初稿全集 → §3 梳理（全集去向对照表 + 提案层清单 + 沉档层）；`target/probes/brainstorm/INDEX.md` 滚动记录（日期/触发原话/焦点/编号区间/初稿数→提案数——收敛比可见），每次报告成为档案。提案层经**规划者复核**（外部事实抽查、主观推测标注、复核注随档保留原文零编辑）与**用户裁决**后进 TODO 待裁菜单点子池（**菜单只收提案层，沉档层留档**——菜单保持一屏可读）；**所有点子不构成预授权**（铁律 6）；裁决吸收/覆盖后随批在菜单登记"已吸收出池"。
- **编号维护（2026-10-21 用户裁决点名成文）**：点子编号 = `<桶字母><序号>`；新点子序号在该桶**已用最大号后续接**（续接基线 = TODO 点子池现役号 + 菜单"已吸收出池"登记保留号，INDEX 轮次区间交叉核对）；**已出池/被覆盖的编号不复用不回收**（历史可追溯）；同实质重复点子不重新编号、并入既有编号登记；新一轮入池时 TODO 点子池与 INDEX 双写位同步。
- **边界**：头脑风暴不直接动工（点子→用户裁决→正常批次）；对外接触类点子（推广/联系维护者）执行仍逐项呈批；首例 = 2026-10-20 七桶档（pre-protocol 形态，保留 `target/probes/brainstorm/ideas.md` 原位不动）。
