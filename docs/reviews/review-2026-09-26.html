5. 结论、整改建议及未测面

对账结论：十四审 R79-R82 四项整改宣称本轮全部亲手复核零失真；c2（修订 12）、String 批（修订 14）、List 批（修订 16）的可复核宣称——verify_selfcomp 174/174 的计数与名实、self_comp 7724 行、文档数字锚全仓对账、存量 62 用例 hex 逐字节不变（本轮以 git show 只读导出 v1.2.10 编译器独立对拍 62/62 全等）——均成立。基线 14 项全绿。但 List 批 B2"按闭包签名特化"的宣称被 F1 击穿：fold 的 acc 为 Float/Bool（非 i64 载体）时 COMPILED 产不可实例化 WASM，与 R81 修复时立下的"编译期严格校验不留坏 WASM"承诺同族；F2 则显示 println(Bool) 三层预扫的登记面与实际拒绝面不匹配（防御兜底保证了不产坏 wasm，代价是自然写法被拒）。绿矩阵（174/174 全绿与 F1 并存）再次印证：官方用例的覆盖选择决定门禁可见性——69_list_fold 恰好只选了 i64 载体的 String acc。

整改建议（只开账，次序归用户）：R84（P2）优先于 R85（P3）。R84 修法方向：fold helper 的类型签名按 acc_vt 特化参数与返回位（ls_get 分支 L5552 同款机制），并成对交付"Float acc fold / Bool acc fold 行为对拍"+"非 i64 载体 acc 绝不产可实例化失败的模块"负向锁定；R85 修法方向二选一：预扫补 ExIf/ExMatch/闭包签名识别，或把该拒绝面在 RFC 信任边界明确登记。两项均不触宿主与冻结语言面。

评级理由：B+ —— 对比轨迹锚点（十二审 1×P1+1×P2 → B；十三审 2×P3 → B+；十四审 2×P1+2×P2 → B），本轮 0×P1、1×P2（行为级但实例化即失败、非静默错值）、1×P3，整改四项全部落实且六批交付的核心宣称独立成立；未回升到 A- 是因为 P2 击穿的恰是本批次的头条宣称（特化机制）且属"宣称-实现"落差，与 R81 当时"已知未修"性质不同。本评级只针对本轮时点与检验面；R84/R85 整改后状态只能由下一轮独立复审重估。
