6. 开账（本轮新发现，R107 起）

R107（P1）——两包各自 import 同一别名：解释器/宿主 WASM 取声明序后者、L2 取首个——同程序跨后端静默不同值，全程零诊断

形态：from libr import { origin as g } + from libs import { base2 as g }（两真名不同、别名相同、无本地 fn），调用 g(3)。

证据（b3proj，原文见附录 A）：解释器 6/6 恒 103（g→base2，后写声明赢——import_aliases 同键覆盖，按 item 序确定）；宿主 WASM 恒 103（4 次运行）；L2 恒 4（4 次运行，g→origin，首个注册摘要保留）；三侧全 rc=0、零诊断（PKG007 不发——两包 public_symbols 不相交；NAM006 不发——无本地 fn）。每侧各自确定，但两侧选边相反——与 R105 同为"遮蔽方向分叉"形态，且因零诊断而静默。

根因（读码 + designs/0008 登记）：解释器 process_import 的别名注册按 item 序后写覆盖；L2（self_comp）按 designs/0008 登记的"别名与既有函数重名静默保留既有摘要"——首个赢。该登记句自称"对齐宿主 fn_idx orig 优先级"，但对别名撞别名（既有"函数"是前一别名而非真 fn）宿主实际取后者——登记口径与宿主行为在此子形态相悖（与二十一审 R105 击穿 designs/0008 L150"主文件赢"句同型）。

波及面：任何两包符号经同一别名导入的程序。全库测试构造性规避——pkg_cases 103 只有一个别名、105 为别名链无同名别名、106/107 与 D5 两新探针均不含此形态（D5 解除覆盖只补了撞名两形态，未含别名撞别名）。非本批引入：本增量对 interpreter process_import / wasm_codegen / self_comp 三处零触碰（git diff 250f0ef..92502e2 --stat 实核），eval_call 改动对此形态等价（functions 无 "g" 键，别名路径不变）。SPEC §8.1 v1.4.10 新句枚举了 alias/local、包符号/local、两包同名三种撞名形态并称"Collisions are not errors: …emits NAM006/PKG007"——别名撞别名既无语义定义也无任何诊断，是该句枚举的漏项。

修法建议（供裁决）：入 R104/R105 同族一并裁决——或 SPEC 冻结"后 import 声明赢"（对齐解释器/宿主，L2 改后写覆盖），或统一取首个（解释器/宿主改）；并加 NAM006 变体（"import 别名 'g' 重复"warning）。负向锁定：不能只进 §11f 分歧档案——两侧不同值且无文档语义无诊断，不满足分歧档案"各侧自身确定 + 语义已冻结"的前提（R104 教训同款）；也不能只改 L2 单侧而不冻结 SPEC 选边。

R108（P2）——包 enum 变体在单文件视图报 NAM003 error：--check 对合法包 enum 程序 rc=1 误拒（存量 103 用例本身即中招）

形态：使用包导出 enum 的变体（显式 import 变体名，或 auto-public 直用）。

证据：a3ctl（单包无撞名对照，from libp import { val, Color, Red } + use(Red)）——run 路径 rc0 输出正确但 stderr 带 [type] error: [NAM003] 未定义变量 'Red'；--check rc=1（error 拦截）。存量 pkg_cases/103 本身：run 输出 13/22/2/1/3/31 全对但 stderr 3 条 NAM003 error（Green/Red/Blue），--check rc=1——三侧运行/编译产物全部正确的合法程序被 --check 拒绝。

根因（读码）：typechecker is_variant_constructor 只查 self.enums（本地声明/内建），不查 external_symbols——import 的变体名虽进 externals 放行集，但 Ident 值位检查路径不消费它。fn 的 externals 放行（跳过 NAM003）与变体的不放行不对称。

波及面与定性：既有面（本增量 typechecker diff 不含 check_expr/Ident 路径；collect_import 的 externals 注册逻辑前后逐字等价——diff hunk 实核）；run/build 路径渐进式不拦截（零行为损坏），但 --check 是 LLM 修复环的信号源，合法程序报 3 错会诱导无谓修复（且 NAM003 附带"是否想用 'len'？"噪声 hint）。未在任何审查/信任边界文档登记（v1.4.9 清零的"3 条 NAM003 假阳性"是包内 as 别名 build 路径，不同族）。修法建议：Ident 检查对 ∈ external_symbols 的名放行（与 fn 同构）或 is_variant_constructor 并查 externals；负向锁定：真未定义名仍 NAM003（存量负例不倒）。

R109（P3）——build 合并单元对"正常单包 import"逐符号发 NAM006 噪音，且"遮蔽 libp::X"文案误导（"本地定义"实为合并进来的 X 自身）

证据：pkg_cases/101（mathlib 标准用法）lom build stderr 3 条 NAM006——import 别名 'square' 与本地定义同名——本地定义优先（遮蔽 mathlib::square）×3（square/cube/factorial）；103 用例 1 条（color_code；pf 走别名、Color 是 enum 故不触发）；本轮 c2/c5 各 2/1 条。v1.4.9 同路径 build stderr 干净（r94 批宣称"仅 1 行已编译信息"）——本批引入（合并单元里包 fn 即"本地 item"，任何 import 必与之同名）。run/--check 单文件视图无此形态（干净）。SPEC §8.1 字面覆盖该形态（"or a merged-unit package symbol collides with a local definition"），非宣称失真；但对标准包用法的逐符号 warning 噪音 + "遮蔽 X"文案（实为 X 自身经合并进入）对 LLM 修复环有诱导（可能据 warning 删 import）。建议：合并单元形态下，当"本地定义"与 import 同源（同一包的同一符号）时静默或改文案（如"import 与合并单元内 libp::square 同名——同源合并，无需 import"）；负向锁定：R105 真遮蔽形态（别名 vs 用户本地 fn）的 NAM006 不得随之消失（r104 集成测试已锁 NAM006 在位）。
