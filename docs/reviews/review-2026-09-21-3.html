5. 新发现（R65 起；只开账不修复）

ID级别发现最小复现
R65 P1 MUT001 错目标 + 非幂等重复应用把用户源码改坏成解析错误。诊断行位于闭包体/match 臂/for 绑定等嵌套作用域内、而外层函数扁平作用域存在同名 let 时，fix_mut001_add_mut 按名过滤命中外层声明（唯一命中 → High Replace），改错对象且原诊断不消；下一轮重诊断时已改为 let mut 的声明仍被收集（collect_let_decls 不过滤 mutable 标志），同坐标再次 Replace → let mut mut x → PARSE001。apply --apply 直接改写磁盘文件，用户源码损坏（ok:false 如实报告，但文件已坏）。三种实例化均验证：闭包体、match 臂块、for 变量遮蔽（后者 applied=3，EFF001 合法修 + MUT001 错改 ×2）。证伪 v1.2.3 宣称"闭包内/match 臂内的 MUT001 降级 hint——宁可不自动修，不可错改"（TODO L228 / SPEC_FOR_AI L690"whose declaration lives inside a closure body or match arm degrades to a Medium hint"——该形态下声明恰在闭包/match 臂内，实际却是 High Replace）。
根因（两个独立缺陷叠加）：① 命中过滤不看诊断行的作用域归属——无法区分"闭包内重赋捕获的外层 x"（应 Replace 外层，实测正确）与"闭包内重赋闭包自己的遮蔽 x"（不应动外层）；② 已可变声明仍计入命中集 → 非幂等重应用。二者任一修掉即可阻断损坏链（① 使其正确降级 hint；② 使 round2 零命中转 hint），但只修 ② 仍残留一次错改。

R67 P2 裸 return 编译为非法 wasm（打印 COMPILED）。与 R66 同根因（StReturn 臂的 Err 死值）：return 语句蒸发后函数体为空，非 void 函数产物栈校验失败无法实例化——失败面从编译期推迟到运行期。RFC 修订 2 已登记"尾部裸 return 使函数块值为 Unit"的语言面事实，self_comp 源码也写了拒绝臂但未生效。 
fn f(x: Int) -> Int
    return x + 1
end
fn main() -> Unit
    println(f(1))
end
→ COMPILED 92 bytes；node 实例化 CompileError: expected 1 elements on the stack for fallthru, found 0（host 打 2）。
R68 P2 let 显式注解信任边界未登记且产坏 wasm。let x: Int = 1.5：self_comp 的类型综合直接采信注解（槽位 i64）而值是 f64 → local.set expected i64, found f64 非法 wasm。宿主语义是注解不匹配仅 TYPE001 warning、运行时值胜出（打 1.5）。RFC-0004 修订 3 的"已知边界"清单未登记该信任差异——编译器信任输入的边界失账。 
fn main() -> Unit
    let x: Int = 1.5
    println(x)
end
→ COMPILED 94 bytes；实例化 CompileError（host 打 1.5）。
R69 P2 case1 字节锚陈旧失真。RFC-0004 L150 与 HANDOVER 顶部宣称"case1 宿主产物 9746 字节 vs L2 产物 121 字节"；HEAD 实测 01_arith_int 为 9852 / 169（verify_selfcomp 自身输出即打印 169），五用例（host 9805-9900 / l2 169-254）无一匹配。量级方向（≈9.8KB vs ≈0.17KB）成立，但锚点数字未随用例定稿重测。doc_audit 不覆盖该数字。 python tools/verify_selfcomp.py 首行 PASS 01_arith_int.lom 169 bytes；lom build 01_arith_int.lom --target wasm → 9852 字节。
R70 P3 HANDOVER §2.2 残留陈旧句："cargo fmt --all -- --check 当前为 R61 已知失败，尚不是 CI gate"——R61 已于同日关闭（rustfmt 机械包 5f2930a），fmt 现零 diff。误导下任维护者跳过 fmt 或以为未设门。 读 HANDOVER §2.2 末段 + cargo fmt --all -- --check 实跑退出 0。
R71 P3 LSP 非 UTF-8 payload 静默丢弃：R63 的"畸形 JSON 回错误响应"只覆盖合法 UTF-8 文本；payload 含无效 UTF-8 字节时 from_utf8 失败走 continue，客户端收不到任何 -32700（v1.2.2 行为残留）。服务器存活。 发 CL 正确、payload 含 \xff\xfe 的帧 → 无响应帧；后续 initialize 正常。
R72 P3 LSP 传输边角两枚：① 双 Content-Length 头 last-wins 不拒（实测第二头 5 覆盖第一头，读 5 字节 → -32700，剩余字节按 header 行消化，无永久失步但 LSP 规范建议拒收重复头）；② exit 未经 shutdown 恒 rc=0（LSP 3.17 建议 error code 1）。均为规范柔顺性毛边，非可达性/稳定性问题。 双头帧实测；printf '...method":"exit"}' | lom lsp → rc=0。

6. 对交接裁决的建议（供用户决策，非本审查越权裁定）

  • L2.3 暂缓放行，先收口 R66/R67/R68（一个整改小包）。理由：L2.3 全语言面将把更多构造叠在当前语句级拒绝死臂上，而 R66 的失败模式（可实例化的静默错误 wasm）是差分/运行都探不到的盲区；L2.4 自举闭环会用 self_comp 编译 self_comp 自身，错误行为会被链式固化。整改方向（供参考，只登记不开方）：comp_blk 语句分派的 match 需把各臂 Result 经 ? 线程化（如臂产出 code 字符串、错误显式 return Err），并补子集外负例集到 verify_selfcomp（本轮探针矩阵——if/while/for/return 语句、注解不匹配、Float %、比较、缺 main、未知函数、嵌套 println——可直接复用为回归用例）；R68 在 RFC-0004 已知边界清单补登记并决定语义（建议：注解与综合值类型不一致即 subset_err 拒绝，与"编译器信任输入"的边界一起明示）。R65 修复属 v1.2.4 工具面整改包（见下），不阻塞 L2 也可以并行——但两者都应在 L2.3 前落账。
  • R65 建议入 v1.2.4 整改包（P1）。语言面不动（纯 fix 引擎行为），符合发布线冻结政策下的工具面小版本惯例（v1.2.2/v1.2.3 同型）。修复方向（只登记不开方）：① collect_let_decls/命中过滤补 !mutable（断非幂等链，独立可测）；② 诊断行作用域归属判定——诊断行位于闭包/match 臂/for 绑定的嵌套区域时，若同名命中指向外层声明则降级 hint（对齐"宁可不自动修"）。①②齐修后补三类负向锁定测试（本轮三探针即现成用例）。
  • R69/R70 文档锚修正随整改包顺带：字节锚按实产重测（或改为区间口径并纳入 doc_audit 锚点面）；§2.2 删除 fmt 陈旧句。R71/R72 可挂账入 LSP 边角清单，不阻塞。
  • 发布冻结维持：本轮全部新发现均为工具行为（fix 引擎/LSP 毛边）、实验性 L2 里程碑产物与文档数字，无一触及语言面；v1.2.3 tag 无需撤回（其自列验收宣称真实），R65 以 v1.2.4 收口即可。
  • 流程观察（不计级）：MUT001 定位面三轮递进收敛（全文回扫 → 函数内 → AST 扁平收集），每轮修掉上一形态又留下一形态——建议下轮整改时把"诊断-声明作用域归属解析"作为终态方案评估（与 typechecker 共享一次 Env 解析），而非继续按名过滤的窄化路线；同一模式也适用于 EFF001 等 span 推算类动作。
