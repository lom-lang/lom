二、问题清单（按优先级排序）

P0-1 SECURITY.md「checked arithmetic」声称与实现不符 —— release 下整数算术静默回绕

声称：SECURITY.md:17："*Integer handling: all arithmetic on Lom Int is checked (i64); division by zero is a runtime error, not a trap.*"；README.md:105（Phase 6.6）重复了该条并把整份清单称为 "hardening inventory (grep-verified … checked arithmetic)"。

实现：src/interpreter.rs:1267-1284 的 eval_arith 对 Int 使用裸运算 a + b / a - b / a * b（无任何 checked_*；全库 grep "checked_" 零命中）。只有除零/取模零被拦截（这部分属实）。WASM 后端为 i64 wrap（WebAssembly 标准语义），同样不是"checked"。

实测（release 二进制，2026-09-03）：

$ lom ovf.lom          # println(9223372036854775807 + 1) 等
9223372036854775807
-9223372036854775808    ← MAX + 1 静默回绕，无任何诊断，退出码 0
9223372036854775807     ← (0 - MAX) - 2 回绕
-2                      ← MAX * 2 回绕
[runtime] error: 整数除以零  ← 除零确有 RUNTIME000（此条属实）

为何定 P0：这不是普通的文档滞后，而是安全审计文档中的加固清单条目失实，且 README 把它标为"grep-verified"——恰好该条目无法用 grep 验证，说明 6.6 的验证程序本身有漏洞。项目的立身纪律是"文档不撒谎"（上轮审查引用的 HANDOVER 治理原则），安全文档是其中可信度权重最高的一层。溢出回绕本身在"受信程序"威胁模型下危害有限（定 P0 的依据是宣称失实，不是攻击面）。

修复建议（二选一）：① 改文档——如实记录"Int 算术为 i64 回绕语义（release）／debug 构建 panic；仅除零/模零为运行时诊断"，并把 §Interpreter hardening 该条移入 Known limitations；② 改实现——checked_add/sub/mul 溢出时发 RUNTIME 诊断（属运行时行为变化，按冻结裁决 §14-3 的精神应过一次 RFC；仅改文档则无冻结冲突）。同时建议 README:105 删去或限定 "grep-verified" 的范围。

P1-1 浮点 inf/NaN/大数显示：格式化 bug + 跨后端分歧，且未列入已知分歧清单

事实一（显示 bug）：interpreter.rs:248-255 的 to_display 对无小数点的 Float 一律补 ".0"，而 Rust f64 的 to_string() 对特殊值产出 "inf"/"NaN"（不含点），于是：

$ lom flt.lom           # println(1.0 / 0.0); println(0.0 / 0.0)
inf.0                   ← 解释器
NaN.0
$ lom build flt.lom --target wasm && node run_wasm.mjs flt.wasm
Infinity.0              ← WASM 后端（JS String() 再补 ".0"）
NaN.0

事实二（跨后端分歧）：同一程序两后端 stdout 不同（inf.0 vs Infinity.0）；大数同样分歧——println(100000.0^6) 解释器输出 1000000000000000200000000000000.0（Rust Display 全展开），WASM 输出 1.0000000000000002e+30（JS 科学计数法）。实测均于 2026-09-03。

为何定 P1：SPEC_FOR_AI:675 的"已知分歧"清单只列了闭包捕获语义与 JSON 数字拆分两条，浮点显示分歧不在其中——"byte-identical dual-backend" 的宣称存在未记录的边界例外；eval 套件没有 inf/NaN/大数用例，所以 114/114 无法暴露它。对以"两后端逐字节一致"为卖点的项目，这是主张的边界漏洞；显示语义不属冻结的语言面，可修。建议：统一 Float 显示规则（含 inf/NaN/科学计数法阈值），补入 SPEC_FOR_AI 已知分歧清单（若不统一）并加 eval 用例。

P1-2 let 绑定递归闭包被误报 Error 级 NAM003 —— 静态拒绝、动态合法

复现：

fn main() -> Unit
    let f = fn(x: Int) -> Int
        if x == 0
            0
        else
            f(x - 1)      ← 此行被报 NAM003 "调用未定义函数 'f'"（Error）
        end
    end
    println(f(5))
end

实测（2026-09-03）：解释器与 WASM 两后端都正确运行输出 0；但 --check 退出码 1、--json 报 ok: false、severity 为 error。README:113 明确声称 WASM 支持 "recursive closures via pre-bind + env slot patch"——即递归闭包是被设计支持的功能，静态检查与动态语义、与文档三方不一致。

根因：typechecker.rs:505-526——Stmt::Let 先 check_expr(value, env)（:506）后 env.define(name, ...)（:525），闭包字面量体内自引用时名字尚不在作用域。修法现成：初始化器为闭包字面量时先预绑 Unknown（Rust 对 let f = || f() 同样报错，但 Lom 的动态语义选择支持它，静态侧应当跟随）。

为何定 P1：误报是 Error 级——把 --check 当 CI 门禁的用户会被误杀合法程序；对"LLM 写代码、诊断导引修复"的核心场景，Error 级假阳性是最伤信任的缺陷类型（LLM 会徒劳地"修"一个正确的程序）。eval 套件无此类用例（category 04 closures 的递归都走命名函数）。

P1-3 闭包捕获 mut 变量：两后端行为相反（2 vs 1）且零诊断

复现（实测 2026-09-03）：let mut x = 1; let f = fn() -> Int { x } end; x = 2; println(f()) —— 解释器输出 2（共享作用域），WASM 输出 1（创建时值拷贝）。

记录状态：SPEC_FOR_AI:675 已如实记录该分歧并警告 "do not rely on either side's behavior"——文档没撒谎。但 --check 对该程序输出"诊断通过，无错误"（退出码 0）：已知陷阱没有任何诊断防线。MUT001（v0.20.0）已建立 TypeEnv.mutables 可变性跟踪，"闭包体引用 mut 绑定"加一条警告的机制是现成的。按项目"诊断先行"的哲学，这是明显的防线缺口：一个 LLM 完全可能写出这种代码，在不同后端得到相反结果且全程无提示。建议：EFF/MUT 家族加 warning 级代码（冻结裁决允许新增 warning-only 代码，§14-3），或至少在教程/SPEC_FOR_AI 高亮区重复警示。

P2-1 深递归栈溢出为裸 Rust panic，无结构化诊断

实测：5 万层递归 → thread has overflowed its stack、退出码 127，无 RUNTIME 诊断。SECURITY.md:14 与冻结裁决 §14-②（"structured stack-overflow diagnostics" 在 post-1.0 挂账）均已如实记录，约 10⁴ 安全深度与实测相符（本条为已挂账项，列出供完整性）。

P2-2 浮点字面量不支持科学计数法 —— spec 如实，但与"LLM 自然写法"目标相悖

实测：println(1e300 * 1e5) → PARSE001（期望 ')' 得到标识符 'e300'）。SPEC_FOR_AI:28 只定义 3.14 形态，行为与 spec 一致（非失实）；且语言面已冻结，v1.x 内无法补。但 Python/JS/Rust 背景的 LLM 写 1e9 是高概率自然形态——这与 5.4 节为 "n = " + 42 专门做拼接提升的动机（"LLM 自然写法被拒的缺口"）属于同类问题，却留在了冻结面外。建议：教程/SPEC_FOR_AI 显著标注此差异（若未标注），错误修复侧可考虑把"1e300 → PARSE001"识别为高置信度改写建议（1000000000.0 等价形式），不改语法即可缓解。

三、最重要的几个发现（展开）

发现 1：「不撒谎」纪律在最敏感的一份文档上出现审计型失实（P0-1）

这个项目的差异化资本之一就是文档可信度：三轮文档腐坏清扫、"严禁虚构数据"写进 CONTRIBUTING、上轮审查的 P0 也是"喂给 LLM 的 spec 与实现矛盾"。本次的 checked arithmetic 失实比普通腐坏更重一档：它位于安全加固清单（安全边界的正式声称），且被 README 标注为 "grep-verified"——一个实际未执行的验证标注。冰山提示：6.6 清单的验证程序是"抽查 grep"，凡 grep 验证不了的条目（语义行为类）都可能是下一个失实点。建议把"安全清单条目必须附可执行验证命令"写入 SECURITY.md 的 Audit procedure 一节——这恰是该节已有的思路（第 34 条已写 grep -rn "unsafe" src/ 必须为空），只需推广到每一条。

发现 2：静态/动态语义的两处分歧，直击 repair-native 主张的软肋（P1-2 / P1-3）

Lom 的核心卖点是"LLM 写错 → 诊断指路 → 原地修复"。这个闭环的隐含前提是诊断永远不说谎：Error 意味着真的错，干净意味着真的对。本次发现恰好各打破一半：递归闭包案例里诊断"错怪好人"（Error 级假阳性，LLM 会去"修"正确的代码）；mut 捕获案例里诊断"纵容真凶"（两后端结果相反、全程零警告，违反 "byte-identical" 的用户预期）。两条的修复机制都是现成的（预绑 Unknown / mutables 警告），成本低于收益。冻结裁决允许新增 warning-only 诊断代码，不动语言面——法律层面无障碍。

发现 3：工程底座经受住了独立复核 —— v1.0 冻结的底气是真实的

验证矩阵（§一）的每一行都是本次亲手复跑的命令，无一失败。特别值得指出的是这类项目少见的几项：生产代码 panic 面全量清点后 21 处全部有构造性守卫（list_get 先边界检查后 unwrap、lexer 在 is_at_end 后 peek、WASM 浮点 % 走 trunc 公式使 unreachable 真不可达——逐条核过）；80 轮随机 fuzz 零崩溃支撑 "total parser" 声称；上轮审查整改清单 9 项抽查全部落地且 HANDOVER:354 记录了"驳回/暂缓"及理由（治理成熟度罕见的部分）。相比之下，两个月的单人项目能把自举验证做到 147 文件六模式逐字对齐，这份冻结声明背后的工程是硬的。

发现 4：eval 套件的覆盖盲区有一个共同形状——"边界值不进集合"

本次三个跨后端分歧（inf/NaN 显示、大数显示、mut 捕获）全部是 114 个 eval 任务覆盖不到的：任务集由"典型形态"构成，而分歧恰恰住在边界值里（IEEE 特殊值、量级极端、别名/可变性交互）。fix_corpus 的思路（成对坏/好文件 + 逐字比对）已经证明"语料即覆盖"的方法有效，建议给 eval 增加一个 backend-parity edge 小分类（inf/NaN/大数/-0.0/空串/空表/单元素元组/mut 捕获/递归闭包），双后端跑同一任务即可把这类分歧变成 CI 可见的回归。
