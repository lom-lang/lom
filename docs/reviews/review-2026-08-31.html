审查日期：2026-08-31 · 审查范围：git 历史、核心文档、源码实现、评测体系与示例 · 审查方式：只读（未修改任何项目文件）· 审查基线：main @ ad7e387（v0.19.0）

总体结论：Lom 是一个定位清晰、工程纪律远超一般个人项目的 AI 原生语言实验：100% conventional commits、零依赖零 unsafe、417 个测试全绿、三平台 CI 含 WASM 双后端 golden 比对、文档以"不撒谎"为核心纪律。真正的差异化创新在 LLM 修复闭环（lom fix --apply + 诊断 schema 族）。 主要风险集中在两点：(a) 文档腐坏呈慢性复发——尽管已有三轮清扫，本次审查仍在 README、两份 spec、eval/README、HANDOVER 中抓出多处与实现矛盾的内容，其中喂给 LLM 的核心文档 SPEC_FOR_AI.md 存在过时描述，恰是项目立身之本；(b) "AI 原生"的实证宣称超出证据——99% 通过率来自 1 个匿名模型 × 1 次采样 × 无对照组的开卷测试，未达到项目自订的"至少 3 个 LLM"标准。

二、Git 历史审查

优点

  • 提交纪律极佳：125/125（100%）使用 conventional-commit 前缀（docs 58、feat 56、fix 6、chore 3、spec 1、ci 1），无一条 "wip"/裸 "fix"。主题普遍带阶段编号 + 版本号，可追溯性极强。
  • feat/docs 成对工作流：几乎每个 feat 跟一条 docs: Phase X.Y 记录，配合 docs/HANDOVER.md 做 AI 会话交接——本身就是"AI 原生"工作流的示范。
  • 发展脉络清晰：规范文档 → LLM-coding 核心 + eval → 修复引擎 → 自举 → 工程化（CI/社区治理）→ WASM 后端（两天 v0.7.0→v0.15.0）→ 修复引擎深化 M1–M4。
  • 产物卫生有过失误但处理得当：examples/_file_demo_tmp.txt 曾误入库，由专门提交 b2f2deb 清除并补入 .gitignore，有留痕。

问题

  • P2 Cargo.lock 未入库（.gitignore 排除）。零依赖下无实际风险且 CI 注释说明是有意为之，但 Rust 官方惯例建议二进制项目提交 lockfile 以保证可复现构建；若未来破例引入依赖，此处会立刻变成真问题。
  • P2 .gitattributes 仅 2 行，无 eol 规则。项目自己踩过 CRLF 坑（fix: lom fmt preserves CRLF — Windows CI fmt gate false positive），用 gitattributes 显式约束换行符可从源头规避，目前是空白。
  • P2 tag 类型前后不统一：v0.5.1–v0.15.0 为附注 tag，v0.16.0 起改轻量 tag；所有提交无 GPG 签名。
  • P2 提交信息语言不统一（早期英文、后期中文）。
  • 提示 单点风险：单人、单分支、直接推 main、无评审环节。脉冲式开发（单日最高 35 提交，间隙期 0 提交）。当前有未提交的 Phase 8 RFC 草稿（docs/rfc/0003-phase8-full-selfhosting.md）。

三、核心文档审查

定位与设计

项目将"AI 原生"拆解为 AI-workload-native（已明确放弃）与 AI-coding-native，并于 2026-08-07 复盘后聚焦 LLM-repair-native：MoonBit 占"一次写对"，Lom 占"写错后原地修复"。叙事自洽，每个语法决策要求回答"是否降低 LLM 错误率"（DESIGN_RATIONALE.md:17），且大量决策有实测回溯（如拒绝 a..=b 因双 range 运算符是已知 LLM 混淆源）。修复机制的置信度分级与"猜测性修复永不自动应用"的安全策略设计成熟；M4 如实记录了 LEX001 与迭代闭环组合产生语义误修的已知限制——"不修但记账"的诚实度少见。RFC 机制实质运转（模板含强制 LLM-impact 分析节）。

优点

  • 文档间有权威层级声明（HANDOVER.md:337"与代码不符时以代码为准"），有三轮文档腐坏清扫记录。
  • SECURITY.md 实质可用：威胁模型明确、加固清单可验证、accepted risks 如实列出（无递归深度守卫、file 模块无路径校验等）。
  • CONTRIBUTING.md 非模板：零依赖需 RFC、禁虚构数据、回归三件套含具体命令、诊断码命名约定。

语言设计层面的疑点

  • 渐进类型"类型错误只是 warning、程序照跑"与 §5.1 "Reassignment is a compile error" 表述冲突，gradual 语义下重赋值到底落到哪一级未说清。
  • match 双臂形态（Form A 无需 end / Form B 需要）是 HANDOVER 反复踩坑（"第三次应验"）的根源——引入这个不对称本身与"降低 LLM 错误率"的目标存在张力，值得在 RFC 层面重新评估。
  • List 无字面量语法（只能 list_cons 链）是明显表达力缺口；RFC-0003 的零新语法冻结意味着 v1.0 也不会有。

五、评测体系与示例审查

优点

  • eval 框架设计规范：113 任务 / 10 分类，prompt 由脚本从 tasks JSON + 上下文机械生成，自包含可复现；runner 有 ps1/sh/wasm 三实现，CI 三平台跑验证且 108 任务在 WASM 后端做 parity gate。
  • 数据真实可复现：本次审查实测复现了参考解 113/113 与候选集 99/100（唯一失败正是 REPORT 记录的 078）。
  • examples 覆盖广（30+ 示例），bootstrap/stmt_interp.lom（52KB 自举解释器）是最有说服力的"语言够用"证据。

问题

  • P1 核心实证宣称超出证据：99% 通过率来自 1 个匿名模型 × 1 次采样、无温度/seed 记录、无 pass@k、无跨语言对照组；prompt 内嵌完整语言速览属开卷考试，测的是"LLM 跟随 spec 的能力"而非"语言对 LLM 友好"。项目自订标准（lom-project-guide.html §3.3："至少覆盖 3 个 LLM 才能宣告 AI 原生成色"）未达成。"60% 基线"是预期值而非实测。
  • P1 任务 ID 冲突：09_modules.json 最后一题与 10_error_repair.json 第一题都是 086——113 个任务只有 112 个唯一 ID；candidates 按 <id>.lom 寻址会互相覆盖。
  • P2 13 个新任务（101-113）从未跑过 LLM；任务难度偏浅（easy/medium/hard ≈ 47/44/22，多数 solution 5–15 行，无多文件、无长上下文、无需求模糊题）。
  • P2 apply_test.lom 是故意写错的文件但命名无标注，易误导浏览者；todo.lom 运行时写 examples/_todo_data.json，未确认是否被 gitignore 覆盖。

七、结语

Lom 的一个月历史展示了一种罕见的组合：高强度的 AI 驱动开发节奏 + 严格的工程纪律 + 对已知限制的诚实记账。修复闭环（诊断 schema 族 + 置信度分级 + 迭代 apply）是真实且有前途的创新方向。当前最大的杠杆不在写更多功能，而在两件事：让 SPEC_FOR_AI.md 这份"喂给 LLM 的契约"永不过期，以及用多模型、有对照的实验把"AI 原生"从叙事变成证据。前者守住身份，后者决定成色。

本报告由独立审查会话基于只读检查生成，所有数据均经实际命令验证（git log、cargo test、eval 复现、clippy 等）。引用格式为 文件:行号，基于 v0.19.0（main @ ad7e387）。
