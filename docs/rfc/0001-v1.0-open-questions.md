# RFC 0001: v1.0 范围裁决 —— 关闭 LANGUAGE_SPEC §11 剩余四个开放问题

- **RFC**: 0001
- **Title**: v1.0 scope adjudication — close §11 open questions #5-#8
- **Status**: accepted
- **Created**: 2026-08-23

## Motivation

`LANGUAGE_SPEC.md` §11 自 Phase 0 起挂着 8 个开放问题，其中 1-4 已随实现关闭（range/字符串拼接/char/match 分隔符），5-8（多返回值、self、trait 派发、pub 粒度）长期悬置，且 spec 结尾"将在 Phase 0 spec 迭代中解决"的句子已陈旧腐坏。悬置的开放问题有两个实际害处：

1. **文档说谎**：spec 把 trait（§6.6）、type alias（§6.5）、pub（§8.3）写成"未来阶段"的草稿特性，但实测它们从未实现、关键字层面从未保留（`src/lexer.rs` 的保留字只有 20 个，不含 `struct/trait/impl/type/pub`）。LLM 读 spec 后会生成 `pub fn`、`type UserId = Int` 这类必被拒的代码——违背 Lom"降低 LLM 犯错率"的身份承诺。
2. **v1.0 无法定义**：不裁决这四个问题，"v1.0 冻结"没有边界。

四个裁决均经项目维护者（用户）逐项确认（2026-08-23）。

## Proposal

逐项裁决（均为"不做/关闭"，无一引入语法或语义变更）：

1. **#5 多返回值 → 元组 + 解构（关闭）**：`return (a, b)` 与 `let (a, b) = expr` 均已实现（Phase 5.1 起），即为正式答案；**拒绝 out-param**。
2. **#6 self → 明确不设（关闭）**：Lom 没有任何方法/接收者概念（结构记录只承载数据，行为在普通函数里），self 关键字无从谈起。若未来引入方法机制，由新 RFC 重开。
3. **#7 trait 派发 → v1.0 不做（关闭）**：§6.6 的结构化 trait 草稿标记为已拒绝。静态/动态派发都以方法系统为前提，而方法系统被刻意排除。
4. **#8 pub 粒度 → 不做 pub（关闭）**：顶层 item 全公开（Phase 4.4 包管理器现状即如此），不引入 per-item 可见性修饰符。

配套文档整改（随本 RFC 一并落地）：

- `LANGUAGE_SPEC.md`：§3 关键字表改为与 lexer 实测一致（20 个保留字，补 `and/or`，删 struct/trait/impl/type/pipe）；§4.3 表、§4.5.1 运行模式表（默认运行自 v0.6.0 起执行类型检查，诊断走 stderr 不拦截——原文"No"已腐坏）、§4.5.5、§6.4 穷尽性（MAT001 是 warning 不是 error）、§6.5、§6.6、§8.3、§11 逐条标注裁决结果。
- `SPEC_FOR_AI.md`：关键字列表同步修正；§8 `pub` 标注改为"rejected"。
- `DESIGN_RATIONALE.md`：新增 §11.8 记录四项裁决及理由；§7 的类型别名缓解措施标注为未实现。

## LLM-impact analysis

本 RFC 的全部效果是**缩小** LLM 需要记忆的表面积：

- 关键字表从"宣称 29 个"收敛到实测 20 个，LLM 不会再把 `trait`/`pub`/`type` 当保留字生成必然 PARSE001 的代码。
- 每个被拒绝的特性（out-param、self、trait、pub）都属于"名字/绑定簿记"类——正是 LLM 实测中最差的类别（对照 SPEC_FOR_AI §10 常见错误清单）。
- 无新增语法，`SPEC_FOR_AI.md` 不需要新增任何章节；Quick Reference 不变。
- 风险：LLM 训练语料中 Rust 习惯（`pub fn`、impl 块）仍会偶发渗出；缓解靠现有的 NAM003/PARSE001 诊断 + `lom fix` 提示，无需新机制。

## Alternatives considered

- **实现 trait（静态派发）**：拒绝。引入方法解析、impl 表、一致性检查，是解释器+类型检查器双侧的 phase 级工作量，且与"结构类型 + 普通函数"的现有正交性冲突；没有实测需求驱动（99/100 eval 未暴露任何"缺 trait"失败）。
- **实现 pub（per-item）**：拒绝。包管理器已在"全公开"假设下工作且无问题报告；隐私是规模问题的答案，而 Lom 当前没有规模问题。
- **保持开放继续挂起**：拒绝。开放问题挂在 spec 里就是文档腐坏的源头（本次已抓出 4 处直接谎言）。
- **out-param 形式的多返回值**：拒绝。第二输出通道与 Lom"值域统一"的设计冲突。

## Drawbacks

- trait/pub 的草稿章节保留在 spec 中（标注为 rejected），文档体积没有缩小——但保留被拒绝的草稿是刻意的：下一个 AI/贡献者能看到"为什么不"，避免重复提议。
- 若未来真实需求出现（如大型包需要隐藏内部辅助函数），重开需要新 RFC 且可能引入破坏性变更——接受此风险，因为 v1.0 前的诚实承诺就是"不冻结"。

## Unresolved questions

- type alias（§6.5）未被本 RFC 正式裁决为"永不"，仅标注"未实现且 v1.0 无计划"。若 v1.0 后有文档化意图区分的真实需求，可单独 RFC。
- v1.0 的完整范围定义（除本 RFC 的四问之外还包含什么）是下一步"编译器阶段 RFC"的前置输入。
