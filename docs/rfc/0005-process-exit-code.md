# RFC 0005: 进程退出码（让 Lom 程序能自己决定以什么状态退出）

- **RFC**: 0005
- **Title**: process exit code — a Lom program's say in how its process exits
- **Status**: accepted — **implemented in v1.18.0（2026-11-25）**（2026-11-24 起草；同日用户裁决"待裁事项全部做，可并行，也可顺序，按合理的方式完成。"——取建议项乙；七个未决问题的答案见文末"裁决记录"；实施批设计见 [designs/0032](../designs/0032-process-exit-code.md)，其 §8 是实施记录，minor 发版，排在工具链 patch 批之后）
- **Created**: 2026-11-24

> 起草缘由：2026-11-23 的 B7 实验（一个 agent 仅凭 SPEC_FOR_AI 写出完整项目）把"程序无法设置退出码"列为全部 26 条卡点里唯一的"高"severity。用户裁决"先起草 RFC 供裁"。本文件只陈述事实与选项，不代表任何已定方向。

## Motivation

**现状（均为 v1.17.0 实测）**：

- 解释器执行完 `main` 后把返回值直接丢弃（`src/interpreter.rs:1184`——`self.exec_block(&main.body, env)?;`，`Ok` 里的值不被读取）。
- 没有任何内建能设置进程退出码；43 个内建里没有 `exit` / `quit` 一类。
- 因此 **Lom 程序自身只能以 0（正常结束）或 1（运行时错误）退出**。探针：`fn main() -> Int` 尾表达式为 `5` → rc 0；`return 7` → rc 0。

**为什么是问题**：

- 命令行工具靠退出码报告结果，这是写 CLI 工具的第一项能力。B7 实验里的 Markdown linter 为了给出"0 / 1 / 2"三种状态，只能：检查出 error 时**故意触发一次运行时错误**来拿到 1；再写一个启动脚本配合状态文件来拿到 2。每次非零退出 stderr 还会多两行解释器诊断。
- Lom 写的工具无法原生满足 ACRI 自己的退出码矩阵（§2.2："工具自身失败 ≥ 2"）——参考实现的命令行能给的保证，用这门语言写的程序给不了。
- 用 C、Rust、Python 习惯写代码的模型会自然地写 `int main()` 返回状态或 `sys.exit(n)`；在 Lom 里前者的返回值被静默忽略，后者不存在。

**影响面（实测，供评估迁移成本）**：

- 被跟踪的 555 个 `.lom` 文件里，`main` 返回类型非 `Unit` 的 **0 个**（524 个 `-> Unit`，31 个无注解或无 `main`）。
- eval 138 题的参考解全部是 `fn main() -> Unit`；评测 runner 要求退出码 0。
- 仓内三处候选代码存档共 514 份（`eval/candidates` 100、`eval/iter_runs` 219、早期评测存档 195），`main` 返回类型**全部为 `Unit`**。 caveat：大规模 pass@k 采样的原始输出多数未归档，这 514 份只是其中留存的子集。
- **普查补全（2026-11-24 供料，逐个判定）**：被跟踪 `.lom` 555 个 = `-> Unit` 524 + 无注解 6 + 无 main 25，声明为 `-> Int` 的 0 个；138 道参考解全为 `-> Unit`；存档六处（上列三处加 `eval/candidates_rerun` 6930）合计 8137 份里，main 的声明类型与实际返回不符的为 **0**。

## Proposal

**建议项 = 乙：`fn main() -> Int` 的返回值成为进程退出码。**

- `main` 声明为 `-> Int` 时，其尾表达式或 `return n` 的值即进程退出码；声明为 `-> Unit`（或缺省）时退出码恒为 0（与今天相同）。
- 运行时错误仍然以 1 退出，不受本提案影响。
- 取值：只接受 0..255；超出范围的值按运行时错误处理（rc 1）。理由：各平台对超范围值的截断方式不同（实测：Git Bash 对 256 取 0、对 -1 取 127；Windows 原生保留 32 位值），定死 0..255 才能让同一程序在各平台表现一致。
- 三个实现的现状（事实）：
  - 解释器：返回值已被产生，只是被丢弃（`interpreter.rs:1184`）；需要读取它并在进程收尾处映射为退出码。
  - AOT（`lom build --target wasm`）：产物的导出 `main` **已经**把该值作为带标签的 i64 返回（实测：`-> Unit` 返回 2，`-> Int` 尾表达式 5 返回 80，`return 7` 返回 112——执行者供料与规划者 2026-11-24 复跑一致）；node 宿主侧目前忽略它（`eval/runner/run_wasm.mjs:280`）。**产物不带 main 的声明类型**（`-> Unit` 或无注解的 main 尾表达式为 5 时同样返回 80），所以只改宿主脚本不够，代码生成侧也要按声明类型收尾。
  - L2 自举编译器：**不是**与 AOT 同源的发射路径（起草时此处写错，2026-11-24 供料更正）——L2 产物不带标签，`-> Unit` 的 main 是 void，带返回类型的 main 返回裸值（`-> String` 为裸指针）。本批只改 L2 宿主脚本的映射，不动自举编译器（动它会改变 quine 字节数）。
- 语法、关键字、内建数、诊断码**均不变**。

**备选**：

- **甲：新增内建 `exit(code: Int)`**。能从任意嵌套调用中退出（乙做不到）。代价：内建 43 → 44（冻结面变化）；约 20 处登记写位要同步（宿主解释器、类型检查签名表、AOT 代码生成的导出表与宿主导入表、L2 自举编译器的内建摘要表与编译路径、自举解释器的签名表与运行时分派）；强 quine 的字节数会变；AOT 产物要从 `env` 多导入一个宿主函数。
- **丙：乙 + 甲都做。**
- **丁：不做，只在规范里写清限制**（现状；规范文档批 `c24c9b9` 已在 SPEC_FOR_AI §1 规则 11 写明）。

## LLM-impact analysis

- **符合模型既有习惯**：`int main()` 返回状态是 C 系语言的传统，`-> Unit` 等价于"总是成功"。对模型来说没有新语法要学。
- **新出现的失败模式（必须写进规范）**：今天 `fn main() -> Int` 尾表达式写什么都无所谓；改后，一个本意是"成功"的程序若以非零整数结尾，会变成失败。评测 runner 要求退出码 0——模型若把计算结果当作 `main` 的尾表达式返回，该题就会从"通过"变成"不通过"。现存 514 份存档候选里没有这种写法，但原始输出多数未归档，不能据此断言从未出现。规范里需要一句显眼的"成功的程序应以 0 结尾，或声明 `-> Unit`"。
- **与评测数字的关系**：已发表的 pass@k 数字是在旧语义下测得的。改后若候选的写法分布不变，数字可比；若出现非零结尾的成功程序，可比性受损。这一点应在实施前用一次零成本采样核对（见未决问题 3）。
- **在 SPEC_FOR_AI 里的样子**（规范文档批 `c24c9b9` 已按现状写入，取乙或丙时成对改写）：§1 规则 11（"No `exit` builtin — a program can only exit 0 or 1"）与 "`main`'s return value is ignored" 的口径；§11e（工作流）说明"退出码 0/1/自定义"三者的来源；§11i 表里 `exit(code)` / `quit` 一行按裁决去留。

## Alternatives considered

- **启动脚本 + 状态文件**（B7 实验的实际绕法）：能用，但每个工具都要带一个平台相关的包装脚本，且拿到退出码 1 靠故意制造运行时错误——这不是语言该让用户做的事。
- **只做甲不做乙**：能力更完整，但代价是全部内建登记写位加 quine 变化，且对一个"返回状态码"的常见需求来说过重。
- **丁（不做）**：零成本；代价是 Lom 写的 CLI 工具永远需要包装脚本。

## Drawbacks

- 改变一个**现有可接受写法**的含义（`-> Int` 的 `main`）：从"返回值被忽略"到"返回值是退出码"。现存程序里没有受影响的，但这是语义变化，所以按 RFC 走。
- 三个实现的宿主侧都要改（解释器收尾、AOT 与 L2 的 node 宿主、playground 的显示已支持非零退出码）。
- 文档面：LANGUAGE_SPEC §7 的退出码句（现为两带旧口径）、SPEC_FOR_AI、ACRI 参考消费器的退出码说明。
- `fix --run` 需要定义"程序以自定义退出码结束"算什么观察结果（见未决问题 5）。
- 双后端差分对拍以"解释器 rc == wasm 宿主 rc"为准（`tools/diff_test.py`），现口径只有 0 / 1，需同步。

## Unresolved questions

1. **取甲、乙、丙还是丁。**
2. **取值范围与超范围处置**（本稿建议 0..255，超范围按运行时错误）。
3. **实施前是否做一次采样核对**：让模型在"带退出码规则的规范"下写一批候选，看成功程序里出现非零结尾的频率——决定评测可比性的风险有多大。
4. **是否属于"语言面冻结"事项**：SPEC §14 列的四项（语法、关键字、诊断码、内建）都不直接覆盖"main 返回值的语义"；本稿按"需要 RFC"处理，但这本身是读法，由用户确认。取甲则明确触冻结面（内建数）。
5. **`fix --run` 的观察结果**：程序以 3 退出，算 `pass`（带退出码）、还是新的一种 outcome。
6. **AOT 与 L2 的宿主侧**：`run_wasm.mjs`、`run_selfcomp.mjs`、playground harness 如何把带标签的返回值映射成退出码；自举六模式与 verify_selfcomp 的 rc 断言是否受影响（它们比的是 stdout 与 rc=0 的成功路径，预期不受影响，须实测）。
7. **时机**：若取乙，是否单独成批、何时升版（语义新增 → minor）。

## 裁决记录（2026-11-24）

用户裁决（原话）："同意改。待裁事项全部做，可并行，也可顺序，按合理的方式完成。"——取建议项乙。上面七个未决问题的答案由规划者按已呈报的建议代定（用户可否决）；实施落点见 [designs/0032](../designs/0032-process-exit-code.md)。

1. **取乙**：`fn main() -> Int` 的返回值即进程退出码。
2. **取值 0..255，超范围按运行时错误**（rc 1，落既有码 RUNTIME000，不新增码）。
3. **采样核对待用户单独授权后再做**——它要调用模型，费用与凭据属不可预授权事项，规划者不自行发起。零成本证据已足：8137 份存档候选、555 个被跟踪文件、138 道参考解，main 的声明类型与实际返回不符的为 0；评测 prompt 不改。【2026-11-25 追记（实施后）：用户已给出模型调用常设授权（记录见 WORKSPACE-LOCAL.md §9），核对已做——给评测 prompt 的副本加上退出码规则，glm-5.3（两个分类）与 deepseek-v4-pro（一个分类）各 3 次采样共 90 份候选，全部仍声明 `-> Unit`、新旧二进制下都通过；风险在本次规模下没有出现，样本量小、不构成"不会出现"的证明（方法与读法见 [designs/0032](../designs/0032-process-exit-code.md) §8）。】
4. **按"需要 RFC"处理**（语义新增）：本 RFC 即授权源；不触四项冻结面，取乙不改内建数。
5. **`fix --run`**：程序以自定义退出码结束不算失败——`outcome: "pass"`，加一个只在 `-> Int` 时出现的可选退出码字段；超范围按运行时错误。
6. **AOT 与 L2 两侧**：AOT 代码生成按 main 的声明类型收尾，AOT 宿主与 L2 宿主脚本同步映射退出码；L2 自举编译器与自举解释器本批不动，"L2 通道对非 Int 的 main 不保证"登记为分歧。自举六模式与 verify_selfcomp 里现有的 rc 断言经逐项核对不受影响。
7. **时机**：工具链 patch 批之后单独成批，minor（v1.18.0）；按 MAINTENANCE §2.2.1 事件 1，此前累计的 patch 级修复随该 minor 一并发布。
