## 2. 设计原则

1. **最小面**：每笔只改造成缺口的那一处行为；不顺手重构。
2. **冻结面**：不新增 error 级码、不改既有码的 severity；新 warning 级码以裁决点 2 的裁决为授权源。
3. **信封契约 append-only**：`lom-diag/v1` 不改既有字段语义；本批不改 `ok` / rc 对 `--check` / `--json` 的含义（裁决点 2 取甲或丙时除外——届时 `--check` 对坏 import 程序由 rc 0 变 1）。
4. **版本**：patch 级。按 MAINTENANCE §2.2.1（发版时点条款），本批**累计不随批升版、不切 tag**，改动记入 CHANGELOG 的 Unreleased 段；何时发 patch 由发版事件决定。
5. **不宣称修复率**：本批不包含、也不暗示任何"agent 修复成功率提升"的数字。

## 3. 逐笔设计

### 3.1 R234 + R243：`lom build` 的退出码与 JSON 合法性（裁决点 1）

- **退出码**（裁决点 1 取"改"时）：`check_and_report_file` 回传"该文件是否有 error 级诊断"（判据用 `!diags.ok`——仅 error 级置 false，warning 不置）；两个检查循环（依赖包 `main.rs:831-833`、根目录 `:851-853`）累计；尾行之后任一文件有 error 级诊断 → `exit(1)`。warning-only 维持 rc 0。
- **源文件不可读**：并入工具失败带 rc 2（ACRI §2.2 "unreadable input ≥ 2"；现只打 stderr、不影响 rc）。
- **`--json` 模式同口径**：现在它在逐文件循环之前就 `return`（`main.rs:799`），依赖解析成功时恒 rc 0 / `ok: true`，与源文件诊断无关。改为人读与 JSON 两个模式对同一项目给出同一个 rc：JSON 模式静默跑同一套逐文件检查只为决定 rc，**信封字段不变**（designs/0021 "JSON 模式 schema 面稳定"的边界保留）。
- **R243（随 R234 修，无选边）**：`path` / `error` 用既有 JSON 转义函数落盘。Windows 上它是主平台上的非法输出，无论裁决点 1 如何都修。
- **文案**：`--help` 退出码段（`cli.rs:229-238`）与口径注释（`cli.rs:447-458`，其中"无 lom.toml → 1"已是错值，实为 2）同步。
- **既有边界处置**：designs/0021 §3 该两条**原位加注**"本边界于 designs/0029 批经用户裁决推翻"，不回写原文（R113/R138 先例）。
- **不做**：`✗` 标记对 warning-only 文件也出现（ cosmetic，另议）；带文件路径 `lom build <file> --target wasm` 在类型 error 时不拦截编译（另一条路径，另议）。
- **测试**：翻转三处既有断言（rc 0 → 1，文案同步）；新增进程级——依赖包含 error → rc 1；依赖包仅 warning → rc 0；根目录文件 parse error → rc 1；仅 PKG007 → rc 0；源文件不可读 → rc 2；`--json` 模式的 rc 与人类模式一致；`--json` 输出可被 `json.loads` 解析且路径含反斜杠时仍合法。

### 3.2 R235：import 的静态校验（裁决点 2）

**建议项 = 乙：新增 warning 级码 `NAM007`（import 目标不可解析），静态、带位置；运行期 RUNTIME005 不变。**

- **检查位置**：typechecker 首遍逐条处理 import 处（`collect_import`，`mod.rs:351-367`——此处已有模块名、导入项与 `from` 行的 span）。
- **范围（本批）**：只校验**标准库模块**的导入项——模块名是标准库模块而导入项不在其导出表中（数据源 = `interpreter::module_of` 与标准库模块表，单一事实源）。非标准库模块名（外部包、拼错的模块名）在 fix / apply / LSP 路径没有包信息，本批不判，避免误报。
- **位置**：锚在 `from` 行（`ImportDecl.span` 现成，不改 AST）；消息给出该模块的可用符号表。
- **severity 与行为**：warning——`--check` / `--json` 对这类程序的 rc 与 `ok` 不变（仍 0 / true），`fix --run` 仍会执行并观察运行期 RUNTIME005；运行期行为零变化。代价如实：一个"确定的错误"被标成 warning 偏轻——这是 §14 在不走 RFC 的前提下唯一允许的形态。
- **码表联动**（新增码的全部写位）：`codes.rs` 的码表与长文案表各 +1（`lom codes --json` 总数与 `lom explain NAM007`）；doc_audit 的源码计数锚随 FAIL 清单同步；LANGUAGE_SPEC §7.3 码表与 SPEC_FOR_AI §11c 码表各加一行；符合性映射里的码数同步。
- **fix 分派表**：`NAM007` 加一个 hint-only 臂（永不自动应用）；顺带把 RUNTIME005 两处只列 io/string/math 的过时提示文案（`fix.rs:869`、`diagnostics.rs:296`）改为不枚举模块。
- **测试**：typechecker 单测（未知符号 / 标准库模块不导出 / 合法导入含别名零误报 / 非标准库模块名不误报）；进程级（w20 形态——坏 import 未被使用：`--check --json` 出现带位置的 NAM007、rc 0、`ok: true`；运行模式 stderr = 静态 NAM007 一条 + 运行期 RUNTIME005 一条。坏名字被使用的形态：在使用点的既有 NAM003 之外**另加** import 行的 NAM007，NAM003 的既有行为不变）。`tests/d0028_runtime_position.rs:131-135` 现断言 stderr 以 `[runtime] error (0:0): [RUNTIME005]` 开头——改后前面多一条静态警告，该断言随批更新。
- **既有资产**：eval 41 题里 broken 含 import 的 16 题、会触发该校验的 0 题（执行者扫描 + 规划者复核 `eval_prompt_check` 的比较口径为 code+severity 多重集）；spec_examples 现有示例无坏 import。

**备选**：
- **甲**：复用 RUNTIME005、在静态阶段以 error 级发出（stage 取 `type`）。信号最强（`--check` 变 rc 1、`ok` 变 false），但落在冻结面读法乙的灰区、首次出现"RUNTIME 前缀 + 静态阶段"的组合、要改写 SPEC_FOR_AI 的成文承诺，且 `fix --run` 对坏 import 程序由"执行观察"变"静态跳过"。
- **丙**：新增 **error** 级码（如 NAM007 error）。severity 诚实、rc 正确，但明确触碰冻结面——须另走 RFC + minor。
- **丁**：不做。

### 3.3 R236：依赖包诊断的可见性（裁决点 3）

**建议项 = 甲：stderr 提示 + 计数，信封与 rc 不变。**

- 入口文件的三条路径（`--json`、`--check`、运行）在项目有 `lom.toml` 依赖时，用无文件 build 的同一套逐文件 externals 算法（`package_closure_externals` / `closure_symbols`，`main.rs:950-981`）静默检查各依赖包源文件；有诊断则在 stderr 打一行：`依赖包里有 N 条诊断未在此显示（E 错误 / W 警告）——在项目根目录运行 lom build 查看全部。` 无诊断则不打。
- `--json` 的 stdout 不变（提示只走 stderr）；`ok` / rc / 信封字段不变；fix / apply 不消费多文件诊断（其单文件假定不碰）。
- 成本如实：运行路径每次多付依赖包源文件的类型检查（包规模小；无清单的单文件程序零成本）。
- **备选**：乙——依赖包诊断合并进入口信封（逐条带 `file`、`ok` / `summary` 跨文件汇总、人类可读输出标明文件）。这是更彻底的解法，但牵动 fix / apply 全链的单文件假定与两处既有的位置错报渲染，需要独立设计；本批不做，登记为后续候选。
- **测试**：进程级——依赖包含 warning → 提示含 1 警告；含 error → 提示含 1 错误；依赖包干净 → 无提示；无清单单文件 → 输出与改前逐字节一致；`--json` 的 stdout 与改前逐字节一致。

### 3.4 R237：类型诊断打印两遍（无选边）

- **形态（规划者定）= 甲**：第一遍（`main.rs:352`）不动；运行时错误分支（`:417-418`）只打新增的那一条运行时诊断，其后补一行完整汇总（`共 N 个诊断（E 错误，W 警告，H 代码洞）。`——需要给 `Diagnostics` 加一个 `pub(crate)` 的汇总行访问器，现 `summary()` 为私有）。每条诊断恰好出现一次。
- 不取"撤第一遍、运行后合并打一份"：那会改变静态诊断相对程序 stdout 的先后。
- **测试**：进程级——1 条静态 warning + 1 次运行时错误 → stderr 中该静态码恰 1 次、运行时码恰 1 次、汇总行 `共 2 个诊断（1 错误，1 警告，0 代码洞）。`；对照：仅静态诊断且运行成功 → 仍打印一次。既有五处 `starts_with("[runtime] error …")` 在无静态诊断的程序上继续成立。
- 连带收益（不作宣称）：迭代修复评测把上一轮 stderr 原文喂回模型，重复的诊断文本自此不再进入反馈。

### 3.5 R238：二元运算类型警告的位置（无选边）

- `binary_result_type` 增一个 span 形参，调用点（`mod.rs:725`）传入该二元表达式的 span；三处 `0, 0` 改用 span——位置 = 二元表达式起点（左操作数起点），与 NAM003 同为词法列、`anchor: exact`。
- 同族顺带：TYPE002 的 match 守卫处（`mod.rs:1152-1158`，span 现成）一并补位置；运算符渲染统一成符号形态（现 `'+'` 与 `Mul` 混用）。
- **不补**（如实登记，R247 保持 open）：元组解构数量不匹配（TYPE001，`mod.rs:505-515`——需给 AST 节点加 span）与子模式数量不匹配（TYPE003，`mod.rs:1322-1333`——在自举 `--static` 比对集内，须自举侧同位）。
- **文档**：五处"TYPE001-3 已带位置"的宣称改成精确表述（哪些带、哪些不带）。
- **评测资产（规划者定）**：eval 127 / 131 两题 prompt 内嵌的 TYPE001 是无位置的旧形态——**不重采**，保持与已发表测量时点一致；在 eval/README 注明"内嵌形态为采集时点（v1.17.0 及更早）的逐字输出"。`eval_prompt_check` 只比 code + severity，不受影响。

### 3.6 R242：依赖包内运行时错误的来源文件（v1.17.0 缺陷修复，裁决点 4）

- **机制**：解释器登记函数时记下来源文件（函数名 → 路径；入口文件与各依赖包文件各自登记）；`call_function` 外壳在执行函数体期间把"当前来源"设为该函数的来源文件，执行完恢复；位置侧通道从 `(line, col)` 扩为 `(line, col, 来源文件)`，`eval_expr` 外壳在最内层写入时一并记下当时的来源。
- **渲染**：上报点按来源文件取源码行并填写 `Diagnostic.file`；来源为入口文件时行为与今天完全一致。
- **已知边界（如实）**：闭包按"调用它的那个函数"的来源归属——跨文件定义并在别处调用的闭包，出错时仍可能归到调用方文件（与 v1.17.0 现状同级，不更坏）；要精确需给闭包值加字段（值表示改动，风险不成比例）。
- **性能**：每次用户函数调用多一次哈希表查找——验收时做同目录交错 A/B 确认在 ±3% 带内（方法见 HANDOVER §3）。
- **测试**：单元级（来源随调用切换与恢复；入口 / 包函数 / 包内嵌套调用）；进程级（§1 表中的探针：报错文件为 `dep/dep.lom`、源码行为 `    n / (n - n)`）；单文件程序输出与改前逐字节一致。

### 3.7 R249：以 `return expr` 收尾的函数被误报 TYPE010（修法无选边；是否并入本批 = 裁决点 5）

- **修法**：`check_block` 在无尾表达式且**最后一条语句是 `return`** 时，把块类型记为未知（这条路径不正常产出值），函数级与闭包级的"声明返回 vs 实际返回"比对随之不对它下判断。不引入新的诊断。
- **真阳性一条不少**（实施批逐条锁）：`return` 语句自身的类型检查不动——`-> Unit` 函数里 `return 3`、`-> Int` 函数里 `return "s"` 照旧报带位置的 TYPE010；尾表达式类型不符照旧报；分支只 `return` 不全（`if a` 里 `return 1`、之后落空）的函数照旧报"实际返回 Unit"；`return 3` 之后还有语句的，照旧按末尾语句的类型判。
- **同型顺带**：闭包体的同型误报（"闭包返回 Unit，但声明返回 Int"，`mod.rs:858` 的另一处发射点）按同一规则处理。
- **三实现一致律**（2026-11-24 L2 实跑后更正——初稿写"L2 只有 `return` 语句级检查、没有函数尾类型比对"，系未经实跑的推断，不成立）：TYPE010 不在自举 `--static` 比对集内（`tools/verify_selfhost.py --static` 覆盖 NAM003 / TYPE003-arity / EFF001 / MAT001）。L2 自举编译器除 `return` 语句级检查（`self_comp.lom:9829-9842`）外，另有尾表达式类型检查（`[L2T001] 尾表达式类型与返回类型不符`）与"void 函数的尾表达式产值"拒绝。L2 口径下实跑（`target/probes/spec_doc_batch/planner/accept11_out.txt`）：收尾 `return` 的四种形态（具名函数 / if-else 全 `return` / elif 链全 `return` / 带返回注解的闭包）**全部 COMPILED**——即现行宿主误报本身就是一处宿主与 L2 的不一致，修复后两侧一致；T3 落空形态、T4 尾表达式类型不符、"`-> Unit` 函数末语句是有值调用"三类在 L2 是编译期拒，宿主修复后维持报警，方向一致。**未核**：F5（循环后 `return`）、F6（`main` 收尾 `return`）、F8（内联 if-return 形态）三个形态尚未做 L2 实跑，由实施批补齐；L2 的"全终止闭包返回类型不可精确推断"规则（`self_comp.lom:3333/3536`）与本修复的交互未逐一核对。解释器与 AOT 的运行期行为本就正确，不动。
- **既有资产**：仓内无测试断言函数级文案（`git grep` 全仓跟踪文件："实际返回"除发射点 `mod.rs:397` 外只在文档与审查归档的引文里出现）；受影响的 8 个被跟踪文件见 §1 表，verify_selfcomp 对正例只比两侧运行的 stdout 与 rc、不看宿主 `--check`（`tools/verify_selfcomp.py:518`）。
- **测试**：typechecker 单测（收尾 `return` 的具名函数 / 闭包 / if-elif 全 `return` → 零 TYPE010；四个真阳性形态照旧）；进程级（§1 表的七个误报形态 `--json` 零诊断；T1–T5 形态诊断逐条不变；`-> Unit` 函数末语句是有值调用仍报 TYPE010）；L2 回归：上列四种收尾 `return` 形态（改前改后都应 COMPILED）与三个 L2 编译期拒的真阳性形态（T3 / T4 / 末语句有值调用）的 L2 结果逐一相同——改前基线见 `accept11_out.txt`。

## 4. 横切面

- **三实现一致律**：五笔加两笔均不改 codegen、WASM 发射层与 L2 自举（R235 的 AOT / L2 两侧本就已静态拒绝）。R236 / R237 / R242 的行为变化会随同一份 Rust 源出现在 playground 引擎里——playground 冒烟须重跑；现有冒烟断言不受影响（执行者逐条核对）。
- **ACRI**：`lom build` 不在 ACRI 命令集内；R234 取 1 后与矩阵第一行一致，符合性映射加一行登记。R235 取乙不改变任何既有码。
- **既有资产**：eval 双后端与 prompt 校验零影响（执行者扫描 + 规划者复核）；自举六模式不受影响（R238 不在比对集内，TYPE003 模式位本批不动）；新增测试会改变测试计数——按 doc_audit FAIL 清单同步各写位。
- **playground**：行为变化自动生效，但线上产物（gh-pages）不随本批部署——部署是独立呈批件。
