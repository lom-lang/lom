第一部分 · 项目定位与设计哲学

1.1 Lom 是什么

Lom（Language of Machine）是一门渐进式融合的 AI 原生编程语言。它从"LLM 编码原生"出发——让 LLM 写代码时出错率低、易修复、容错可解析——在工具链与语义稳定后，再渐进引入"AI 工作负载原生"的硬本事（张量、自动微分、异构计算）。

双关含义：既指"给机器（LLM）写的语言"，也暗示"机器时代的语言"。

1.2 为什么需要 Lom

当前 AI 原生语言赛道存在两个被混淆的方向：

方向代表设计取向问题
AI 工作负载原生 Mojo / NEURON / Bend 张量、自动微分、GPU 异构计算 语法复杂，LLM 写起来更难；赛道红海，Mojo 已有 17.5 万开发者
LLM 编码原生 MoonBit（工具链侧）/ Zero（JSON 诊断） 容错解析、结构化错误、线性语法 赛道空白，仅 MoonBit 一家有明确意图且仍处意图阶段，缺公开评测

Lom 选择先占空白赛道（LLM 编码原生），用差异化定位站稳脚跟，再向工作负载侧扩展。这与"直接对标 Mojo"的正面竞争路径相反，是一条侧翼切入路线。

1.3 与现有项目的差异化定位

项目定位Lom 的差异
MoonBit工作负载原生 + 工具链 AI 友好Lom 先做编码原生，工具链更激进（容错解析器是一等公民）；评测集公开

1.4 四条设计哲学

  1. 局部性 > 全局性：声明与使用必须在同一视野内闭合，避免"远距离验证"。
  2. 容错性 > 严谨性：语法错误不致命，类型错误可降级。LLM 写错也能"跑一部分"，配合工具链逐步修复。
  3. 线性 > 嵌套：流式生成天然适合 pipeline、early return、guard clause，不适合深层嵌套。
  4. 自描述 > 隐式约定：意图写在代码里（可执行 docstring、schema 即类型），减少 LLM 需要"猜约定"的场景。

1.5 不做什么（防范围蠕变）

明确排除项（阶段 0-3 内不做，阶段 4+ 视情况）：
  • 不做张量一等类型、自动微分、GPU 异构计算（阶段 4 可调整里程碑）
  • 不做完全独创语法——采用熟悉语法壳（Rust 系），蹭训练数据先验
  • 不做高表达力上限——刻意保持"低表达力上限、高表达力下限"
  • 不为追求新颖而造语法——熟悉壳 + 改造内里

Rust 单元测试

关键 bug 修复：跨行运算符消歧
发现并修复了 LLM 友好性的关键 bug：当一行以数字结尾、下一行以 - 开头时， 解析器会将 - 误认为二元减法而非一元取负（如 n > 0\n-1 被解析为 n > (0 - 1)）。 同理，跨行的 ( 被误认为函数调用。

修复方案：在 parse_addition 和 parse_postfix 中检查 token 行号， 跨行的 - 视为一元取负，跨行的 ( 不视为函数调用。 这是"局部性 > 全局性"设计哲学的体现——同一行的表达式才是一个整体。

已知限制（Phase 2 修复）

  • 字符串字面量不支持 UTF-8 多字节字符（lexer 按字节处理）
  • 函数不能作为一等值传递（仅闭包字面量可以），顶层函数名不能赋值给变量
  • 无类型检查（运行时动态类型），Fn 作为函数参数的类型占位符（运行时忽略）
  • 无错误恢复（语法错误即停止），无 LSP/REPL

差异化优势（相对 MoonBit）：① AI 修复闭环更完整——lom fix --apply 自动应用高置信度修复，MoonBit 无此能力；② 效应系统更纯粹（! [IO] 强制 I/O 显式化）；③ LLM 实测数据扎实（99/100，error_repair 100%）；④ 渐进式类型（动态可跑 + 检查可选，LLM 试错友好）。

劣势：① 生态空白（无包管理/LSP/REPL/多后端）；② 性能路径缺失（树遍历解释器，MoonBit 有 LLVM+Wasm+Native）；③ AI 原生特性单薄（缺形式化证明、安全沙箱）；④ 工具链不完整。

三、差异化定位

MoonBit 已占据"AI 原生语言"主赛道且资源充足，Lom 不应正面对标全栈路线，聚焦 MoonBit 尚未做透的细分：Lom = "LLM 代码修复原生"（LLM-repair-native）。MoonBit 追求"让 LLM 一次写对"（生成→检查→验证→重生成），Lom 追求"LLM 写错后高效修复"（生成→诊断→原地补丁修复，不重生成）。互补而非竞争。

四、Phase 4 方向决策

三档方案对比后选择方案 A：聚焦"LLM 修复原生"差异化 + 补齐基础工具链。理由：保持语言主线、聚焦 lom fix 差异化（MoonBit 未做）、补齐必要基础（REPL/LSP/包管理是语言标配）、投入产出比合理（不做 JIT/形式化证明等高投入项）。

放弃原 Phase 4"AI 工作负载内核扩展"（张量/自动微分/Python 互操作/MLIR）：Mojo 被高通收购后 AI 计算赛道资源充足，Lom 无需进入；工作负载扩展投入大（12-20 周），投入产出比不如修复工具链。

  • 错误 JSON 字段：fix 字段格式要让 DeepSeek 能直接消费并正确修复；针对 DeepSeek 对中文+JSON 的响应特性做字段顺序与措辞优化
  • 评测集样本：包含 DeepSeek 易犯的错误模式（如常见语法偏差、命名习惯），让评测更针对性
  • 对照基线：阶段 2 起，Claude/GPT 作为对照基线，确保 Lom 不是"只对 DeepSeek 过拟合"

3.3 防过拟合策略

过度针对单一 LLM 优化会让 Lom 在其他 LLM 上表现差。缓解：
  • 错误 JSON 字段遵循通用结构化规范（稳定 error_code + fix 字段 + retry 字段），不针对单一 LLM 加私有字段
  • 评测集至少覆盖 3 个 LLM 才能宣告"AI 原生"成色
  • 每新增一个 LLM 评测对象，重新审视 SPEC_FOR_AI 是否需要调整
