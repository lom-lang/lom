第一部分 · 项目定位与设计哲学

1.1 Lom 是什么

Lom（Language of Machine）是一门渐进式融合的 AI 原生编程语言。它从"LLM 编码原生"出发——让 LLM 写代码时出错率低、易修复、容错可解析——在工具链与语义稳定后，再渐进引入"AI 工作负载原生"的硬本事（张量、自动微分、异构计算）。

双关含义：既指"给机器（LLM）写的语言"，也暗示"机器时代的语言"。

1.2 为什么需要 Lom

当前 AI 原生语言赛道存在两个被混淆的方向：

方向代表设计取向问题
AI 工作负载原生 Mojo / NEURON / Bend 张量、自动微分、GPU 异构计算 语法复杂，LLM 写起来更难；赛道红海，Mojo 已有 17.5 万开发者
LLM 编码原生 MoonBit（工具链侧）/ Zero（JSON 诊断） 容错解析、结构化错误、线性语法 赛道空白，仅 MoonBit 一家有明确意图且仍处意图阶段，缺公开评测

Lom 选择先占空白赛道（LLM 编码原生），用差异化定位站稳脚跟，再向工作负载侧扩展。这与"直接对标 Mojo"的正面竞争路径相反，是一条侧翼切入路线。

1.3 与现有项目的差异化定位

项目定位Lom 的差异
MoonBit工作负载原生 + 工具链 AI 友好Lom 先做编码原生，工具链更激进（容错解析器是一等公民）；评测集公开
Mojo工作负载原生，性能优先Lom 不与之正面竞争，工作负载是阶段 4 扩展项而非身份
ZeroJSON 诊断，未规模化Lom 吸收其 JSON 诊断思想，但补齐完整语言+评测集+开源生态
Unison内容寻址，函数式小众Lom 不强绑内容寻址，保留为可选优化

1.4 四条设计哲学

  1. 局部性 > 全局性：声明与使用必须在同一视野内闭合，避免"远距离验证"。
  2. 容错性 > 严谨性：语法错误不致命，类型错误可降级。LLM 写错也能"跑一部分"，配合工具链逐步修复。
  3. 线性 > 嵌套：流式生成天然适合 pipeline、early return、guard clause，不适合深层嵌套。
  4. 自描述 > 隐式约定：意图写在代码里（可执行 docstring、schema 即类型），减少 LLM 需要"猜约定"的场景。

1.5 不做什么（防范围蠕变）

明确排除项（阶段 0-3 内不做，阶段 4+ 视情况）：
  • 不做张量一等类型、自动微分、GPU 异构计算（阶段 4 可调整里程碑）
  • 不做完全独创语法——采用熟悉语法壳（Rust 系），蹭训练数据先验
  • 不做高表达力上限——刻意保持"低表达力上限、高表达力下限"
  • 不为追求新颖而造语法——熟悉壳 + 改造内里

2.2 阶段 0：语言设计与规范（1-2 周）

阶段 0 · 语言设计与规范 研究性

目标：定语言身份，写规范，搭 repo 骨架。不写一行编译器代码。

产出物

  • LANGUAGE_SPEC.md：完整语言规范，含 EBNF、类型系统、效应系统、错误模型、模块系统草案
  • SPEC_FOR_AI.md：精简规范（<2000 词），专门给 LLM 读，对标 Codong 模式
  • DESIGN_RATIONALE.md：设计理念，讲清楚"为什么 Lom 是 AI 原生的"
  • README.md、LICENSE（Apache 2.0）、.gitattributes（Linguist 注册）、CI 骨架
  • 语言命名 + 文件扩展名（已定：.lom）+ GitHub org/lom-lang/lom

技术栈

纯文档 + Git + GitHub Actions（文档 lint + markdown 链接检查）

目标 LLM 适配（DeepSeek 优先）

  • 写 SPEC_FOR_AI 时，用 DeepSeek 做"可读性测试"：喂规范让它生成代码，看合法率
  • 错误 JSON 字段设计针对 DeepSeek 响应特性优化（中文+JSON 的响应特性需重点测试）
  • 评测样本要包含 DeepSeek 易犯的错误模式

退出标准

把 SPEC_FOR_AI.md 喂给 DeepSeek（及 1-2 个对照 LLM），生成的代码片段语法合法率 > 80%。

2.3 阶段 1：最小解释器（4-6 周）

阶段 1 · 最小解释器 研究性

目标：能跑通基本语法子集的树遍历解释器。不做类型检查、不做张量、不做工作负载特性。

技术栈

Rust + logos（词法）+ 手写递归下降（语法）+ Pratt（表达式）+ tree-walking（解释）

语法子集

fn let let mut if else while for return
基本类型：Int Float Bool String Unit
运算符 + 函数 + 闭包

场景

LLM 生成代码的运行环境（最小版）——LLM 生成简单脚本，解释器能跑。

退出标准

建立 10+ 个测试用例（斐波那契、字符串处理、循环、递归），LLM 基于 SPEC_FOR_AI 生成的代码能跑通其中 70%+。

2.4 阶段 2：LLM 编码原生核心（6-10 周）— 身份阶段

阶段 2 · LLM 编码原生核心 MVP

目标：把"LLM 编码原生"做出来。这是与其他语言的区别点，也是 Lom 身份的成立点。

核心特性（按优先级）

  1. 容错解析器：半截代码产出"带洞 AST"，对标 Zero，让 LLM 边写边得反馈
  2. 结构化 JSON 错误诊断：含 error_code（如 NAM003 风格稳定码）、fix 字段、retry 字段，对标 Zero
  3. 类型信息导出：lom info <file> 输出 JSON，给 LLM 当上下文
  4. AI 可读修复计划：lom fix --plan --json，对标 zero fix --plan --json
  5. 线性 pipeline 语法：|> 运算符
  6. 模式匹配：match，穷尽性检查
  7. 结构类型：对标 TypeScript，LLM 不需要记类名
  8. 渐进式类型：默认动态可跑，标注后检查
  9. 显式效应系统：副作用在签名中声明
  10. 错误是值：Result<T, E>，不用异常

技术栈

Rust + 解释器 + 基础类型检查器（两遍：签名收集 + 体检查）

场景

LLM 生成代码的运行环境（完整版）。

核心产出 · LLM 生成通过率评测集

评测集：100 个任务，覆盖语法/类型/错误修复，放在主 repo 的 eval/ 目录，开源。 评测对象优先级：DeepSeek（阶段 0 即适配）→ Claude/GPT（对照）→ 后续 Kimi/GLM/Gemini。 主流 LLM 生成通过率 > 基线（基线需先测，预计 60%+）。

这是阶段 2 的核心产出，也是 Lom "AI 原生"成色的硬指标——回应"营销热度远超学术共识"质疑的硬证据。

退出标准

评测集完成 + 主流 LLM 生成通过率达标 + 标志性 demo：LLM 生成错误代码 → Lom 返回结构化 JSON 修复建议。

2.5 阶段 3：可用 MVP（8-12 周）

阶段 3 · 可用 MVP MVP

目标：语言可用于小规模实际任务。

技术栈升级

+ Cranelift JIT（毫秒级编译，性能可用，docs File 2 推荐的中间层）

新增

场景扩展

从"LLM 运行环境"扩展到"通用脚本"+"后端服务雏形"。

退出标准

能用 Lom 写一个完整 CLI 工具（如 todo list）或简单 Web 服务（如 JSON API）。

阶段末方向复盘

阶段 3 完成时做一次方向复盘，根据当时 Mojo/MoonBit/Zero 的现状和 Lom 阶段 2-3 的反馈，决定是否推进阶段 4（工作负载扩展），或调整阶段 4 范围。

2.6 阶段 4：工作负载内核扩展（12-20 周）— 可调整里程碑

阶段 4 · 工作负载内核扩展 可调整

目标：加入 AI 工作负载原生的硬本事。这是"两者融合"的工作负载侧。

可调整性说明：本阶段投入大（12-20 周），且依赖阶段 3 末复盘结论。可能的结果：按计划推进 / 推迟 / 缩小范围 / 砍掉。复盘决策须在阶段 3 退出标准达成后 2 周内做出，并更新本文件。

新增

场景扩展

退出标准

能用 Lom 写完整 MNIST 训练脚本，性能不弱于纯 Python+numpy 的同等实现。

第三部分 · 目标 LLM 优先级策略

3.1 优先级排序与适配方案

优先级LLM引入阶段适配重点
P0DeepSeek阶段 0SPEC_FOR_AI 可读性、错误 JSON 字段响应特性、易犯错误模式采样
P1Claude / GPT阶段 2对照评测、跨模型一致性验证
P2Kimi / GLM / Gemini阶段 3+覆盖中文模型与多模态、扩展评测覆盖面

3.2 DeepSeek 优先的具体含义

  • SPEC_FOR_AI 设计：用 DeepSeek 做"可读性测试"，规范文档要让 DeepSeek 生成合法代码率 > 80%
  • 错误 JSON 字段：fix 字段格式要让 DeepSeek 能直接消费并正确修复；针对 DeepSeek 对中文+JSON 的响应特性做字段顺序与措辞优化
  • 评测集样本：包含 DeepSeek 易犯的错误模式（如常见语法偏差、命名习惯），让评测更针对性
  • 对照基线：阶段 2 起，Claude/GPT 作为对照基线，确保 Lom 不是"只对 DeepSeek 过拟合"

3.3 防过拟合策略

过度针对单一 LLM 优化会让 Lom 在其他 LLM 上表现差。缓解：
  • 错误 JSON 字段遵循通用结构化规范（稳定 error_code + fix 字段 + retry 字段），不针对单一 LLM 加私有字段
  • 评测集至少覆盖 3 个 LLM 才能宣告"AI 原生"成色
  • 每新增一个 LLM 评测对象，重新审视 SPEC_FOR_AI 是否需要调整

第四部分 · 7 个辅助规划维度

4.1 评测体系

  • LLM 生成通过率评测集：阶段 2 核心产出，100 任务，开源，放 eval/ 目录

  • TextMate 语法文件：.tmLanguage，阶段 0 提供，覆盖 VS Code/Atom/Sublime/GitHub 高亮

4.3 文档体系

  • LANGUAGE_SPEC.md：完整规范，阶段 0 起
  • SPEC_FOR_AI.md：精简规范（<2000 词），阶段 0 起，随语言演进同步更新
  • DESIGN_RATIONALE.md：设计理念，阶段 0 起
  • 教程：阶段 1 起逐步建立
  • 示例库：examples/，阶段 1 起
  • RFC 流程：阶段 3 起建立

4.4 AI 协同开发流程（内化 docs File 2 七步）

  1. 环境先行：先设计测试框架、CI、反馈机制，再写实现
  2. 上下文窗口管理：测试运行器只打印摘要，避免 LLM 上下文爆炸
  3. 快速反馈循环：采样测试 1%-10%，快速迭代
  4. 锁文件协调：多 Agent 任务分配，避免冲突
  5. 参考预言机：用 GCC/Rust 作为正确性参考
  6. 任务分解：编译器天然可分解（lexer/parser/interp/typeck 分模块）
  7. 分层使用 AI：AI 从 0 到 1，人工从 1 到生产级

4.5 风险缓解策略（针对 docs File 2 的 4 大风险）

风险影响缓解策略归属阶段
生态缺口（S4TF 教训） 致命 Python 互操作作为阶段 4 第一天特性；阶段 3 前编译到主流语言借力生态 阶段 4 起
AI 一致性天花板（10 万行） AI 辅助开发后期效率骤降 模块化设计，每模块控制在 5 万行以内；人工接管核心架构 阶段 0 起
MLIR 学习曲线陡峭 初期开发速度慢 先 Tree-sitter + 解释器验证语义，阶段 4 再引入 MLIR 阶段 4
AI 前范式科学状态 技术选型可能快速过时 保持架构可扩展（MLIR 方言可热插拔）；避免过早锁定范式；阶段 3 末复盘 阶段 0 起

4.7 差异化定位（持续维护）

Lom 的差异化三角：
  1. LLM 编码原生优先（赛道空白，MoonBit 仍在意图阶段）
  2. 工作负载渐进融合（不与 Mojo 正面竞争，阶段 4 可调整）
  3. 开源评测集（第一个公开 LLM 生成通过率评测集的 AI 原生语言）
每个阶段退出前，重新审视差异化是否仍成立。若 MoonBit/Zero 公开了类似评测集或显著改变了工具链方向，需更新本文件。
